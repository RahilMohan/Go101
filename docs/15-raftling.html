01Stack Evaluation

The stack: channels, an in-memory bus, and the Raft paper

raftling implements leader election, log replication, and commit advancement using nothing but stdlib primitives: goroutines and channels for the node event loop, an in-memory Hub message bus standing in for the network, and math/rand for election jitter. No RPC framework, no gRPC, no go.sum. The transport is a two-method interface — Send(m Message) and Recv() <-chan Message — which is the entire seam between the consensus logic and any real network you might bolt on later.

Rejected alternatives

  • Real-network Raft libraries (hashicorp/raft, etcd-io/raft) — the production answers, and deliberately not used here. etcd/io's library doesn't even own its transport or storage: it hands you Ready structs and expects you to wire I/O — which is exactly the work this project exists to teach from scratch. Using either library would replace the lesson (why terms exist, why the commit rule has a term check, what a step-down actually is) with configuration and glue.
  • TCP/gRPC transports instead of an in-memory hub — tempting for realism, fatal for testing. Real sockets make timing ambient, ports contended, and failure injection coarse. The Transport interface means a TCP implementation could be added without touching a line of consensus code — the boundary proves itself by existing.
  • Mutex-guarded shared Raft state — the style most tutorials use, and where most tutorial Rafts go subtly wrong. Splitting state across locks invites interleavings no test explores. One goroutine owning everything makes the state machine literally sequential: between two select cases, no other event can be observed.

What this stack uniquely teaches

  1. Consensus from the paper, honestly. Every subtle rule of Raft §§5.1–5.4 — one vote per term, election restriction on up-to-date logs, the current-term-only commit check that defuses Figure 8, step-down on any higher term — is implemented by hand against the paper's own numbering. Afterward, hashicorp/raft's source reads like documentation rather than archaeology.
  2. Actor-style state ownership. The single-goroutine event loop is Go's answer to "how do I write correct concurrent state machines": don't share memory, serialize events. This pattern recurs everywhere — game loops, protocol stacks, the runtime's own schedulers.
  3. Deterministic testing of distributed behavior. Partitions, drops, reordering, and duplication are usually things you hope your tests stumble into. Here they're API calls with seeded randomness, so the same interleaving reproduces on every machine — and the CI pipeline re-runs the suite three times under the race detector to keep it honest.
  4. The module-publishing story. A go.mod, a semver version, path-filtered GitHub Actions CI, and a README version note — the full lifecycle of shipping a Go module, exercised at the smallest scale it still applies to.

02Requirements

Derived directly from raft_test.go — the executable specification. If your implementation passes these tests (including -race), it satisfies the requirements.

Functional

  • R1 — Single-node clusters elect themselves and serve KV. A lone node reaches Leader, accepts Set, and answers Get with the written value — majority arithmetic must degrade gracefully to a cluster of one.
  • R2 — Exactly one leader per term among many nodes. Three nodes elect a sole leader whose term is stable, and every follower independently acknowledges the same leader ID at a term ≥ the leader's.
  • R3 — One vote per term, even against maximally up-to-date strangers. A forged "ghost" candidate with a huge log and a higher last-log-term receives zero grants from followers who already voted in the current term — and still gets explicit denials, not silence.
  • R4 — Quorum commits and read-your-writes. Set returns only after quorum commit; an immediate Get through the leader observes the value (linearizable read barrier). Followers answering Get fail fast with ErrNotLeader.
  • R5 — Partitioned minority serves nobody — no split brain. With the leader fully isolated, the majority side elects a replacement at a higher term, while the old leader fails both Set and Get with ErrNoQuorum. On heal, it steps down and catches up on replicated state, restoring exactly one leader.
  • R6 — Drops, delays, and reordering preserve commit order. With 35% seeded drop probability plus pair-swap reordering on every link, eight sequential Sets commit and all three replicas converge to exactly the expected map — proving ordered application despite hostile delivery.
  • R7 — Rejoined followers catch up. A follower black-holed during three commits resynchronizes to the exact committed state once its link heals — the log-matching/backfill path must work without snapshots.
  • R8 — Misconfigured fault policies never kill the process. Toggling DropProb at runtime with a nil Rand falls back to a deterministic internal source instead of panicking inside the library-owned pump goroutine (where no caller could recover).
  • R9 — Higher-term rejections force immediate step-down. A leader receiving an AppendEntries rejection stamped with a higher term reverts to Follower at that term — Raft §5.1 applied to the reply path, not just inbound requests.
  • R10 — Inverted timing bounds are normalized, never negative. WithTiming(hb, 400ms, 300ms, …) swaps the bounds (min=300ms, max=400ms) instead of producing a negative jitter span that would panic rand.Int63n; equal bounds are legal too.
  • R11 — Local backpressure is distinct from lost quorum. A full request queue yields ErrBusy ("this node is congested"), while an uncommitable request yields ErrNoQuorum after the RPC timeout — callers can tell rerouting apart from waiting.

Non-functional

  • NF1 — Determinism where possible. Per-link seeded rand.Rand streams and injected clocks make fault scenarios reproducible; bounded polling replaces fixed sleeps.
  • NF2 — Race-clean under repetition. The suite must pass go test -race -count=3 ./solution/... (~20s wall clock) — repetition widens the interleaving window the race detector samples.
  • NF3 — Honest limitations. The package doc states up front: no persistence or snapshotting, no membership changes, no log compaction. A teaching Raft that hides these cuts would lie about what Raft actually requires.
  • NF4 — CI gates the contract. Path-filtered workflow runs gofmt, vet, verifies root stub tests fail, and runs the solution suite with -race -count=3.

03Architecture Decisions

D1: Actor-per-node — one goroutine owns all Raft state

for {
    select {
    case <-ctx.Done():
        return
    case m, ok := <-n.tr.Recv():
        ...
        r.handleMessage(m)
    case req := <-n.reqCh:
        r.handleRequest(req)
    case <-r.election.C():
        ...
        r.startElection()
    case <-r.hbC:
        r.broadcastAppend()
        ...
    }
}

The replica struct holds every piece of Raft state — role, term, votedFor, log, commitIndex, per-peer next/match, pending client requests — and exactly one goroutine ever touches it. Inbound network messages, client requests, election timers, and heartbeats arrive as events on four channel arms of one select. The consequence is architectural: there is no lock to forget, no field that needs atomic access, no interleaving where two handlers observe a half-updated term. The few genuinely cross-goroutine surfaces (Status(), Snapshot(), the stopped flag) publish immutable copies under a small mutex — observability, never mutation, crosses the boundary. This is why -race -count=3 passes not by luck but by construction.

D2: Fault injection as an API, not a sleep schedule

faults[id].Mutate(func(p *Policy) { p.DropAll = true })
// ... majority elects replacement, minority fails with ErrNoQuorum ...
faults[id].Mutate(func(p *Policy) { p.DropAll = false })

Classic distributed-systems tests simulate partitions by killing processes and sleeping through election timeouts — slow, flaky, and unable to produce specific interleavings on demand. raftling instead wraps every node's transport in a FaultTransport whose Policy supports DropAll, probabilistic DropProb, fixed Delay, and pairwise Reorder. Crucially, policies change at runtime only via Mutate, which takes the wrapper's lock — direct writes would race with the message paths. A partition becomes a one-line toggle inside a test, the heal is another toggle, and the entire scenario completes in milliseconds. The wrapper filters both directions (outbound Send and inbound Recv via its pump goroutine), so a "link" down is truly bidirectional.

D3: Injectable clock and randomness — determinism as a parameter

p.DropProb = 0.35
p.Reorder = true
p.Rand = rand.New(rand.NewSource(int64(42 + i))) // deterministic per-link stream

Election timeouts need jitter (otherwise nodes vote in lockstep forever), but ambient math/rand makes failures irreproducible. So jitter comes from an injectable *rand.Rand, and each test link seeds its own stream (42+i): the drop decisions for link n0 are identical on every machine, every run. Likewise the Clock interface exists so tests could drive timers by hand. The same principle guards misconfiguration: if DropProb is set but Rand is nil, the fallback derives a source from the wrapper's message counter rather than panicking — because the inbound check runs inside the library-owned pump goroutine, where a panic would take down the whole process with no recover possible.

D4: Reads as log entries — the OpRead commit barrier

case reqGet:
    e := Entry{
        Index: r.lastIndex() + 1,
        Term:  r.term,
        Op:    OpRead,   // carries a key, writes nothing
        Key:   req.key,
    }
    r.log = append(r.log, e)
    ...

A leader answering reads straight from its state machine can serve stale data right after election — it may not yet know which entries are committed. Raft offers read-index protocols and leases; raftling uses the simplest correct form: append an OpRead entry and let it ride the normal replication path. Its reply resolves only in applyCommitted after applying everything through the barrier index, so a successful Get has, by construction, observed all previously acknowledged writes. The cost is real (every read costs a round of replication) and acceptable here — the point is that linearizability came from a mechanism, not a hope. When leadership is lost mid-barrier, stepDown fails all pending requests with ErrNotLeader; when quorum never forms, the client-side timeout answers ErrNoQuorum. An isolated leader therefore serves neither stale writes nor stale reads.

D5: An error taxonomy callers can act on

case n.reqCh <- &req:            // enqueue failed within timeout?
case <-ctx.Done():
    return "", false, ErrBusy      // local backpressure — retry/reroute
...
case <-ctx.Done():
    return "", false, ErrNoQuorum  // enqueued, never committed — wait/heal

Three sentinel errors divide the failure space by what the caller should do. ErrNotLeader: wrong node, look up the real leader and retry there. ErrNoQuorum: this node believed it led, but the request couldn't commit within the RPC timeout — typically partitioned away from the majority; retrying locally is futile until healing. ErrBusy: the node's local request queue (cap 32) didn't drain within the timeout — pure local congestion, unrelated to cluster health. Collapsing the last two into one "failed" error would send healthy-cluster clients into pointless rerouting during load spikes, and partitioned clients into hammering a dead leader. Error design is API design: the distinctions encode recovery strategies.

04Concept Walkthroughs

Leader election — terms, votes, and the up-to-date restriction

r.term++
r.state = Candidate
r.votedFor = r.n.id
r.votes = map[string]bool{r.n.id: true}
...
upToDate := m.LastLogTerm > r.lastTerm() ||
    (m.LastLogTerm == r.lastTerm() && m.LastLogIndex >= r.lastIndex())
canVote := r.votedFor == "" || r.votedFor == m.CandidateID

Time is chopped into monotonic terms — logical epochs that make "who is legitimate" decidable without synchronized clocks. A follower whose election timer fires increments the term, votes for itself, and solicits votes. Three rules make the outcome safe. First, votedFor grants at most one vote per term — two leaders in one term would each need a majority, and majorities overlap, so some node would have to vote twice (impossible). Second, the grant condition checks the candidate's log is at least as up-to-date as the voter's (compare last term first, then length): a candidate lacking committed entries can't win, which is precisely why new leaders inherit every committed entry. Third, any message bearing a higher term triggers stepDown generically before the type switch even looks at the message kind — stale candidates watching for their own votes get demoted by the very responses they solicited. Single-node clusters fall out of the same math: majority = 1, so self-vote wins instantly.

Log replication — conflict hints and the §5.4.2 commit rule

for idx := r.lastIndex(); idx > r.commitIndex; idx-- {
    if r.log[idx].Term != r.term {
        break                        // §5.4.2: only current-term entries
    }                                 // advance commitIndex directly
    count := 1
    for _, p := range r.n.peerIDs {
        if r.match[p] >= idx { count++ }
    }
    if count >= r.majority() {
        r.commitIndex = idx
        ...
    }
}

Replication is a two-sided negotiation. The leader probes each peer at next[peer], sending PrevLogIndex/PrevLogTerm as a consistency check: if the follower's log disagrees there, the AppendEntries is rejected — with a conflict hint telling the leader where to jump nextIndex (just past our log if we're too short, else the first index of the conflicting term), so convergence takes one round trip instead of decrement-by-one crawls. Matching prefixes are idempotent — replaying an entry whose term already agrees is a continue, not a duplicate — which is what makes duplicated deliveries harmless. On the leader side sits Raft's most famous subtlety: a replicated-but-old-term entry must not be committed directly, because a majority replica does not imply a majority of the current term has acknowledged it (paper Figure 8: such an entry can be overwritten by a new leader). Hence the break above — old entries commit only indirectly, dragged along when a current-term entry at a higher index reaches quorum. Delete that two-line check and you have a correctness bug no ordinary test will catch; raftling's structure makes the rule impossible to omit silently.

Step-down everywhere — including the gap the fleet review caught

func (r *replica) handleAppendResp(m Message) {
    if m.Term > r.term {
        // Raft §5.1: any message bearing a higher term — including a
        // rejection of our own AppendEntries — forces a step down.
        r.stepDown(m.Term)
    }
    if r.state != Leader || m.Term != r.term {
        return
    }

Raft §5.1 says: if any RPC request or response carries a term higher than yours, update yours and become a follower. The easy part is requests — handleMessage steps down on any inbound higher term before dispatch. The subtle part is responses. The original implementation filtered stale replies with an early m.Term != r.term return, which accidentally swallowed higher-term AppendEntries rejections too: a deposed leader rejecting its successor's heartbeats never learned the new term from those replies and kept self-reporting Leader (appending doomed client writes) until its own election timer or fresh inbound traffic corrected it. The adversarial fleet flagged this as a liveness-only deviation — no split brain was possible, since quorum never formed and all such writes failed with ErrNoQuorum — and the fix is the two lines above: inspect the term before filtering. Two regression tests pin it forever: the ghost-voter denial (R3) and TestLeaderStepsDownOnHigherTermAppendResp (R9). The transferable lesson: "check the common case first" filters are exactly where protocol violations hide, because they run before your carefully-written handler logic.

05Testing Strategy

Bounded polling, never sleeps

func eventually(t *testing.T, d time.Duration, what string, cond func() bool) {
    deadline := time.Now().Add(d)
    for time.Now().Before(deadline) {
        if cond() { return }
        time.Sleep(testPollGap)
    }
    t.Fatalf("timed out after %v waiting for: %s", d, what)
}

Every asynchronous assertion goes through eventually: poll a condition every 5ms until it holds or a 5-second deadline expires. No fixed time.Sleep(500*time.Millisecond) anywhere — sleeps are simultaneously too slow (when the system is fast) and too fast (when CI runners throttle), and they convert timing luck into pass/fail. Polling converts the question from "did it happen by now?" to "does it happen within budget?", which is the only question a distributed test can legitimately ask. Failure messages name what was awaited ("majority side elected replacement leader"), so a red CI log reads like a diagnosis.

The fault harness — scenarios as policy mutations

nodes, _, faults := newCluster(t, []string{"n0", "n1", "n2"}, nil)
faults[id].Mutate(func(p *Policy) {
    p.DropProb = 0.35
    p.Reorder = true
    p.Rand = rand.New(rand.NewSource(int64(42 + i)))
})

newCluster wires N nodes over one Hub, wrapping each transport in an individually addressable FaultTransport and registering cleanup. Tests then sculpt networks: DropAll isolates a leader (split-brain probe), blackholes a follower (catch-up probe), or combines DropProb + Reorder with per-link seeded streams (chaos probe). Determinism comes from those seeds — link i drops exactly the same messages on every run — while the assertion stays absolute: after 8 sequential Sets under 35% drop and pair-swapped delivery, all three replicas' snapshots must equal the expected map exactly. Exact-equality convergence is the strongest available claim: missing entries, reordered applications, or phantom values all break it. Replay tolerance gets its own coverage implicitly (duplicate deliveries are idempotent via the term-match continue) and explicitly via forged-message tests that triple-deliver and re-send traffic the cluster already processed.

Safety proofs disguised as tests

The sharpest cases aren't happy paths but forgery. TestDuplicateVotesRejectedInSameTerm invents a "ghost" node — a Hub inbox with no Node attached — and sends MsgRequestVote claiming a 10,000-entry log at a maximally recent term: the perfect candidate by the election restriction, and therefore the perfect probe of one-vote-per-term. The assertion is quantitative (zero grants, exactly len(nodes)-1 denials), so partial compliance fails loudly. TestPartitionedMinorityUnavailableNoSplitBrain walks the full lifecycle — isolate leader, verify majority promotes at a strictly higher term, verify the isolated leader refuses both writes and reads with ErrNoQuorum, heal, verify step-down, catch-up, and restoration of exactly one leader — the complete safety argument for the hardest property in the project, executable in milliseconds. And the fleet-review regressions (TestDropProbWithoutRandDoesNotKillProcess, TestLeaderStepsDownOnHigherTermAppendResp, TestWithTimingNormalizesInvertedElectionBounds, TestFullRequestChannelReturnsErrBusy) prove that adversarial findings became permanent specification rather than fixed-and-forgotten bugs.

Honesty note — the reorder policy: pair-swap reordering strands an odd trailing message until its partner arrives or Flush() is called. That's a harness liveness quirk, not a Raft defect — heartbeats pair up almost immediately, and Raft tolerates arbitrary swaps anyway. Similarly, full Hub/FaultTransport buffers drop silently rather than blocking senders; at teaching scale, retries recover via heartbeat ticks. Both behaviors are documented in code, not hidden.

Honesty note — the error taxonomy: ErrBusy and ErrNoQuorum are deliberately distinct and separately tested. A full request queue is this node's backpressure (reroute or back off briefly); an RPC-timeout expiry is the cluster's inability to commit (wait for healing). Tests exercise both paths mechanically — stuffing reqCh to capacity for the former, a hard partition for the latter — so the distinction is contractual, not aspirational.

Discipline: race × count × clock

The suite's final gate is mechanical: go test -race -count=3 ./solution/... passes in roughly 20 seconds (fresh-cache single runs land near 6–7s; -count=3 triples the interleavings the race detector samples). gofmt and go vet are clean, and the CI job re-runs the identical commands on every push touching the project. Bounded polling keeps total wall time dominated by real work rather than padded waits — the same reason the fault harness beats process-killing integration tests: faster feedback, tighter scenarios, reproducible failures.

06Go in the Wild

Where this stack runs in production

Raft is the most-deployed consensus protocol on earth, and Go is arguably its most popular host language:

  • etcd — Kubernetes' backing store, built on Raft via the go.etcd.io/raft library. That library is the industrial descendant of exactly what you built: it deliberately omits transport, storage, and networking, exposing a Ready-struct state machine — the Transport interface idea, taken to its logical extreme so embedders bring their own I/O.
  • HashiCorp Consul — service discovery and KV over Raft, using hashicorp/raft, the batteries-included sibling: TCP transports, snapshot stores, and boltdb logs wired for you. Same algorithm, opposite point on the packaging spectrum — comparing the two libraries is a masterclass in API tradeoffs.
  • CockroachDB — a distributed SQL database where every range of data is a Raft group, implemented in Go on top of a forked etcd/raft. Your per-range replication model — small consensus groups coordinating through a layer above — is the architecture at scale.
  • TiKV — the Rust/C++ counterpoint: the storage engine behind TiDB runs Multi-Raft with the protocol implemented in Rust, proof that the paper's ideas — and the figure-8 commit subtlety you handled in advanceCommit — transcend any one language.

Why hand-rolled consensus remains a rite of passage

  1. Every distributed database is Raft-shaped underneath. Group membership, WALs, quorum reads, leader leasing — the vocabulary repeats across etcd, CockroachDB, MongoDB, Kafka's KRaft mode. Having implemented the core, those systems' design docs stop being folklore and start being readable engineering.
  2. The actor/event-loop pattern is Go's native idiom for protocol state machines. TLS stacks, SSH servers, container runtimes, and the Go runtime's own netpoller all reduce to "one owner goroutine, events over channels." raftling's replica loop is the smallest complete specimen of that shape you'll find with real correctness stakes.
  3. Fault-injection harnesses are how serious distributed teams test. Jepsen made its name by doing to databases what FaultTransport.Mutate does to raftling — injecting partitions, reordering, and duplication while checking invariants. The gap between "tested" and "tested under adversarial scheduling" is precisely the gap between demo and production, and this project installs the habit early.

The through-line: channels + an interface + the Raft paper is not a toy combination — stripped of persistence and membership, it is the exact skeleton running inside the infrastructure that runs Kubernetes, Consul, and CockroachDB, exercised here in ~700 lines with every safety rule pinned by a regression test the adversarial fleet helped write.
