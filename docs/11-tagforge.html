01Stack Evaluation

The stack: reflect + strconv, nothing else

tagforge is built from two load-bearing stdlib packages — reflect and strconv — with strings, slices, fmt, errors, and math in bit parts. No validator library, no code generator, no go.sum. Every prior project avoided dependencies because they weren't needed; this one avoids them where most Go code reaches for them by reflex, which makes it the more interesting kind of discipline.

Rejected alternatives

  • Validator libraries (github.com/go-playground/validator) — the obvious production answer, and genuinely excellent at it. But it hides exactly the mechanics this project exists to teach: how a validate:"min=3,email" string becomes checks, how reflection walks fields, why errors carry paths. After building tagforge you can read validator's docs and know what its single-universe option flags are trading away. Using it here would turn the lesson into configuration.
  • Code generation — tools that emit a hand-written Validate() method per type are a legitimate different tradeoff: zero runtime reflection, compile-time errors, at the price of a build step and generated files in review. It's worth naming precisely because it solves the cost problem this project measures, while giving up the flexibility problem reflection exists for — dynamic types discovered at runtime (like tagforge's own reflect.StructOf test helpers) simply have no codegen story.
  • Hand-written Validate() error methods per type — no reflection at all, but no shared guarantees either: every type reinvents required/min/max, forgets aggregation, drifts from its siblings. Tag-driven validation buys uniformity; this project builds that uniformity once, visibly.

What this stack uniquely teaches

  1. reflect.Type / reflect.Value discipline. Types describe structure (walk it once); values hold data (walk it per call) — internalizing that split is what separates reflective code that works from reflective code that panics. Validity checks before Elem(), Kind dispatch instead of type assertions, and honest handling of unexported fields become muscle memory.
  2. Tag grammar parsing from first principles. A struct tag is just a raw string convention — f.Tag.Get("validate") hands you bytes and wishes you luck. Designing a small grammar (names, arguments, separators), failing closed on anything you can't fully understand, and fuzzing the parser until it can't be crashed is a complete miniature of real-world input handling.
  3. Precompilation as the escape hatch from reflection's cost. Reflection re-does structural work every call; a compiled schema does it once. The measured gap — roughly 15–25× depending on machine and config shape (on one M1 Pro laptop: ~3,300 ns/op naive vs ~170 ns/op compiled on a six-field nested config) — is not an implementation detail. It is the argument behind every schema-building API you'll ever meet, from JSON decoders to protobuf, measured here with your own benchmarks.

02Requirements

Derived directly from tagforge_test.go — the executable specification. If your implementation passes these tests, it satisfies the requirements.

Functional

  • R1 — Six constraints, correct across their type matrix. required (non-zero demanded), nonzero, min=N/max=N (numeric comparison or length for string/map/slice/array), email (exactly one @, non-empty local and domain parts), oneof=a|b|c (string membership). Each constraint passes and fails on the right side of each applicable type — ints, uints, floats, strings, slices, maps, bools.
  • R2 — All violations aggregate into one error. A config with five broken fields returns a single ValidationError naming every one, each wrapped with its dotted field path ("Server.Timeout") — never fail-fast.
  • R3 — Nested and embedded structs resolve to dotted paths. Named nested structs recurse (DB.Port); embedded structs promote so their fields validate at top-level paths (ID, never embBase.ID) — including embeds whose type name is unexported.
  • R4 — Pointers follow three rules. A nil pointer violates iff required; an optional nil pointer skips its remaining checks entirely (no spurious min/max failures on nothing); a non-nil pointer's pointee is checked after dereference.
  • R5 — Fail closed on bad tags. Unknown constraint names, missing or unexpected arguments, malformed numbers, and constraints that cannot apply to the field's type (including co-resident with an applicable one, e.g. min=1,email on an int) must error — in Validate and in BuildSchema alike — with messages naming the field and the offending token.
  • R6 — Strict numeric arguments only. min=nan, inf, 0x1p3, 1_000, 1e309 are rejected; plain decimals (-3, +5, .5, 1.5e-3) are accepted.
  • R7 — Non-struct input rejected cleanly. Ints, strings, maps, nil, and nil pointers produce an explanatory error, never a panic; pointer-to-struct input is accepted and dereferenced.
  • R8 — Schemas are reusable and type-checked. One built Schema validates many values without state leaking between runs, and rejects a value whose type doesn't match the schema's.
  • R9 — Unexported fields are ignored silently. Even an impossible tag on an unexported field triggers neither the fail-closed path nor a violation — reflection cannot meaningfully read-check them, so promising to would lie.
  • R10 — The parser survives arbitrary input. Under fuzzing, parseTag never panics, and an error result always implies nil constraints.

Non-functional

  • NF1 — Both execution modes agree. Every constraint test runs twice: through the naive Validate and through a prebuilt Schema.Validate — the two paths must be behaviorally indistinguishable.
  • NF2 — The performance claim is measured, not asserted. Benchmarks isolate naive reflection (parse-every-call) against the compiled schema, plus a third benchmark pricing BuildSchema itself so callers can compute their own break-even point.
  • NF3 — Zero dependencies, zero panics. Stdlib only; no code path panics on hostile input — hostile input gets errors.
  • NF4 — Documented edges stay documented. Numeric comparisons convert through float64: uint64 values beyond 253 lose precision. That is an accepted, tested edge — not a surprise.

03Architecture Decisions

D1: Two phases — parse-once plans vs parse-per-call

func Validate(v any) error {
    ...
    sp, err := buildStructPlan(rv.Type(), "")  // rebuilt EVERY call
    ...
}

func (sc *Schema) Validate(v any) error {
    ...
    sc.plan.run(rv, &errs)                    // plan built once at BuildSchema
}

Both public entry points execute the same structPlan.run; they differ only in who pays for planning. Naive Validate rebuilds the plan per call — simple, stateless, perfect for startup-time configs validated once. BuildSchema pays planning once and executes forever after — the right shape for hot loops. This is the entire architecture in one sentence: a validator is a compiler whose IR is a field plan, and the API question is merely when compilation happens. Keeping one execution engine guarantees the modes can't drift apart behaviorally (NF1 falls out of the structure, not from extra tests).

D2: The compiled plan — index chains, not field names

type fieldPlan struct {
    idx    []int       // index chain from the root struct value
    path   string      // dotted path used in error messages
    c      constraints // parsed tag — numbers already converted
    isPtr  bool        // final hop is a pointer
    nested *structPlan // non-nil when the effective field type is a struct
}

A plan entry records where to find the field (a chain of indices, so promoted embedded fields address as []int{embedIdx, fieldIdx}), what to check (constraints with parsing already done — oneof split into a slice, min/max held as float64), and where to recurse. At run time there is zero string work: no Tag.Get, no Splits, no ParseFloat — just walk(sv, fp.idx) followed by typed reads. The dotted path is computed at build time too, so even error construction avoids re-deriving names. This shape is deliberately boring: a flat slice of self-contained instructions that range can burn through.

D3: Fail-closed applicability, checked per constraint family

if c.minSet && !numericKind(t.Kind()) && !lengthKind(t.Kind()) {
    return notApplicable("min")
}
if c.email && t.Kind() != reflect.String {
    return notApplicable("email")
}
// required/nonzero apply to any type — no check needed

The tempting shortcut is checking applicability lazily at validation time: skip email on an int, move on. That silently accepts a typo'd or misapplied tag forever — the config author believes protection exists that doesn't. tagforge instead fails closed at build time, and critically, checks each family independently: a tag like min=1,email on an int contains one applicable and one inapplicable constraint, and the inapplicable one is still rejected by name. A combined "does any part apply?" check would let the email typo through. Fail-closed means: if we cannot make full sense of your intent, we refuse rather than guess.

D4: Aggregation with dotted paths, and nil-pointer semantics

*errs = append(*errs, FieldError{fp.path, "must be >= 10"})
// ValidationError.Error():
// tagforge: 5 violation(s): Name: ...; Server.Timeout: ...; ...

Validation stops at the first error is the default everywhere because it's easier — and it's worse UX everywhere, forcing users through fix-one-rerun cycles. tagforge accumulates a []FieldError through the whole walk and wraps them in one ValidationError implementing error (and discoverable via errors.As). Two rules keep the report honest. First, a zero value violating required short-circuits that field's further checks — piling "min failed" onto an empty string is noise. Second, pointer semantics are explicit: nil violates iff required, optional-nil skips remaining checks entirely (you can't length-check a string that doesn't exist), and crossing an intermediate nil pointer during walk leaves nothing to validate — skipped, not failed.

D5: Promotion rules mirror the language's own

if ft.Kind() == reflect.Struct && f.Anonymous {
    // Embedded structs promote even when the embedded type name
    // is unexported: reading its exported fields is legal.
    sub, err := buildStructPlan(ft, prefix)
    for j := range sub.fields {
        promoted := sub.fields[j]
        promoted.idx = append([]int{i}, promoted.idx...)
        sp.fields = append(sp.fields, promoted)
    }

Go itself promotes embedded fields — cfg.ID works even though embBase is unexported, because ID is exported. The validator matches: an embedded struct's tagged fields flatten into the parent's plan at top-level paths, prefixing each subtree index chain with the embedding field's index. Meanwhile plain unexported fields are detected via f.PkgPath != "" and skipped silently — including their tags. That silence is deliberate and tested: an impossible tag on an unexported field must not trip fail-closed, because the library never promised to enforce anything about fields it cannot legitimately read-check.

D6: Strict numbers by whitelisting around strconv

func parseStrictNumber(path, name, arg string) (float64, error) {
    if strings.ContainsAny(strings.ToLower(arg), "xni_") {
        return 0, fmt.Errorf("field %s: %s=%q is not a plain decimal number", path, name, arg)
    }
    n, err := strconv.ParseFloat(arg, 64)
    if err != nil || math.IsNaN(n) || math.IsInf(n, 0) {
        return 0, fmt.Errorf("field %s: %s=%q is not a plain decimal number", path, name, arg)
    }
    return n, nil
}

strconv.ParseFloat is designed for data interchange, so it happily parses NaN, Inf, hex floats like 0x1p3, and underscored literals — none of which belong in a validation tag where min=nAn is far more likely a typo than IEEE semantics. Rather than write a decimal parser, the wrapper bans any argument containing the characters those forms need (x, n, i, _) and then double-checks the parsed result isn't NaN/Inf. One subtle win: banning x/n/i/_ also keeps overflow forms like 1e309 out via the explicit NaN/Inf check on the result — ParseFloat returns ±Inf on overflow, which the second guard catches. Whitelist-first wrapping is the cheap way to make a permissive parser strict without owning its grammar.

04Concept Walkthroughs

reflect fundamentals — Type vs Value, Kind switches, validity before Elem

rv := reflect.ValueOf(v)
if !rv.IsValid() {          // ValueOf(nil) is the zero Value
    return rv, false
}
for rv.Kind() == reflect.Ptr {
    if rv.IsNil() {
        return rv, false
    }
    rv = rv.Elem()           // safe: Kind was checked, nil was checked
}

Reflection splits the world in two. reflect.Type describes structure — field names, tags, layout — and never changes for a given type, which is why planning walks Type once. reflect.Value holds actual data for one particular value, which is why execution walks Value every call. Confusing them is the source of most reflection bugs. Three disciplines keep it safe. Check IsValid() before anything — reflect.ValueOf(nil) yields a Value on which every other method panics. Check Kind() before Elem() — calling Elem on a non-pointer, or Elem on a nil pointer, panics; the value is telling you what it is if you ask. And dispatch on Kind, not concrete type: min=3 must treat int, int64, and a named type Port int identically, and Kind is the axis that erases those distinctions. Note also the split getters: signed kinds read via Int(), unsigned via Uint(), floats via Float() — using the wrong one panics, which is why numValue is an explicit three-way switch.

Struct tags are raw strings — the lookup convention is all you get

Timeout int `validate:"min=10"`
...
tag := f.Tag.Get("validate")   // "min=10" — a plain string, nothing more

There is no validate package in the runtime and no special syntax. The backtick literal lands in the type metadata verbatim, and StructTag.Get merely applies the ecosystem's key:"value" spacing convention to fish one key's string back out. Everything downstream — separator rules, constraint names, arguments — is yours. tagforge's grammar accepts spaces and commas between constraints (strings.Fields(strings.ReplaceAll(tag, ",", " "))), matching how the two big conventions in the wild diverge (encoding/json uses commas, validator uses commas with namespace dots — being liberal here costs nothing and spares users the trivia). The lesson generalizes: whenever you see a magical-looking annotation in Go — JSON keys, ORM columns, CLI env names — underneath is a plain string and someone's parser, exactly like the ~20-line one you wrote here.

Why precompilation wins — measuring the gap honestly

BenchmarkValidateReflect    ~3,300 ns/op    // reflect walk + tag parse, every call
BenchmarkValidateSchema       ~170 ns/op    // reflect walk only — plan reused
BenchmarkBuildSchema        ~6,600 ns/op    // the one-time price, priced separately

On a six-field config with a nested struct, the compiled path runs roughly 15–25× faster (numbers above from an M1 Pro; your machine will differ, the ratio's order of magnitude won't). Where does the time go in the slow path? buildStructPlan re-does everything structural per call: NumField iterations, Tag.Get string lookups, strings.Cut/Split allocation, ParseFloat conversions, applicability checks — work whose answer cannot change between calls because it depends only on the type. The compiled path reduces each call to index-chain hops and arithmetic. Crucially, BuildSchema has its own benchmark: at ~6,600 ns/op it costs about twenty schema-path validations, so the break-even is around twenty validations of this type — trivially reached by any server, pointless for a validate-once-at-startup config. That third number is what turns "precompile everything" dogma into an engineering decision you can actually compute.

Numeric edge cases — unsigned branches and precision honesty

switch fv.Kind() {
case reflect.Int, ..., reflect.Int64:
    return float64(fv.Int())     // signed branch
case reflect.Uint, ..., reflect.Uint64:
    return float64(fv.Uint())    // unsigned branch — separate getter!
default:
    return fv.Float()            // Float32/Float64
}

Merging every numeric kind into one float64 comparison simplifies the logic enormously — one <, one >, done — but it imports two edge cases you must own explicitly. First, the getters are disjoint APIs: Uint() on a signed value panics and vice versa, hence the branch. Second, float64 has 53 bits of mantissa, so a uint64 like 2^60 rounds on conversion and a boundary comparison at min=1152921504606846976 could judge the wrong side. tagforge documents this as an accepted edge — realistic config bounds live nowhere near 253, and the alternative (per-integer-kind comparison paths) would triple the code to guard a case the domain excludes. The transferable judgment call: converting types to simplify logic is fine when the precision loss is characterized, documented, and outside the domain's real range — and dishonest when any of those three is missing.

When NOT to reflect

The rule: reflection is for structure you can't know at compile time. If generics, interfaces, or plain code can express it, they will be faster, safer, and debuggable with ordinary tools.

Three honest boundaries for this stack. Hot paths: even the compiled schema pays reflect-based field access per call (~170 ns/op here); a serializer pushing millions of values per second wants codegen or manual marshaling, which is why encoding/json offers Marshaler hooks and protobuf generates code. Public APIs where generics suffice: a function that needs to compare or copy values of one shape should take [T any] constraints, not any plus reflection — generics moved a whole category of "flexible" APIs off reflection since Go 1.18. Cold paths: conversely, a config validated once at startup doesn't deserve even tagforge's schema abstraction — the naive path's few microseconds, paid once, are cheaper than the cognitive cost of another concept. Reflection is a tool with a real price tag; knowing when not to pay it is half the lesson.

05Testing Strategy

The constraint × type matrix, executed twice

err := Validate(tt.val)
if got := err != nil; got != tt.wantErr { ... }

sc, scErr := BuildSchema(reflect.TypeOf(tt.val))
err = sc.Validate(tt.val)
if got := err != nil; got != tt.wantErr { ... }  // same verdict, second engine

TestConstraints is a table of pass/fail cases spanning every constraint against every applicable type: required on int/string/float/bool, min/max edges on int (boundary values on the limit must pass), floats, uints, string lengths, slice caps, map sizes, the email shapes (missing @, doubled @, empty local, empty domain), oneof members and strangers. The structural trick: every row asserts its verdict twice — once through naive Validate, once through a freshly built Schema — so behavioral drift between the two execution modes is impossible to merge. Edge testing leans on boundaries specifically, because < vs <= bugs live exactly at the limit value.

Build-time rejection tests for inapplicable combinations

TestUnknownConstraint treats misconfiguration as a first-class specification. Unknown tokens must fail with the field and token named. Malformed arguments (min=banana) must fail. Inapplicable constraints (email on an int) must fail — in both engines. And the sharpest case: co-resident combos like min=1,email on an int, where one constraint is legal and its neighbor is not — the test demands rejection and that the error name the guilty family (email), proving the per-family independence of D3 rather than a blanket any-part-applies shortcut. TestStrictNumberParsing then sweeps the numeric grammar with a reject list (nan, inf, 0x1p3, 1_000, 1e309) and an accept list (+5, .5, 1.5e-3), building throwaway types via reflect.StructOf so each variant gets a fresh struct without ten named declarations.

Fuzzing the grammar — arbitrary input, defined failure

f.Fuzz(func(t *testing.T, tag string) {
    constraints, err := parseTag(tag)
    if err != nil && constraints != nil {
        t.Errorf("parseTag(%q): error must imply nil constraints", tag)
    }
})

FuzzTagGrammar throws arbitrary strings — NUL bytes, invalid UTF-8, absurd lengths, half-tokens — at the parser and asserts the only invariant that matters: it never panics, and an error always comes back with nil results (never a partial parse masquerading as success). The seeds encode known nasty shapes ("min=", "a=b=c", "ONEOF=x" for the case-sensitivity trap) so coverage is good even before fuzzing explores. This is the minimal viable fuzz target: pure function in, structured result out, one invariant — exactly the shape worth fuzzing first in any codebase.

Benchmark methodology — the honesty note

The note: both benchmarks validate the same value through the same execution engine (structPlan.run + checkLeaf). The only difference is whether tag parsing happens inside the timed loop. The measured delta therefore isolates exactly the thing the architecture claims to save — and nothing else.

This design choice is what makes the numbers meaningful. If the fast path used different check code, a skeptic could attribute the speedup to leaner validation logic rather than to precompilation. Here that objection is structurally impossible: run is shared, the bench config is shared, and BenchmarkBuildSchema separately prices the setup cost so readers can compute break-even for their own call frequency. When you publish a performance claim, engineer the experiment so the mechanism under test is the only variable — then the number argues for itself.

Behavioral contracts as executable cases

The remaining tests pin the semantic fine print that docs alone never seem to hold: TestAggregatesAllViolations requires ≥5 distinct FieldErrors in one pass with paths present (Server.Timeout) and recoverable via errors.As; TestNestedAndEmbeddedPaths asserts promotion positively (ID appears) and negatively (embBase.ID must not); TestPointerHandling walks all four nil/non-nil × required/optional corners; TestSchemaReuse interleaves failing, passing, and failing values through one schema to prove no state leaks, then feeds a mismatched type to prove the type check; TestUnexportedFieldsIgnored plants an impossible tag on an unexported field and demands silence. Each is one sentence of contract, executable.

06Go in the Wild

Where this stack runs in production

Struct-tag-driven reflection is one of the most-traveled roads in the Go ecosystem — you've been benefiting from it since your first json:"name":

  • encoding/json — the original proof that a raw-string tag convention could power the standard library. Its decoder walks exported fields via reflection, resolves json:"..." options, and caches the field scan per type — tagforge's BuildSchema trick, shipped in 2011.
  • Kubernetes CRD validation culture — k8s API types carry json:"replicas,omitempty" plus validation markers; controller-gen derives OpenAPI schemas from those tags, and the whole ecosystem's "declarative config with validated structure" posture rests on tag-driven tooling reading Go source.
  • gin / echo binding — every web framework's c.ShouldBind(&req) decodes JSON into your struct and then runs validator over the same tags' binding:"required,min=1" siblings — the exact decode-then-validate pipeline tagforge isolates down to just the validating half.
  • go-playground/validator internals — the library you'd use in production implements tagforge's two-phase idea at scale: parse tag strings into cached per-field plans keyed by type, then execute plans per call. You've now built its architecture in miniature.

Why reflection stuck despite its price

  1. Tags give declarative config a home next to the data it constrains. The field, its wire name, and its rules sit on one line — readable, diffable, greppable. Every alternative scatters the information: builder patterns move it away from fields, codegen moves it into artifacts, external schemas move it out of the language entirely. The tag convention won because locality wins.
  2. The cost problem has a known solution pattern. Nobody ships parse-tags-per-call validators at scale; the ecosystem converged on caching structural work per type (json's field cache, validator's plan cache, ORM column mappings). Once you recognize the pattern — reflect slowly once, execute quickly forever — you see it across serialization, dependency injection (wire's and fx's reflection versus codegen debate), and ORMs. tagforge made you implement the pattern, measure the gap, and compute the break-even yourself.
  3. Reflection cost in serialization stacks is real and measurable. It's why easyjson and protobuf generate marshalers, why json.Marshal dominates many service flame graphs, and why Go added encoding/json/v2 experiments exploring faster paths. Knowing from the inside what a reflective field access costs — and what fraction of it is avoidable planning — lets you read those flame graphs and immediately know which half of the work is structural overhead versus genuine data movement.

The through-line: reflect + a tag string + fail-closed parsing + a precompiled plan is not a teaching toy — it is the load-bearing architecture of Go's entire declarative-config ecosystem, exercised here in ~550 lines with a fuzz target keeping the parser honest and benchmarks keeping the performance story true.
