01Stack Evaluation

The stack: pprof + testing benchmarks + GODEBUG — all of it ships with Go

perfhunt's toolchain is whatever go test already knows how to do. Benchmarks come from testing.B, profiles from runtime/pprof driven by go tool pprof, allocator/GC introspection from GODEBUG=gctrace=1 and GODEBUG=allocfreetrace=0-era knobs like madvdontneed. No profiler daemon, no APM agent, no benchmark framework in go.mod — the entire performance curriculum is the standard library plus flags that have been in the toolchain for a decade. That is deliberate: profiling is a skill about reading your own program, and every third-party layer between you and the runtime is one more thing translating.

Rejected alternatives

  • Continuous profilers (Parca, Pyroscope, Datadog Continuous Profiler) — production-grade and genuinely valuable for fleet-wide always-on sampling. But they add agents, storage backends, and UIs to a lesson whose core loop is: run a benchmark, open a profile, find the hot frame. They also sample; here we want deterministic whole-program attribution of a microbenchmark. Once you can read a pprof flame graph by hand, the continuous tools are just that skill with retention.
  • Third-party benchmark frameworks (cerny/go-bench-style harnesses, stat-heavy comparison tools) — nice statistical dressing (deltas, confidence intervals, regression gates) around the same testing.B output. Worth adopting when you operate CI performance budgets; noise to a learner who first needs to understand what b.N even is. The stdlib harness plus benchstat's core idea (compare distributions, don't eyeball single runs) covers the methodology lesson.
  • Live services under load (wrk/vegeta against a running binary) — realistic, but couples the lesson to network noise, connection handling, and load-generation artifacts. perfhunt instead keeps every function pure and network-free so the benchmark isolates algorithmic cost (see D2).
  • eBPF-based system profilers — superb for cross-service and kernel-adjacent questions, wrong altitude entirely for "why does this function allocate 20k times per op".

What this stack uniquely teaches

  1. Profiles as falsifiable claims. Every anti-pattern → fix pair in this project carries a named piece of profile evidence — delete the per-call regexp.MustCompile and syntax.Parse frames vanish from the CPU flame graph; stop boxing floats into []any and runtime.convT64 disappears from the heap profile. You learn to predict a profile before taking it, which is what separates measurement from superstition.
  2. The three-number literacy of go test -bench. ns/op, B/op, allocs/op answer different questions, and they can disagree — this repo's own TopK pair has the slow twin allocating less than the fast one while still running ~2.5× slower. Learning to ask "which number am I optimizing and why" is portable to every language with a benchmarking culture.
  3. Allocation discipline as the lever the GC hands you. Go's collector makes garbage cheap but not free; reducing it moves latency tails and CPU in ways no GOGC tweak can. On one M1 Pro laptop the Aggregate rewrite runs ~38× faster and drops allocs/op from 20,026 to 19; Normalize drops ~22× (3,467 ns → 158 ns) and from 14 allocations to 1. Your machine will produce different absolute numbers — the ratios' orders of magnitude, and the profile frames explaining them, will match.

02Requirements

Derived directly from perfhunt_test.go (shared verbatim by both packages) and solution/bench_test.go — the executable specification.

Functional

  • R1 — Aggregate computes a full summary in one pass. Count, distinct-ID count (dedup via map, duplicates count once), sum/mean/min/max of Value, and a per-region Value total map. Empty input yields the zero Summary with a non-nil empty ByRegion and Mean/Min/Max left at zero — asserted exactly via reflect.DeepEqual in TestAggregateEmptyInput.
  • R2 — TopK returns the k most frequent items. Ordered by descending count, ties broken ascending by item name; k <= 0 yields an empty slice; k larger than the distinct count returns everything. Boundary cases (k=0, negative k, k exceeding distinct items) are pinned as explicit table rows.
  • R3 — Normalize canonicalizes tags ASCII-only. Lowercase ASCII letters, keep digits, collapse every other byte-run into a single -, trim leading/trailing dashes. Bytes ≥ 0x80 are separators — including runes that Unicode lowering would map into ASCII (the U+212A KELVIN SIGN lowers to 'k'; out of spec here).
  • R4 — Handler serves two GET routes. /stats returns the aggregate JSON; /tags?k=N returns the top-N tag array (default N=5). Non-GET gets 405 with Allow: GET; unknown paths get 404; responses carry Content-Type: application/json; overflow-sized or negative k falls back to the default rather than wrapping.
  • R5 — Slow twins exist and behave identically. AggregateSlow, TopKSlow, NormalizeSlow, HandlerSlow satisfy the same spec as their fast counterparts — pinned by shared parity tests, not by convention.
  • R6 — The dataset is fixed and deterministic. Seeded PRNG (source 42), 5000 records with ~50% duplicate IDs across ≥2 regions, 15000-tag stream including Normalize-exercising variants ("Beta ", "--GAMMA--") — built once behind sync.Once, identical on every run.

Non-functional

  • NF1 — Correctness tests are timing-free. No test asserts on wall-clock durations; speed differences live exclusively in benchmarks, which never gate correctness.
  • NF2 — Every optimization claim is measurable. Each anti-pattern pair has a benchmark sub-test plus a documented expected profile signature (see OPTIMIZATIONS.md's evidence column).
  • NF3 — Concurrency-clean. Handlers hold no shared mutable state beyond the sync.Once-guarded dataset; go test -race ./... passes.
  • NF4 — Documented hazards stay documented. The hand-rolled float serializer would emit invalid JSON for NaN/Inf — unreachable today because the dataset generates only finite seeded values, and recorded as such in the code where the hazard lives.

03Architecture Decisions

D1: The baseline is preserved in-tree, not in history

// slow.go is the preserved "intentionally slow baseline" commit for
// Project 13. ... every classic Go performance mistake lives here,
// side-by-side with the optimized rewrites in perfhunt.go, and
// bench_test.go measures them against each other.

Most tutorials show you the "before" as prose or a diff against a commit you can't easily check out. perfhunt commits the anti-patterns as living code: AggregateSlow boxes floats through []any under mutexes, concatenates fingerprints with +=, dedups IDs with O(n²) scans; NormalizeSlow compiles a fresh regexp every call. Keeping both versions compilable in the same package means the learner can flip between them, profile either on demand, and — crucially — the parity tests can hold them to the same contract. Slowness becomes a property you measure, not a story you're told. The cost is dead code shipped to students; the payoff is that every claim about why the fast path wins is one go test -bench away from verification.

D2: Pure, network-free functions — benchmarks need no server

req := httptest.NewRequest(http.MethodGet, "/stats", nil)
return func(b *testing.B) {
    for i := 0; i < b.N; i++ {
        w := httptest.NewRecorder()
        h(w, req)
        body, _ := io.ReadAll(w.Result().Body)
        _ = body
    }
}

Even the HTTP handler is benched without a socket: httptest.NewRequest + NewRecorder drive it in-process. This is the load-bearing decision for the whole project. Network benchmarks mix your algorithm's cost with TCP, scheduler, and load-generator noise — the signal drowns. Here every unit under test is a pure function of its arguments over a fixed dataset, so ns/op measures exactly one thing. The tradeoff is honest: real services also pay serialization, connection, and queueing costs, which is why the handler benchmark's delta looks modest next to Aggregate's own — a lesson in itself (see the OPTIMIZATIONS.md note that the endpoint is dominated by the aggregate it calls).

D3: Parity tests pin slow == fast before anything may be fast

if got, want := AggregateSlow(recs), Aggregate(recs); !reflect.DeepEqual(got, want) {
    t.Fatalf("slow %#v != fast %#v", got, want)
}

An intentionally slow twin is only pedagogically useful if it computes the same thing — otherwise the benchmark compares apples to oranges and the speedup is partly cheating. So the spec's first-class citizens are TestSlowMatchesFast*: identical seeded random records through both aggregates compared with DeepEqual, TopK across k ∈ {-1, 0, 1, 3, 100}, Normalize across ASCII and non-ASCII inputs, and k-parse acceptance matched case-by-case against strconv.Atoi. Bitwise-identical summation order keeps Total/Mean/ByRegion exactly equal, so the comparison needs no float tolerance. The rule generalizes: whenever you keep two implementations of one behavior, the equality test comes first — it's what lets every later number mean something.

D4: One pass beats three — the shape of the big win

sum.ByRegion[r.Region] += r.Value   // single probe
seen[r.ID] = struct{}{}            // map dedup, not O(n²) scan
// ...all of it inside ONE loop over records

AggregateSlow walks the records five-plus times (boxed append pass, unbox-sum pass, min pass, max pass, fingerprint/dedup/map pass, grand-total pass), boxes every Value into an interface, locks a mutex per record, and probes byRegion three times per record. The fast version does everything in one range loop with a presized seen map and index-based iteration (r := &records[i]) to avoid copying each struct. This single decision produces most of the headline win — on the reference laptop ~38× ns/op and a 20,026 → 19 allocs/op collapse, dominated by killing the quadratic string fingerprint and the boxing. The architectural takeaway isn't "one pass good": it's that pass structure and data representation dominate constant-factor tricks, and profiles tell you which regime you're in.

D5: Hand-assembled JSON at the edge — with the hazard written down

buf = strconv.AppendFloat(buf, s.Total, 'g', -1, 64)
...
// KNOWN LATENT HAZARD (review round 1, deferred by design): the
// hand-rolled float serialization emits bare NaN/+Inf/-Inf for non-finite
// values, which is INVALID JSON. This is unreachable today because
// dataset() generates only finite seeded values...

HandlerSlow builds a map[string]any and reflects over it with encoding/json; Handler appends bytes directly with strconv.AppendInt/AppendFloat/AppendQuote into one reusable buffer — halving allocs/op (70 → 36 on the reference run) and removing all reflection machinery from the request path. The honest part is the comment above: encoding/json rejects NaN/Inf with an error, while the hand-rolled serializer would happily emit invalid JSON. The dataset's finiteness is what makes the hazard latent, and the fix condition ("if the dataset ever becomes data-driven... a finite check MUST be added") is stated where a future editor will trip over it. Fast paths buy you control, and control obligates you to write down what the library used to guarantee for free.

04Concept Walkthroughs

CPU vs heap vs block profiles — three questions, three instruments

go test -bench=BenchmarkAggregate -cpuprofile cpu.out ./solution/
go tool pprof -top solution/cpu.out          // who burns the cycles?
go test -bench=BenchmarkAggregate -memprofile mem.out ./solution/
go tool pprof -top -sample_index=alloc_space solution/mem.out
                                             // who mints the garbage?

Each profile answers a different question, and using the wrong one wastes days. CPU profiles sample stacks while threads run: use them to find compute hot spots — in this repo they expose regexp.(*Regexp).Compile/syntax.Parse dominating NormalizeSlow, runtime.concatstrings/growslice dominating the fingerprint loop. Heap/alloc profiles attribute allocated bytes (or objects — switch -sample_index) to call sites: here they catch runtime.convT64, the frame where each boxed float64 escapes to the heap. Block and mutex profiles record time waiting on synchronization — mostly zeros in this project precisely because the mutexes guard unshared single-goroutine work, which is itself the finding: uncontended lock/unlock pairs still cost ~20ns each, times n records, buying nothing. The workflow is always: benchmark → profile → name the frame → predict the fix → re-profile to confirm the frame vanished.

Reading allocs/op — and knowing when it lies

BenchmarkTopK/Slow   543262 ns/op     1248 B/op      11 allocs/op
BenchmarkTopK/Fast   217146 ns/op     3832 B/op       7 allocs/op

The honesty note: perfhunt's own TopK pair has the slow twin allocating less than the fast one — its mutex-guarded counter map is never presized, so it grows lazily into fewer, larger chunks. Yet it runs ~2.5× slower. ns/op and allocs/op tell different stories.

allocs/op counts allocations per timed operation — a proxy for GC pressure and allocator work, not for speed. It's most diagnostic in extremes: AggregateSlow's 20,026 allocs/op means roughly four allocations per record, each paying allocator bookkeeping and eventually collector work; the fast path's 19 is effectively constant regardless of input size. Normalize is the cleanest teaching case — 14 allocs → 1: compiling a regexp allocates its program and tables on every call, while the byte-scanner allocates exactly one result buffer. The transferable habit: when allocs/op scales with n, hunt for per-element allocations hiding in loops (boxing, string concat, per-call compilation); when it doesn't, stop optimizing allocations and go look at the CPU profile instead.

Benchmark methodology — b.N, stability, and machine dependence

func BenchmarkAggregate(b *testing.B) {
    b.Run("Fast", func(b *testing.B) {
        b.ReportAllocs()
        for i := 0; i < b.N; i++ {
            _ = Aggregate(benchRecords)
        }
    })
}

The harness picks b.N adaptively: it runs the function, estimates throughput, and re-runs with larger N until the measurement stabilizes — your job is only to write a loop that does exactly one operation per iteration and nothing else inside the timer. Setup lives outside the loop (here, benchRecords/benchTags come from package-level dataset() built long before any timer starts). Sub-benchmarks share one input so Slow/Fast deltas isolate implementation, and results should be compared with benchstat over multiple runs, never eyeballed from a single line. And the caveat that governs every number in this doc: benchmarks are machine-bound. The reference figures below come from one Apple M1 Pro at -benchtime=10x — order-of-magnitude evidence. Your laptop will disagree on absolutes and almost certainly on precise ratios; what should reproduce everywhere is the sign of every delta and the profile frames explaining it.

GC tuning knobs — after the allocations, not instead of them

GODEBUG=gctrace=1 go test -bench=. -run=NONE ./solution/
// gc 3 @0.052s 1%: 0.09+0.8+0.03 ms clock, ... 12->6 MB

GOGC=200 GOMEMLIMIT=512MiB ./service   // fewer, bigger cycles

Go's collector is concurrent, tri-color, and non-compacting; you tune it with three levers. GOGC sets heap growth between cycles (default 100 = collect when the heap doubles): raising it trades memory for fewer collections. GOMEMLIMIT (Go 1.19+) caps total runtime memory, soft-clamping the collector before the OS does it harder — the right tool when GOGC alone risks unbounded growth. GODEBUG=gctrace=1 prints each cycle's pause, CPU fraction, and heap size so you can see cadence change. The ordering lesson is the whole point: run gctrace on the slow baseline and you'll watch the collector thrash through thousands of tiny allocations; apply the Aggregate fix first and the same trace shows collection nearly vanishing — then GOGC/GOMEMLIMIT become meaningful refinements for tail latency and memory ceilings. Tuning the collector before fixing allocations optimizes the cost of producing garbage rather than the garbage itself.

When NOT to reach for these tools

The rule: profile before optimizing. Most code is fast enough; the expensive lines are rarely the ones you'd guess, and intuition-driven optimization reliably beautifies cold paths.

Three boundaries worth naming. Cold code: startup-time work running once doesn't deserve a single allocation saved — the complexity cost outweighs nanoseconds nobody experiences. Unprofiled suspicions: if you can't name the frame you expect to disappear, take the profile first; half of perfhunt's anti-patterns (the dead fingerprint string, the pointless mutexes) are things a reader might "optimize" forever without noticing they weren't even the bottleneck. Wrong altitude: microbenchmarks answer per-function questions; capacity planning, p99-under-load, and multi-service questions need load tests and production observability — a 38× local speedup says nothing about whether the endpoint was ever slow for users.

05Testing Strategy

Correctness is timing-free; timing lives only in benchmarks

if !approx(body.Total, want.Total) || !approx(body.Mean, want.Mean) ||
   !approx(body.Min, want.Min) || !approx(body.Max, want.Max) { ... }
// No test anywhere asserts on elapsed time — benchmarks measure,
// tests verify.

Every test in the suite asserts on values, statuses, and shapes — never on durations. This separation is what makes a performance-teaching repo CI-safe: timing assertions flake on loaded machines and teach the wrong lesson when green. The functional suite covers known-record aggregation (duplicate ID counted once), empty-input zero-Summary semantics via DeepEqual, TopK ordering/tie-breaking/limits including k=0 and negative k, the full Normalize table, and handler routing (404, 405 with method checks, default and explicit ?k=). Performance claims get their own instrument — benchmarks — which are run deliberately, not gated.

Parity twins: the executable equivalence proof

for _, s := range []string{
    "\u212A", "A\u212AB", "caf\u00E9", "\u00C5rge",
} {
    if got, want := NormalizeSlow(s), Normalize(s); got != want {
        t.Fatalf("Normalize(%q): slow %q != fast %q", s, got, want)
    }
}

TestSlowMatchesFast* is the suite's backbone: identical seeded inputs through both implementations, DeepEqual verdicts, bitwise-equal floats because summation order matches. These tests earned their keep the hard way during adversarial review, which found two real holes in the original parity claim — and both now ship as regression cases:

  • The Normalize unicode-parity hole (fleet finding F1). strings.ToLower is Unicode-aware: the U+212A KELVIN SIGN lowers to ASCII k, so the original NormalizeSlow("\u212A") returned "k" while the byte-scanning Normalize returned "" (non-ASCII bytes are separators, trimmed). The fix made the contract explicit — bytes ≥ 0x80 are separators — and had the slow twin blank out non-ASCII bytes before lowering (blankOutNonASCII), so the twins agree byte-for-byte. The Kelvin sign, café, and Årge cases pin it permanently.
  • The k-overflow guard (fleet finding F2). The slow handler's hand-rolled atoiSimple accumulated digits without a range check, so /tags?k=99999999999999999999 silently wrapped to a large positive int and returned all rows, while the fast path's strconv.Atoi errors and keeps the default k=5. atoiSimple now mirrors Atoi's cutoff/limit arithmetic, and TestSlowMatchesFastParseK sweeps overflow, MinInt-edge, sign-only, and garbage strings, asserting acceptance agreement with strconv.Atoi plus exact value agreement where accepted. TestHandlerTagsKOverflowDefault pins the end-to-end behavior: huge k means default k=5, never a wrap.

Race detector and shared-state hygiene

var (
    datasetOnce sync.Once
    datasetRecs []Record
    datasetTags []string
)

go test -race ./solution/... passes because the handlers own no mutable shared state: every request works on freshly allocated buffers, and the one shared artifact — the embedded corpus — is built exactly once behind sync.Once with deterministic seed 42. The race check matters more than usual here because the codebase deliberately contains mutexes (in the slow twins); verifying they're unnecessary overhead rather than necessary protection requires proving the data really is goroutine-local, and the detector is that proof.

The NaN hazard: documented, tested-around, honestly deferred

Adversarial review confirmed that feeding NaN Values into Aggregate propagates Mean=NaN (and all-NaN input leaves Min=+Inf, Max=-Inf), which the hand-rolled serializer would emit as bare NaN/+Inf — invalid JSON. It is unreachable today: dataset() generates only finite seeded values (rng.Intn(100_00)/100), and the handlers accept no caller data. Rather than paper over it, the hazard lives as a comment at the exact AppendFloat call sites stating the trigger condition ("if the dataset ever becomes data-driven or Aggregate accepts caller input here, a finite check MUST be added"). The testing lesson: when a defect can't be exercised without changing the architecture, the next-best control is a machine-readable warning at the vulnerable line — plus the fixed-dataset determinism tests (TestDatasetShape) that keep the current safety argument true.

What the benchmarks assert (carefully)

Benchmarks assert nothing about correctness — by design — but their structure encodes claims: the Slow/Fast sub-benchmarks share one dataset and one request object, b.ReportAllocs() makes the B/op and allocs/op columns mandatory, setup sits outside the timed loop, and -benchtime=10x in the reference run trades stability for speed while the doc labels the output "order-of-magnitude evidence." The remaining gap — that a reader might mistake one noisy run for a law — is closed by the methodology walkthrough's instruction to compare multiple runs with benchstat on their own hardware.

06Go in the Wild

Where this stack runs in production

pprof, allocation discipline, and GC tuning aren't academic exercises — they're routine maintenance on some of the largest Go fleets on earth:

  • Uber's Go GC tuning — Uber engineers wrote up tuning GOGC and later championed GOMEMLIMIT (which grew out of their proposal work) to tame container memory ceilings: raising GOGC cut GC CPU on CPU-bound services, and GOMEMLIMIT made that safe near hard memory limits. Exactly the knobs this project exercises — after, not before, fixing allocations.
  • Cloudflare's pprof culture — Cloudflare has published multiple deep-dives using Go pprof on production edges, from diagnosing a memory leak via heap profiles in Rust-adjacent Workers' Go components to profiling their DNS infrastructure; their posts are essentially this project's workflow (benchmark → profile → name the frame → fix → re-profile) at fleet scale, with net/http/pprof exposed carefully behind access controls.
  • Dgraph / Badger allocation work — the Dgraph database and its embeddable KV store Badger were built allocation-first: value-log design, arena-style buffers, and repeated public releases citing reduced allocs/op and GC pauses. Badger's README-era benchmarks read like this project's table — ns/op, B/op, allocs/op — because its maintainers treated those columns as release criteria.
  • The Go runtime itself — every escape-analysis improvement, sync.Pool addition, and GC cycle in the standard library was validated with the same testing.B harness and benchstat comparisons used here; the compiler's own benchmarks live in -tree under test/bench and the x/bench repository.

Why the stdlib profiling stack stuck despite flashier alternatives

  1. Zero-friction ubiquity beats best-of-breed tooling you have to deploy. Any Go process — yours, a vendor's, a customer's — exposes a CPU profile with one import or one flag. When Slack, an issue tracker, and a curl command can pull a flame graph from prod, profiling happens; when it requires standing up a continuous-profiler backend, profiling happens next quarter. The ecosystem's default posture is that every Go engineer can read pprof output, so every team invests in keeping that skill current.
  2. The allocation story is unusually legible. Go's GC made raw allocation cheaper than in stop-the-world collectors, which shifted performance work toward a simple, teachable currency: bytes and objects per operation. That's why B/op and allocs/op became community lingua franca, why escape analysis entered ordinary engineering vocabulary, and why projects from Docker to Kubernetes publish allocation-reduction PRs as routine hygiene.
  3. GC tunability arrived when hardware did. GOGC dates to the earliest releases; GOMEMLIMIT landed in Go 1.19 specifically because cloud containers made hard memory ceilings universal. Uber's production experience fed the design discussion — a straight line from fleet-scale pain to a flag you can try on this repo's benchmarks tonight.

The through-line: a preserved slow twin, a benchmark harness, and three profile types are not a teaching simplification of production performance work — they are production performance work, minus the pager. Learn the loop here on functions you can fully hold in your head, and the day you're staring at a real service's flame graph, the only new thing will be the stakes.
