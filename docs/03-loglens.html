01Stack Evaluation

The stack: pure standard library, one more time

loglens leans on four load-bearing stdlib packages — regexp, bufio, errors, and strconv — plus fmt, io, sort, and strings in supporting roles. No log-parsing library, no line-oriented DSL, no go.sum. Where project 01 proved you can build a real tool with nothing imported and project 02 proved persistence needs no database, project 03 proves something about cost models: the same library call can be free or catastrophic depending on where you put it.

PackageRole in loglensLesson it carries
regexpMatch each line against one compiled pattern (lineRe)Compile once at package level vs per-call costs — a 100×-style performance cliff hiding behind identical-looking code
bufioScanner streams lines without ever loading whole filesBuffer limits are real: the 64KB default silently fails long lines unless you raise it
errorsSentinels (ErrMalformed, ErrSkip) and the wrapping chain through *LineErrorError values as data: wrap with %w, interrogate with errors.Is/errors.As
strconvTurn raw status/bytes captures into numbersParse failures become first-class errors you can wrap, not silent zeros

Rejected alternatives

  • Full log-parsing libraries — Go's ecosystem has mature options for structured and semi-structured logs. But they would hide the exact lesson this project exists to teach: what a regex match actually costs and why compilation is a one-time investment. When the parser is a black box, "compile once at package level" never comes up, and neither does the discipline of distinguishing skipped lines from malformed ones.
  • strings.Fields-only splitting — splitting on whitespace gets you tokens fast, but it can't validate structure. A quoted request field contains spaces; a timestamp lives inside brackets; there's no way to tell "five tokens that happen to be a log line" from "five random tokens." The regex is the contract: either a line has the shape of an access-log entry or it doesn't, and that decision is testable.
  • Reading the whole file into memory — os.ReadFile plus a split on newlines is three lines shorter and works fine until the file doesn't fit. Streaming via bufio.Scanner is barely more code and scales to inputs many times larger than RAM — the difference between a learning exercise and something you'd point at production logs.

What this stack uniquely teaches

  1. One-time regex compilation vs per-call costs. Moving regexp.MustCompile out of the loop and to package level is the single most memorable performance lesson in early Go — visible in benchmarks, explainable in one sentence, applicable forever.
  2. Scanner streaming with buffer limits. bufio.Scanner looks effortless until a real-world 800KB URL line trips its default cap and lines start disappearing silently. Raising the limit explicitly teaches that convenience APIs have configuration surfaces worth reading.
  3. Error wrapping chains. Sentinel + custom error type + %w + errors.As composes into errors that carry structured context (which line? which field? underlying cause?) while remaining programmatically checkable at every layer.

02Requirements

Derived directly from loglens_test.go at the project root — the executable specification. If your implementation passes these tests, it satisfies the requirements.

Functional

  • R1 — Valid lines parse and aggregate. A well-formed common-format line increments Total, adds 1 to ByStatus[200] (or whatever the status is), and counts the path in ByPath. Lines with a byte count and lines with - in place of bytes both work; CRLF endings are tolerated.
  • R2 — Non-matching lines are skipped, not fatal. A line that doesn't match the format ("this is not a log line") increments Skipped and analysis continues. Analyze returns nil error for input containing only skippable lines.
  • R3 — Mixed streams produce partial stats plus one precise error. For a stream of valid, skipped, and malformed lines, Analyze returns non-nil stats covering everything parsed before the failure and an error satisfying errors.As(err, &lineErr) whose LineError.Line is the 1-based number of the malformed line (line 4 in the mixed fixture).
  • R4 — Malformed fields surface ErrMalformed through the chain. A line with the right shape but a non-numeric status yields an error satisfying errors.Is(err, ErrMalformed) — reachable only if LineError.Unwrap and fmt.Errorf("%w") wiring are intact.
  • R5 — Large volumes aggregate exactly. 100,000 generated valid lines yield Total = 100000, Skipped = 0, and by-status counts summing back to exactly N — no lost or double-counted lines under sustained streaming.
  • R6 — Very long lines still parse. A single ~800KB line (a pathological URL) parses successfully — which is only possible if the Scanner buffer was raised above the 64KB default.
  • R7 — TopPaths sorts deterministically and clamps. Sorted by count descending, ties broken by path ascending; requesting more than exists clamps to the distinct-path count; n ≤ 0 returns an empty slice.
  • R8 — CompilePattern exposes the shared pattern. Returns a usable *regexp.Regexp that matches a valid log line — and never recompiles.

Non-functional

  • NF1 — Constant memory. Analyze must never load the whole input into memory; aggregation happens line-by-line as bytes stream through the Scanner.
  • NF2 — Errors wrap, don't erase. Every failure travels as a wrapped chain: strconv's own error nested inside ErrMalformed nested inside *LineError — checkable at any layer via errors.Is/As.
  • NF3 — Deterministic output ordering. Any sorted report derived from Stats (like TopPaths) must be fully deterministic despite Go's randomized map iteration — hence explicit tie-breaking rules.

03Architecture Decisions

D1: One package-level compiled pattern

var lineRe = regexp.MustCompile(`^(\S+) \S+ (\S+) \[([^\]]*)\] "([A-Z]+) (\S+) [^"]*" (\S+) (\S+)$`)

This single line carries the project's central lesson. Regex compilation — building the state machine that powers matching — is expensive relative to matching itself. Compile inside Analyze and you pay that cost once per call; compile at package level and you pay it once per process. On a million-line log the difference dominates runtime entirely. MustCompile (panic-on-bad-pattern) is correct here precisely because the pattern is a compile-time constant: if it's wrong, the program is broken and should fail loudly at startup, not return errors at runtime. Note also what stays out of the regex: status and bytes are captured as raw strings ((\S+), (\S+)) rather than \d+, so unparseable values reach strconv and get reported as ErrMalformed instead of causing a silent non-match that masquerades as "skipped."

D2: Raise the Scanner buffer — or lose lines silently

sc := bufio.NewScanner(r)
sc.Buffer(make([]byte, 64*1024), maxLineSize) // maxLineSize = 1024 * 1024

The Scanner's default limit is 64KB per token. Exceed it and sc.Scan() returns false with bufio.ErrTooLong — which, fatally, looks exactly like clean end-of-input if you don't check sc.Err(). Real access logs contain URLs far past 64KB (query-string attacks, deep paths, base64 blobs). The fix is one explicit Buffer call raising the ceiling to 1024 * 1024 bytes — an effective maximum of 1,048,575 bytes per line, since the Scanner reserves one byte of buffer headroom and rejects a token of exactly 1,048,576 with ErrTooLong — plus the final if err := sc.Err(); err != nil check so I/O trouble becomes a returned error instead of truncated results. This pitfall is why the test suite includes an ~800KB line: it proves the limit was raised and proves the implementation didn't take the "silently stop early" exit.

D3: Partial-stats-on-error contract

status, err := strconv.Atoi(m[6])
if err != nil {
    return stats, &LineError{Line: lineNum, Err: fmt.Errorf("%w: status %q: %w", ErrMalformed, m[6], err)}
}

When a malformed line aborts analysis, the function returns both the stats gathered so far and the error — never nil alongside an error. Callers (see the CLI's run) can print the partial report and treat the LineError as a warning, because "everything before line 4 is valid" is genuinely useful output. The abort policy is deliberately asymmetric:

  • Skipped lines never abort. A non-matching line just increments stats.Skipped and the loop continues — logs routinely contain noise (blank lines, banners, startup messages) and treating each one as fatal would make the tool useless on real files.
  • The first malformed line aborts. A line that matches the log-entry shape but has unparseable fields signals corrupted data, and continuing past corruption risks reporting aggregates nobody should trust. So Analyze stops at the first such line, reporting exactly that one line number in the LineError.

Blank lines fall on the skip side: they don't match the format, so they increment Skipped like any other noise.

D4: Skipped vs malformed — two different failures

The distinction is the heart of the design. Skipped means "this line isn't a log entry at all" — expected, counted, harmless. Malformed means "this line claims to be a log entry but its fields are garbage" — unexpected, specific, abort-worthy. Collapsing them into one bucket destroys information: you'd either crash on ordinary noise or silently ignore corruption. The two sentinels encode the policy in the type system: ErrSkip names the benign case and ErrMalformed the severe one.

Honesty note: ErrSkip is currently declared but never produced — skipped lines simply increment a counter without constructing an error. Treat it as reserved API surface for learner extension exercises: e.g., collect every skipped line's number into a []*LineError{..., Err: ErrSkip} and report them after the scan, or add a strict mode where skips abort too. The sentinel exists so those extensions don't need to invent their own vocabulary.

D5: Library core, thin command shell

projects/03-loglens/
├── loglens.go               # package loglens — stubs you implement
├── loglens_test.go          # the executable spec
└── solution/
    ├── solution.go          # package solution — lineRe, Analyze, Stats
    └── cmd/loglens/main.go  # flag parsing + report printing

All parsing and aggregation lives in the library; main only handles flags (-n top-N paths, -status filter), iterates input files (or stdin), and formats output. Its one piece of judgment is interpreting the partial-stats contract: a *LineError prints as a warning and the run still exits 0 with its partial report; anything else (unreadable file, scanner failure) exits 1. Same library-plus-cmd layout as projects 01 and 02 — by now it should feel like the default shape of a Go tool.

04Concept Walkthroughs

regexp.MustCompile vs Compile — panic-once philosophy

The idea: Compile returns (*Regexp, error); MustCompile panics on a bad pattern. Choose based on where the pattern comes from: constants want MustCompile, user input wants Compile.

var lineRe = regexp.MustCompile(`^(\S+) \S+ (\S+) \[([^\]]*)\] ...`)  // package level, once

m := lineRe.FindStringSubmatch(line)  // cheap: reuse the compiled machine

A literal pattern in source code can't vary at runtime, so an error branch for it is dead weight — if the author typo'd the regex, every execution is equally doomed, and failing immediately at process start (via panic during package initialization) is strictly better than failing lazily mid-request. That's the entire rationale of the Must* convention, which recurs across the stdlib (template.Must, sql.Open wrappers). The flip side is placement: even a correctly compiled regex recompiles every time MustCompile executes, so the variable must live outside whatever function runs per-line. Benchmark this yourself — move the compile inside Analyze and watch the throughput collapse. It is the most vivid constant-vs-recompute lesson available in pure stdlib Go.

bufio.Scanner mechanics — tokenization over a Reader

sc := bufio.NewScanner(r)
for sc.Scan() {          // true per line, false at EOF or error
    line := sc.Text()      // string copy of the token, newline stripped
}
if err := sc.Err(); err != nil { /* handle */ }

A Scanner pulls bytes from any io.Reader in buffered chunks, splits them into tokens (lines, by default), and hands you one token per Scan(). Three details matter here. First, memory: at any moment only one buffer-sized chunk of input is alive — the whole file never exists in your process, which is what makes TB-scale inputs tractable. Second, Text() copies the token into a string; Bytes() returns a slice into the internal buffer that's invalidated by the next Scan() — use Text when you keep the value past the loop iteration (as Analyze does when storing map keys). Third, the loop's false exit is ambiguous between "done" and "gave up": only Err() distinguishes clean EOF from ErrTooLong or an I/O failure. Skipping that check is how implementations silently drop data — the exact bug D2 exists to prevent.

errors.As with a custom type — the Unwrap chain

type LineError struct {
    Line int   // 1-based
    Err  error // ErrSkip or a wrapped parse failure
}

func (e *LineError) Error() string { return fmt.Sprintf("loglens: line %d: %v", e.Line, e.Err) }
func (e *LineError) Unwrap() error  { return e.Err }

Sentinels answer "is this that kind of failure?" (errors.Is). Custom error types answer "what are the structured details?" (errors.As). Here the detail is the offending line number, which no string comparison should ever have to recover. The chain built for a bad status on line 4 looks like this, unwrapped layer by layer:

*LineError{Line: 4}                       // errors.As target — carries the line number
└── Unwrap() →
    fmt.Errorf-wrapped: "malformed line: status \"abc\": ..."   // %w → ErrMalformed
    ├── errors.Is target: ErrMalformed                          // the domain sentinel
    └── innermost %w → strconv.NumError                         // the raw parse failure

The magic double-%w line does the splicing:

fmt.Errorf("%w: status %q: %w", ErrMalformed, m[6], err)

Since Go 1.20, fmt.Errorf accepts multiple %w verbs, producing an error with several wrapped parents — so one formatted message simultaneously links to ErrMalformed (for errors.Is checks) and to the original strconv.NumError (for callers who want field-level forensics). The tests pin both ends: TestAnalyzeMixedStreaming asserts errors.As(err, &le) with le.Line == 4; TestSentinelErrors asserts errors.Is(err, ErrMalformed) survives the full chain. Break Unwrap — return nil, forget the method — and both tests fail, proving the chain is architecture, not decoration.

strconv errors wrapped inside LineError

status, err := strconv.Atoi(m[6])          // m[6] is the raw captured string
if err != nil {
    return stats, &LineError{Line: lineNum, Err: fmt.Errorf("%w: status %q: %w", ErrMalformed, m[6], err)}
}

strconv.Atoi never panics or coerces — a failed parse returns a typed *strconv.NumError carrying the function name, the original string, and the syntax/range cause. Discarding it (or flattening it into a message) throws away exactly the context a debugger wants. Wrapping it preserves the whole story: which line (LineError), which field and value (status %q), why it failed (the NumError itself). Also notice the deliberate asymmetry in the bytes field: "-" is checked before parsing, because the format defines it as "no bytes recorded," not as a parse failure. Format-level conventions belong in explicit branches; numeric validation belongs to strconv — each concern handled by the layer built for it.

Map aggregation patterns — counting without order illusions

stats.ByStatus[status]++
stats.ByPath[m[5]]++

The zero-value trick makes aggregation one line: indexing a nil-or-empty map returns zero, so m[k]++ works without any "does the key exist" ceremony. Both maps are pre-initialized in the constructor anyway so callers always receive usable, non-nil maps even on empty input. The trap arrives at read time: ranging over these maps yields keys in randomized order, so any ordered view must sort explicitly. That's TopPaths' job — flatten to a slice, sort.Slice with count-desc then path-asc tie-break, clamp to n. The tie-break isn't cosmetic: without it, equal counts would shuffle between runs, making output non-reproducible and any golden-file testing impossible. Determinism is a feature you opt into with a comparator.

05Testing Strategy

Mixed fixtures prove the streaming contract

TestAnalyzeMixedStreaming builds one input containing a valid line, a garbage line, another valid line, a malformed line, and a blank line — four kinds of reality in five lines of text. Then it asserts everything at once:

var le *LineError
if !errors.As(err, &le) {
    t.Fatalf("error %T (%v) is not a *LineError", err, err)
}
if le.Line != 4 {
    t.Errorf("LineError.Line = %d, want 4", le.Line)
}
if stats.Total != 2 || stats.Skipped != 1 { /* partial stats required */ }

The assertions interlock: stats must be non-nil alongside the error (the partial-stats contract), totals must reflect exactly the two lines parsed before the failure, the blank line must count as skipped, and the reported line number must be the first malformed one — not the last, not a count. A table-driven sibling (TestAnalyzeSingleLine) covers the individual cases: minimal entries, entries with bytes, CRLF tolerance, and pure-skip input returning nil error.

The 800KB line: buffer limits are testable behavior

longPath := "/" + strings.Repeat("a", 800_000) // proves the raised Scanner limit
line := fmt.Sprintf("1.2.3.4 - - [t] \"GET %s HTTP/1.1\" 200 -\n", longPath)

Most tests exercise logic; this one exercises configuration. An implementation using the Scanner's default 64KB buffer fails here not with a wrong answer but with a missing line — or worse, with ErrTooLong mistaken for EOF. Building a single ~800KB input makes the raised limit observable: pass and you know Buffer() was called and sc.Err() handled. Meanwhile TestAnalyzeLargeInput generates 100,000 lines across five status codes and asserts the by-status counts sum back to exactly N — a conservation law catching off-by-one and dropped-token bugs that small inputs hide.

Sentinel assertions via errors.Is / errors.As

if !errors.Is(err, ErrMalformed) {
    t.Errorf("errors.Is(err, ErrMalformed) = false through LineError chain")
}

Like taskline before it, the suite demands wrapping discipline, not just error presence: the assertion passes only if %w wiring connects the returned error to the sentinel through however many layers intervene. TestSentinelErrors goes further, asserting le.Unwrap() != nil — the chain must continue past the LineError to whatever caused it. These are tests of mechanism: you cannot satisfy them by formatting a convincing message string, only by building the actual linked structure.

TopPaths: ordering, tie-breaks, and edge cases

want := []PathCount{
    {"/c", 5},
    {"/a", 3}, // tie with /b broken by path asc
    {"/b", 3},
}

The fixture engineers a deliberate tie (/a and /b both at count 3) and pins the deterministic resolution: alphabetical. Without the tie-break rule, map iteration randomness could swap them run-to-run and flake the test — which is precisely the bug the test exists to prevent ever shipping. Edge cases ride along: n=100 against four paths clamps to four, n=0 returns an empty (non-nil-behavior-safe) slice. Sorting logic with tie-breaks is exactly the kind of code where "looks right" and "is right" diverge, so the spec encodes the difference.

06Go in the Wild

Where this stack runs in production

Streaming, regex-shaped, line-oriented processing is the daily bread of observability infrastructure — much of it written in Go:

  • Prometheus — scrapes and stores time series from endpoints whose exposition formats are line-oriented text; the parser family it grew up with (expfmt) processes exactly the kind of streamed text this project does, just with more rigor and more years of optimization.
  • Grafana Loki — a log-aggregation system written largely in Go whose whole premise is "treat logs as streams of labeled lines." Its ingestion pipeline faces the same problems as loglens — arbitrary formats, malformed input, enormous volume — at industrial scale.
  • Vector-alternatives in Go — the log-shipping ecosystem (Fluent Bit plugins, Telegraf tail inputs, homegrown collectors) is full of Go daemons doing bufio-style tailing plus format detection plus aggregation, deployed on millions of hosts.
  • nginx/Apache combined log format — the format loglens parses is the de-facto standard for web servers worldwide; every analytics pipeline, WAF, and bot detector that starts from raw access logs begins with a parser shaped like lineRe.

Why streaming matters at TB scale

  1. Memory is the constraint, CPU is negotiable. A busy service produces gigabytes of access logs per day; a fleet produces terabytes. Loading even one day's input into RAM is a non-starter, so production parsers are all variations of bufio.Scanner: read a bounded chunk, extract a record, aggregate, discard, repeat. The aggregation maps grow with distinct keys, not total volume — which is why the by-status/by-path shape scales when raw line storage wouldn't.
  2. Silent truncation is the classic outage. The Scanner's default-limit pitfall isn't academic: log pipelines everywhere have quietly dropped long lines — losing evidence during incident response — because someone forgot a Buffer() call or an Err() check. The habit of asking "what does this API do at its limits, and does failure look like success?" is learned once here and applied to every reader-based API afterward.
  3. The compile-once principle compounds. Prometheus compiles metric-name matchers once; Loki compiles label matchers once; every hot-path regex in production Go lives at package scope or in a constructor. Learning the cost model on a toy analyzer means recognizing — and benchmarking — the anti-pattern instantly when you meet it in a code review.

The through-line: one compiled regex, one buffered scanner, and a disciplined error chain are not teaching simplifications. They're the skeleton of every serious log pipeline in the Go ecosystem — exercised here in under 200 lines, against a format that has outlived several of its critics.
