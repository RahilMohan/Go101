01Stack Evaluation

The stack: three stdlib packages and a strong opinion about floats

moneylib is built on math/bits, strconv, and errors, with fmt, math, and strings in supporting roles. No decimal library, no arbitrary precision, no go.sum. That minimalism is the point: money is just an integer count of minor units plus a label, and every hard problem in this project — overflow, rounding, parsing, formatting — is an integer problem. Where project 03 taught cost models of library calls, project 04 teaches something more dangerous: how numbers silently lie when you pick the wrong representation.

Rejected alternatives

  • float64 money — the classic bug. Representing $1.10 as a float and adding it up is the canonical demonstration that binary floating point cannot represent most decimal fractions: 0.1 + 0.2 = 0.30000000000000004. In a toy this is funny; in a billing system it is an audit finding. The entire library exists as the counter-example: every value here is an int64, and no conversion to or from floating point exists anywhere in the API surface.
  • shopspring/decimal — the de-facto ecosystem answer for decimal arithmetic. It would work perfectly, which is precisely why it's rejected: it hides the integer-precision lesson. When the library absorbs rounding and scale, you never learn why minor-unit arithmetic is the industry default or what a 128-bit product has to do with multiplying cents. Use it at work after you can build its reasoning yourself.
  • big.Rat / big.Int — arbitrary-precision rationals make overflow impossible, which sounds like a feature until you notice what it costs: allocations on every operation, pointer-heavy values, and no reason to ever think about int64 limits. Real payment cores use fixed-width integers because they are fast, comparable, and cache-friendly — and therefore must be checked. Overkill here means the lesson disappears.

What this stack uniquely teaches

  1. Minor-unit integer arithmetic. Storing cents instead of dollars converts "decimal precision" into plain integer math — exact, order-independent, and free. This is how ISO 4217 actually models currency, and once internalized it permanently changes how you read financial code.
  2. Checked overflow via bits.Mul64. Fixed-width integers overflow; the professional response is not avoidance but detection. Computing the full 128-bit product and comparing against the representable range turns silent wraparound — the worst kind of bug — into an ordinary returned error.
  3. Fuzz-driven API confidence. Two fuzz targets encode the library's deepest promises (round-trip fidelity, inverse operations) as machine-checkable properties, then let millions of random inputs attack them. Table tests pin known edges; fuzzing searches for the ones you didn't think of.

02Requirements

Derived directly from money_test.go at the project root — the executable specification. If your implementation passes these tests, it satisfies the requirements.

Functional

  • R1 — Construction and accessors. NewAmount(minor, c) builds an Amount; MinorUnits() returns the signed count and Currency() the denomination — fields stay encapsulated (TestAccessors).
  • R2 — Add/Sub within one currency. Both return new Amounts with correct results across positive, negative, and zero operands, and across all four currencies including JPY (exponent 0) and BHD (exponent 3).
  • R3 — Currency mismatch is an error, not a sum. Adding or subtracting USD and EUR (or USD and JPY) yields an error satisfying errors.Is(err, ErrCurrencyMismatch) and a zero Amount — never a number that pretends two currencies are comparable.
  • R4 — Mul detects overflow. MaxInt64 × 1 and MinInt64 × 1 succeed; (MaxInt64/2+1) × 2, MaxInt64 × 10, MinInt64 × 2, and the notorious MinInt64 × -1 all return errors rather than wrapped garbage (TestMulOverflow).
  • R5 — Alloc splits exactly, remainder to the earliest parts. For every tested currency, totals including negatives, and n = 1..7: parts sum back to the total exactly, each early part is base+step and each later part base, and Alloc(5, 2) gives [3, 2] while Alloc(-5, 2) gives [-3, -2].
  • R6 — Alloc rejects non-positive n. n = 0, −1, −7 each return an error.
  • R7 — String is canonical per exponent. 123456 USD renders "1234.56 USD"; -1250 EUR renders "-12.50 EUR"; 123456 JPY renders "123456 JPY"; fractional digits are zero-padded to full exponent width; NewAmount(math.MinInt64, USD).String() equals "-92233720368547758.08 USD" exactly (TestStringFormats, TestMinInt64String).
  • R8 — ParseAmount accepts canonical forms and round-trips. "1234.56 USD", "-12.00 EUR", "500 JPY", "1.001 BHD" parse to expected minor counts and re-render byte-identically.
  • R9 — ParseAmount rejects sixteen classes of malformed input. Wrong fractional digit count either way ("1.234 USD", "1.2 USD"), any decimals on JPY ("1.5 JPY"), unknown codes, lowercase codes, bare signs, leading dots, trailing dots, embedded spaces, non-digits, out-of-range magnitudes — each produces an error, never a best-effort Amount.

Non-functional

  • NF1 — No floats, anywhere. Parsing, arithmetic, and rendering are exact end to end; the string representation round-trips without information loss.
  • NF2 — Errors wrap with context. The sentinel travels inside fmt.Errorf("%w") chains that name the offending operation and operands, so errors.Is checks survive while messages stay debuggable.
  • NF3 — Properties hold under fuzzing. Any input that parses must re-parse identically through String; any successful same-currency Add must be inverted exactly by Sub. Both properties are encoded as fuzz targets.

03Architecture Decisions

D1: Immutable Amount value semantics

// Amount is an immutable value: a count of minor units plus the currency it
// is denominated in.
type Amount struct {
    minor    int64
    currency Currency
}

Every operation is a method on the value receiver returning a brand-new Amount: a.Add(b) never mutates a. This mirrors how money behaves in the real world — paying someone changes your balance by producing a new balance, not by reaching into their wallet. Value semantics also make Amounts safe to share across goroutines with zero synchronization, trivially comparable with == (the fuzz targets lean on this), and usable as map keys. The zero Amount is documented as not a valid monetary value: build amounts only through NewAmount or ParseAmount, and error paths return it deliberately so callers can detect "no result" without nil-pointer ceremony.

D2: Unexported fields + accessors — invariants need a chokepoint

a := NewAmount(123456, USD)
a.MinorUnits()   // 123456 — read access, sign included
a.Currency()    // Currency{"USD", 2} — read access

Why hide minor behind MinorUnits() when the field could simply be exported? Because exported fields are a promise that any value of the struct is valid, forever. If minor were public, nothing stops a caller from constructing an Amount that bypasses every check this library performs — and a future change (say, normalizing on construction, or caching a derived field) becomes a breaking API change. Unexported fields create a single chokepoint: the package controls every Amount that exists, so its invariants ("currency is always one of the registered ones", "operations never silently mix currencies") are enforceable, not aspirational. Accessors preserve readability for legitimate reads. This is the standard-library idiom throughout — time.Time, strings.Builder — and TestAccessors pins it as behavior, not style.

D3: Currency as a comparable struct, not a string

type Currency struct {
    Code     string // ISO 4217 alphabetic code, e.g. "USD"
    Exponent int    // minor units per major unit is 10^Exponent
}

var (
    USD = Currency{"USD", 2}
    JPY = Currency{"JPY", 0}
    BHD = Currency{"BHD", 3}
)

A string-only design would push exponent knowledge into every call site — every function asking "how many decimal places does "USD" have?" — inviting divergence between modules that disagree about their own currency. Making Currency a struct bundles the code with its exponent, and because structs containing only comparable fields are themselves comparable, the mismatch guard is a single ==:

if a.currency != b.currency {
    return Amount{}, fmt.Errorf("money: %w: %s + %s", ErrCurrencyMismatch, a.currency.Code, b.currency.Code)
}

The named variables (USD, EUR, JPY, BHD) act as the registry; byCode indexes them for parsing. Note what the comparison costs: nothing. No string normalization, no lookup — structural equality in one instruction, which is why the fuzz target can afford to check mismatch behavior on every iteration.

D4: Alloc — the remainder-to-earliest convention

base := a.minor / int64(n)
rem := a.minor % int64(n)
step := int64(1)
if rem < 0 {
    step = -1
}
parts := make([]Amount, n)
for i := range parts {
    m := base
    if int64(i) < int64(abs64(rem)) {
        m += step
    }
    parts[i] = Amount{minor: m, currency: a.currency}
}

Splitting 5 cents two ways has no exact answer; the library's contract is that the leftover goes to the earliest parts: [3, 2]. The convention matters more than the choice — any deterministic rule keeps the core invariant (sum(parts) == total) true, but "earliest gets the remainder" matches how payment splits are typically reconciled and makes the output predictable enough to pin in tests. The step flip handles the subtle Go detail that -5 % 2 == -1: remainders carry the dividend's sign, so negative amounts distribute [-3, -2] symmetrically instead of drifting toward zero. TestAllocExactSum brute-forces 4 currencies × 6 totals × 7 values of n and asserts the invariant on every single part — a property test wearing a unit-test uniform.

D5: Errors as API — sentinel inside a wrapping chain

var ErrCurrencyMismatch = errors.New("money: currency mismatch")
...
return Amount{}, fmt.Errorf("money: %w: %s + %s", ErrCurrencyMismatch, a.currency.Code, b.currency.Code)

Callers need to ask one question programmatically — "is this a currency problem?" — and read a different answer humanly — "USD + EUR failed." The sentinel answers the first via errors.Is; the %w-wrapped context answers the second with the actual codes and operation. Returning the zero Amount alongside the error completes the contract: failure never yields a plausible-looking number.

04Concept Walkthroughs

The MinInt64 trap — absolute value needs uint64 space

A real bug found in review: writing abs(x) as -x for negative x looks airtight — and detonates on exactly one input. -MinInt64 wraps around to MinInt64 itself, because in two's complement the negative range is one wider than the positive range.

// abs64 returns |x| computed in uint64 space so MinInt64 is representable.
func abs64(x int64) uint64 {
    if x < 0 {
        return uint64(-(x + 1)) + 1
    }
    return uint64(x)
}

Two's complement gives int64 the range [−263, 263−1]. The magnitude of MinInt64 is 263 — a number that fits in uint64 but not in any int64, including itself. So negation cannot be the last step; it must never happen in signed space at all. The trick above adds 1 first (bringing MinInt64 down to a negatable MaxInt64), negates, casts to unsigned, then adds the 1 back. Every consumer of magnitudes — Mul, String's digit extraction, Alloc's remainder comparison — routes through this one function. The test suite pins the consequence: NewAmount(math.MinInt64, USD).String() must equal "-92233720368547758.08 USD", a literal computed by hand because any implementation that flirts with signed negation will produce the wrong digits here. This is the kind of bug fuzzing finds eventually and a good edge-case table finds immediately.

Overflow detection with bits.Mul64 — borrowing the missing half of the product

neg := (a.minor < 0) != (n < 0)
hi, lo := bits.Mul64(uint64(abs64(a.minor)), uint64(abs64(n)))
// Magnitude 2^63 is representable only as MinInt64, so legal only for a negative result.
maxMag := uint64(math.MaxInt64)
if neg {
    maxMag = 1 << 63
}
if hi != 0 || lo > maxMag {
    return Amount{}, fmt.Errorf("money: multiply overflows int64: %d * %d", a.minor, n)
}

Multiplying two 64-bit numbers truthfully produces up to 128 bits; int64 * operator simply discards the top half and hands you a wrong-but-well-typed answer. Go's bits.Mul64 refuses to discard anything: it returns the full product split into high and low 64-bit words. Detection then reduces to arithmetic: if the high word is nonzero the product exceeds 64 bits outright; otherwise compare the low word against the largest representable magnitude. That asymmetry — MaxInt64 for positive results, 263 for negative ones — is the two's complement boundary again, and it produces the pleasingly precise test row {"min times minus one overflows", MinInt64, -1, ..., wantErr: true} sitting right next to {"min times plus one fits"}. Sign handling stays outside the multiplication entirely: take absolute values (via abs64, naturally), multiply magnitudes, reapply the XOR of signs afterward. The alternative — pre-dividing inputs to "check ahead of time" — is fiddlier, slower, and easy to get subtly wrong; the hardware already did the wide multiply for you.

Table-driven test anatomy — one loop, many verdicts

tests := []struct {
    name    string
    a       Amount
    b       Amount
    wantSum int64
    wantSub int64
    wantErr error // non-nil means both ops must fail with errors.Is
}{
    {"same currency add/sub", NewAmount(150, USD), NewAmount(25, USD), 175, 125, nil},
    {"cross currency USD/EUR", NewAmount(100, USD), NewAmount(100, EUR), 0, 0, ErrCurrencyMismatch},
    ...
}
for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) { ... })
}

The anonymous struct is the whole pattern: cases are data, the runner is code written once. Three details separate competent table tests from great ones. First, t.Run(tt.name, ...) gives each case its own subtest, so a failure names the case (--- FAIL: TestAddSubTable/cross_currency_USD/EUR) instead of pointing at a line inside a giant loop. Second, error expectations live in the table too (wantErr), and the runner branches: expected-error cases assert with errors.Is and verify the zero-Amount contract; success cases assert both the numeric result and the surviving currency. Third, one table exercises two functions (Add and Sub) whose cases mirror each other — because the operations' relationship is itself part of the specification. When a reviewer asks "what happens with JPY? with BHD?" the answer is visible as rows, not buried in procedural assertions.

Fuzzing in Go — properties attacked at scale

func FuzzParseAmount(f *testing.F) {
    f.Add("1234.56 USD")          // seed corpus: known-good
    f.Add("-12.00 EUR")
    f.Add("")                     // seed corpus: known-bad
    f.Add("1.234 USD")
    f.Fuzz(func(t *testing.T, s string) {
        a, err := ParseAmount(s)
        if err != nil {
            t.Skip()              // unparseable input isn't a bug — skip
        }
        b, err := ParseAmount(a.String())
        if err != nil || a != b {  // the property: round-trip is identity
            t.Fatalf("round trip changed value: %v -> %v via %q", a, b, a.String())
        }
    })
}

Run go test -fuzz=FuzzParseAmount and Go generates millions of random strings, feeding each through the property function; any crash is minimized and saved into testdata/ as a permanent regression case. Without -fuzz, the seeds still run as ordinary unit tests in CI — which is why the corpus mixes valid formats, rejection cases, and empty strings. The intellectual content is the property, not the machinery: we don't assert what any particular input should produce, we assert a universal law — ParseAmount(String(a)) == a for every parseable string. t.Skip encodes the domain knowledge that most random strings are legitimately unparseable; only inputs that claim validity can violate the law. A sibling target, FuzzAdd, attacks arithmetic: for matching currencies, (a+b)−b == a whenever both operations succeed, and mismatched currencies must yield the sentinel plus a zero Amount on every single iteration. Together they cover the two ways a money library can quietly betray you: losing information in text, and losing it in arithmetic.

Doc comments as the public API contract

$ go doc -all ./solution | head -20
package money // import "example.com/moneylib/solution"

// Package money provides currency-safe monetary arithmetic using minor
// units, teaching integer-vs-float precision, table-driven tests, and
// fuzzing.
...

In Go, doc comments aren't supplementary prose — they're rendered by go doc and pkg.go.dev into the interface users actually read, so imprecise wording becomes imprecise behavior in the reader's mind. This library treats them as specifications. The package comment states the no-floats guarantee. Amount's comment warns that the zero value is not a valid monetary amount. String's comment promises canonical output with zero-padded fraction digits so that String round-trips through ParseAmount — turning the fuzz property into published contract. ParseAmount's comment enumerates the rejection rules, including the exact-digit requirement. Writing these comments first forces the design questions early ("what does Alloc do with −5?"), and the tests then exist to keep the documentation honest. Contract in prose, proof in code, confidence in the fuzzer.

05Testing Strategy

Property-based thinking: invariants, not examples

The suite pairs every example-style table with a property that must hold for all inputs. Two carry the library's core promises:

// Property 1 — String ∘ Parse is identity (FuzzParseAmount)
b, err := ParseAmount(a.String())
if err != nil || a != b { t.Fatalf(...) }

// Property 2 — Sub inverts Add (FuzzAdd)
sum, err := a.Add(b)
if err != nil { t.Skip() }
back, _ := sum.Sub(b)
if back != a { t.Fatalf("(a+b)-b = %v, want %v", back, a) }

Notice what the properties do not do: they don't hard-code expected outputs. They assert relationships that must hold universally, which means every random input the fuzzer invents becomes a fresh test case with a known correct answer derived from the library itself. The skips are load-bearing: "this input is out of domain" is a different outcome from "this input broke the invariant," and conflating them either floods you with false failures or buries real ones.

Pinned edges: the inputs designed to hurt

// Expected literal computed by hand:
// |MinInt64| = 9223372036854775808 minor = 92233720368547758 major + .08
got := NewAmount(math.MinInt64, USD).String()
want := "-92233720368547758.08 USD"

Some inputs deserve a pinned, hand-computed expectation even alongside a property, because they sit exactly where implementations traditionally die: MinInt64 for sign handling and overflow, MaxInt64×1 vs (MaxInt64/2+1)×2 for the overflow boundary, MinInt64×−1 (overflow!) next to MinInt64×1 (fits). Exponent variety is pinned the same way — the format tables include JPY rows ("123456 JPY", no dot ever) beside BHD rows ("0.001 BHD", three digits), so an implementation hardwired for two decimals fails visibly rather than incidentally. Hand-computing the expected literal is deliberate: it prevents the test from merely echoing whatever the implementation does.

Exactly-exponent digits: why "1.5 USD" must fail

if len(fracPart) != c.Exponent {
    return Amount{}, fmt.Errorf(
        "money: ParseAmount(%q): %s needs exactly %d fractional digits, got %q",
        s, c.Code, c.Exponent, numStr)
}

The strictest rule in the parser looks like hostility and is actually the thing that makes the round-trip property possible. If "1.5 USD" were accepted, what minor count should it produce — 15? 150? Either choice invents a scaling the user didn't state, and then String renders "0.15 USD" or "1.50 USD" — a different string than the input, and the round-trip property dies. By requiring the fraction width to equal the currency exponent exactly, the grammar becomes canonical: one string per Amount, one Amount per string, bijection guaranteed by construction rather than by normalization heuristics. The rejection table enforces it from both directions ("1.234 USD" too many, "1.2 USD" too few, "1.5 JPY" absurd) and even pins the case analysis in error messages. Strictness at the boundary bought simplicity everywhere else.

Brute-force invariants: Alloc's exhaustive grid

for _, c := range []Currency{USD, EUR, JPY, BHD} {
    for _, total := range []int64{7, 100, 12345, -5, -12345, 1} {
        for n := 1; n <= 7; n++ {
            // assert: len(parts) == n, each part == base (+step if earliest),
            //         and sum(parts) == total
        }
    }
}

Alloc gets the suite's densest treatment because its failure modes are quiet: a one-cent drift in a split reconciles fine today and corrupts ledgers over months. Rather than trusting a handful of examples, the test enumerates the full small grid — 168 combinations — and checks the strongest available invariant on each: the parts reassemble into the original amount exactly, and the remainder lands on the earliest indices per the documented convention, with negative totals exercising the signed-remainder branch. Between the exhaustive grid, the hand-pinned extremes, and two running fuzzers, the suite covers the classic testing trinity: examples teach the reader, edges catch known cliffs, properties patrol everything in between.

06Go in the Wild

Where this stack runs in production

Money-as-integers in Go isn't a pedagogical pose — it's how some of the largest financial systems on the internet are built:

  • Stripe — the payments platform's backend heritage is famously Go-heavy, dating to before Go was fashionable; its APIs quote every amount as an integer in the smallest currency unit (the amount parameter is cents for USD), which is exactly the minor field of this project exposed to the public internet.
  • Coinbase — a major crypto exchange built substantially on Go, where a rounding error is measured in basis points of other people's assets; integer minor-unit accounting and explicit overflow discipline are survival traits, not preferences.
  • Monzo — the UK digital bank runs its core banking on a large Go microservices estate, processing millions of ledger entries daily; the "immutable value + exact integer + explicit error" shape of this library is recognizably the shape of its transaction primitives.
  • ISO 4217 everywhere — card networks, PSPs, and open-banking APIs (including PSD2's) model currency as code-plus-minor-units; the Currency{Code, Exponent} struct in this project is a faithful miniature of how the standard itself distinguishes USD (2), JPY (0), and BHD (3).

Why minor units won

  1. Binary floats can't hold decimal money. Every currency amounts system that started on double has accumulated reconciliation horror stories — cent-level drift appearing from nowhere because 0.1 has no exact binary representation. Integer minor units make every value exact and every comparison meaningful; that's why Stripe's API, settlement files, and virtually every core ledger speak integers.
  2. Fixed-width forces honesty about limits. Arbitrary-precision types are wonderful until a hot path allocates one per operation. Production payment cores prefer int64 precisely because it can overflow — forcing the explicit checks this project practices with bits.Mul64. The constraint is the feature: bounded values, cache-friendly comparisons, and bugs that surface as errors instead of slow memory pressure.
  3. When decimals are truly required, the ecosystem has an answer. FX rates, interest accrual, and tax computations genuinely need fractional intermediate values — that's the territory of shopspring/decimal, the standard Go fallback, which stores coefficients as big integers with an explicit exponent (notice: still no binary floats). Knowing when to reach for it — and that even it is integer math underneath — is the payoff of building the simple case by hand.

The through-line: an int64 of cents, a struct pairing code with exponent, and errors that refuse to fabricate sums are not teaching simplifications. They're the skeleton of real payment infrastructure — exercised here in ~250 lines, with a fuzzer standing guard over every promise the docs make.
