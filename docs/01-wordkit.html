01Stack Evaluation

The stack: pure standard library

wordkit uses six stdlib packages — os, bufio, flag, io, fmt, and unicode. No third-party dependencies, no go get, no module proxy round-trips. This is deliberate: project 01 is your first Go program, and every import you don't recognize is friction between you and the language.

osos.Stdin, os.Open, os.Exit, stderrFiles are just Readers; exit codes communicate failure to shells

Rejected alternatives

  • cobra / urfave-cli — excellent production flag frameworks, but they hide exactly what this lesson teaches: how argument parsing works, how flag.Args() yields positional arguments, how a CLI composes flags with plain functions. You'll appreciate cobra more after you've written without it. Later projects reintroduce richer tooling where it earns its complexity.
  • Any counting library / regex approach — counting words via regexp would work but obscures the byte-level streaming loop that is the point of this project, and pays regex compilation cost per run.
  • Loading the whole input into memory — trivially simpler, but fails the core constraint: constant memory regardless of input size (see Architecture).

What this stack uniquely teaches

  1. The io.Reader abstraction. One function — Analyze(r io.Reader) — handles stdin, files, network streams, and test strings alike. Nothing else in beginner Go demonstrates dependency inversion this concretely.
  2. Error as value. No exceptions exist in Go. Errors come back as a second return value, are compared against sentinels like io.EOF, and are wrapped with context. wordkit's read loop is a textbook exercise in all three.
  3. Program anatomy from scratch. A complete main package importing its own library package shows the two-package shape nearly every real Go program has: reusable logic in a library, thin wiring in cmd/.

02Requirements

These are derived directly from wordkit_test.go — the executable specification. If your implementation passes these tests, it satisfies the requirements.

Functional

  • R1 — Count four statistics over an io.Reader: lines (\n characters), words (whitespace-separated fields per unicode.IsSpace), bytes, and UTF-8 characters.
  • R2 — Final unterminated line counts. A final non-empty line without a trailing newline still counts as a line: input "last" yields Lines: 1, and the multi-line fixture "one two\tthree\nfour five\n\nlast" yields Lines: 4. This is deliberately wc-like but not identical: unlike wc -l (which counts only \n bytes), any content — including trailing whitespace — after the last newline adds one line. Compare outputs against real wc -l with that difference in mind.
  • R3 — Unicode-aware character count. "héllo wörld ✓\n" is 18 bytes but 14 chars: multi-byte runes count once each.
  • R4 — Invalid UTF-8 degrades gracefully. Each invalid byte counts as one char ("h\xffi\n": Bytes 4, Chars 4) rather than erroring out.
  • R5 — Mixed whitespace splits words. Tabs and multiple spaces separate words; consecutive whitespace produces no empty words.
  • R6 — Empty input → zero stats, nil error.
  • R7 — Format matches wc. Four space-padded %8d columns in order Lines, Words, Bytes, Chars.

Non-functional

  • NF1 — Constant memory. The 10,000-line large-input test feeds an in-memory strings.Reader, so it proves correctness at volume — not the constant-memory property itself. That property holds (verified empirically: piping 100 MB through the CLI keeps RSS roughly flat), but it is a design property of the streaming loop, not something this test demonstrates.
  • NF2 — Errors propagate checkably, stats zeroed. A failing reader must surface via errors.Is, and Analyze must return zeroed stats together with the error — never partial counts from before the failure.
  • NF3 — CLI behavior: no args reads stdin; one or more file paths are each analyzed; -l/-w/-c/-m select columns; no flags prints all four; a missing file prints to stderr and exits non-zero while other files still process.

03Architecture Decisions

D1: Stats as a flat struct of int64

type Stats struct {
    Lines int64 // count of '\n' characters; a final line without '\n' still counts
    Words int64 // whitespace-separated fields (unicode.IsSpace)
    Bytes int64 // total bytes read
    Chars int64 // UTF-8 rune count; invalid bytes count as one char each
}

A single value struct means Analyze returns one comparable result — the tests can do got != want. int64 (not int) makes the counts stable on 32-bit platforms and mirrors how wc-scale tools think about sizes. Structs of zero-value fields need no constructor: var s Stats starts at all zeros, which is exactly the empty-input answer.

D2: Streaming, not load-all

Analyze wraps the input in a bufio.Reader and walks it one rune at a time. Memory use is the buffer size (~4 KB), whether the input is 10 bytes or 10 GB. The alternative — io.ReadAll then iterate — would double peak memory (the full slice plus whatever produced it) and break NF1. The cost is a slightly more intricate loop with explicit state (inWord, pendingLine) instead of convenient string methods like strings.Fields.

D3: Rune-by-rune decoding

ReadRune decodes one UTF-8 rune per call and returns its byte width, which gives us both counters in a single pass:

c, size, err := br.ReadRune()
if err != nil {
    if err == io.EOF { break }
    return Stats{}, fmt.Errorf("wordkit: read: %w", err)
}

This is why invalid UTF-8 "just works": Go's decoder substitutes utf8.RuneError (U+FFFD) with size 1 per bad byte, so each corrupt byte still advances both counters by one — requirement R4 falls out of the strategy rather than being special-cased. On a real read error, the accumulated partial stats are discarded: Analyze returns zeroed stats alongside the wrapped error, so callers can't mistake a truncated read for a complete one.

D4: Two-state line tracking

pendingLine records whether any non-newline content appeared since the last '\n'. At EOF, if it's set, one final line is added (R2). Note this deviates from strict wc -l semantics, which count only newline bytes: an unterminated final line — even one made solely of trailing spaces — still counts here. The single boolean replaces buffering the last line.

D5: Library + cmd split

projects/01-wordkit/
├── go.mod                  # module definition — no proxy round-trip needed
├── wordkit.go              # package wordkit — stubs you implement
├── wordkit_test.go         # the executable spec
├── cmd/wordkit/main.go     # stub CLI wiring you flesh out
└── solution/
    ├── solution.go         # package solution — reference Analyze/Format
    └── cmd/wordkit/main.go # reference thin CLI wiring

All logic lives in the library package; main only parses flags, opens files, and formats output. This makes the counting logic testable without spawning processes, and models the layout real Go CLIs use (docker/cli, gh — see sidebar).

D6: Per-file isolation in main

The CLI loops over file arguments, and a failed open or analyze sets failed = true but keeps processing remaining files — then exits 1 at the end. Files are closed immediately after analysis via f.Close(), even on the error path, so a many-file invocation never leaks descriptors.

CLI contract caveats, honestly stated

  • No flag bundling. Go's flag package treats -lw as an undefined flag: it prints usage and exits with status 2 (parse errors exit 2; file errors exit 1). Unix tools like wc -lw bundle short flags; wordkit's stdlib contract does not.
  • Filenames pass through verbatim. A file's name is printed as-is next to its stats — including any ANSI escape sequences or newlines it contains. This is byte-identical to GNU wc's behavior, so it is a property of the wc-style output contract, not a bug — but see the callout below before piping this tool's output anywhere.

Security note — untrusted filenames corrupt line-oriented consumers. Because operand names are emitted raw into stdout and stderr, a filename like $'bad\n12345678 98765432 fake.txt' can splice a forged stats row into the output of wordkit *.txt | parser, and escape sequences render in terminals that display it. If you harden a wc-like tool for hostile input, quote names (%q) or emit a structured format (JSON) — accepting the deviation from wc-compatible output.

04Concept Walkthroughs

io.Reader / io.Writer — why they matter

The idea: io.Reader is a single-method interface: Read(p []byte) (n int, err error). Anything that can produce bytes implements it — files, stdin, network connections, compressed streams, in-memory strings. Code written against the interface works with all of them, forever.

wordkit's entire engine is one signature:

func Analyze(r io.Reader) (Stats, error)

Look at how differently the callers feed it:

// from stdin (main.go):
solution.Analyze(os.Stdin)

// from a file (main.go) — open errors are reported, not ignored:
f, err := os.Open(name)
if err != nil {
    fmt.Fprintln(os.Stderr, "wordkit:", err)
    failed = true
    continue // other files still process (D6)
}
solution.Analyze(f)

// from a test fixture (wordkit_test.go):
Analyze(strings.NewReader("hello\n"))

An OS file handle, the process's standard input, and a garbage-collected test string — same function, zero adaptation. In exception-flavored languages you'd often see three overloads or a base-class hierarchy here. In Go, it's one interface and one implementation. This pattern — accept interfaces, return concrete types — is the backbone of Go's standard library design, and you will reuse it in every subsequent project.

io.Writer is the mirror image (Write(p []byte)) — stdout, files, HTTP response bodies, buffers all implement it. wordkit's CLI writes results with fmt.Println, which targets os.Stdout, itself a Writer under the hood.

Error values vs exceptions

Go has no try/catch. Fallible operations return an error interface value as their last result; nil means success. Three idioms appear in this project:

  1. Sentinel errors. io.EOF is a predefined package-level error. The read loop compares against it to detect end-of-input — control flow expressed as an ordinary value comparison: 
    if err == io.EOF {
    break
}
    Caveat: direct == comparison is only safe because bufio.Reader returns io.EOF unwrapped. In general — and anywhere wrapping (%w) might be involved — prefer the chain-aware form errors.Is(err, io.EOF), which is what production code should reach for first.
  2. Wrapping with context. Rather than returning a bare upstream error, Analyze adds provenance: 
    return Stats{}, fmt.Errorf("wordkit: read: %w", err)
    The %w verb wraps the original error inside the new one, preserving the chain. Note the zero-value Stats{} — on failure the partial counts accumulated so far are discarded, exactly as NF2 requires (see D3 above).
  3. Checking chains with errors.Is. Callers never parse message strings; they interrogate the chain: 
    if !errors.Is(err, sentinel) { ... }
    errors.Is unwraps through every %w layer until it finds a match. This is precisely what TestAnalyzePropagatesReaderError asserts.

Compare with exceptions: errors here are values in your function signatures — visible in the type system, impossible to forget to declare. The trade-off is verbosity (if err != nil everywhere); Go's bet is that explicitness beats surprise. Notice also the error-path discipline in main: diagnostics go to stderr (Fprintln(os.Stderr, ...)), data to stdout, and the exit code tells the shell something failed.

bufio — buffered streaming

Raw Read calls have no size guarantee — a reader may hand back 1 byte per call. Reading rune-by-rune straight from a file would mean one syscall per byte. bufio.NewReader inserts a ~4 KB buffer between you and the source: big reads underneath, tiny logical reads on top. br.ReadRune() decodes from memory almost always, dipping into the underlying reader only when the buffer empties. Memory stays constant (NF1) while throughput approaches bulk reads.

UTF-8 runes vs bytes

In Go, a byte is a raw octet (uint8); a rune is a Unicode code point (int32). They differ the moment text leaves ASCII: é is one char but two bytes, ✓ is one char but three. Hence two separate counters — and hence the test case "héllo wörld ✓\n" expecting Bytes 18, Chars 14. The subtlety worth internalizing: when ReadRune hits a byte that isn't valid UTF-8, it returns utf8.RuneError with size 1 instead of failing. Corrupt input degrades to byte-faithful counting rather than aborting — a small decision with big consequences for tools that must chew arbitrary data.

The flag package

lines := flag.Bool("l", false, "print the newline count")
words := flag.Bool("w", false, "print the word count")
flag.Parse()
args := flag.Args() // positional args after flags

Each flag.Bool registers a boolean flag and returns a pointer to its value — your first encounter with Go pointers-as-out-parameters. After flag.Parse(), *lines holds whether -l was passed, and flag.Args() contains leftover positional arguments (file paths). The convention <name> -l -w file.txt comes free; so does -h/--help with auto-generated usage text. When you later meet cobra in bigger tools, understand that it builds on exactly these primitives.

05Testing Strategy

Table-driven tests

The heart of TestAnalyze is a slice of anonymous structs — name, input, expected stats, expected error — iterated with t.Run:

for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        got, err := Analyze(strings.NewReader(tt.input))
        if (err != nil) != tt.wantErr {
            t.Fatalf("Analyze() error = %v, wantErr %v", err, tt.wantErr)
        }
        if got != tt.want {
            t.Errorf("Analyze() = %+v, want %+v", got, tt.want)
        }
    })
}

Why this shape dominates Go testing:

  • Adding a case is a five-line literal, not a new function.
  • t.Run(tt.name, ...) gives each case its own named subtest — failures report TestAnalyze/unicode_chars_differ_from_bytes, pinpointing the case instantly.
  • t.Fatalf (abort this subtest) for precondition failures vs t.Errorf (keep going) for assertion failures — a distinction that matters once cases grow checks.
  • Because Stats is comparable, got != want compares all four fields at once. No reflection, no deep-equal needed.

Error-path injection with a fake reader

How do you test "what happens when the disk fails mid-read"? You don't simulate a disk — you exploit R1's abstraction and supply a reader whose Read always fails:

// errReader always fails, exercising Analyze's error propagation.
type errReader struct{ err error }

func (r errReader) Read([]byte) (int, error) { return 0, r.err }

Four lines, no mocks framework. Because Analyze accepts any io.Reader, the test injects failure at the exact boundary where real I/O would fail. The assertions check two things: the sentinel survives wrapping (errors.Is) and no misleading partial stats leak out — a full-struct compare against the zero value (stats != (Stats{})), not a spot-check of one field. A companion test (TestAnalyzeMidReadErrorZeroesPartialStats) feeds some data first, then fails, pinning that partial counts are zeroed even mid-stream. These tests are unpassable until your implementation wraps errors correctly — they're the executable form of lesson "error as value."

Scale as a test case

TestAnalyzeLargeInput builds a ~340 KB synthetic input (10,000 formatted lines) and asserts exact totals. Its purpose isn't performance — it pins down that streaming state machine logic doesn't drift at volume: off-by-one bugs in inWord/pendingLine show up as mismatches in the 50,000-word expectation long before they'd bite in production.

Format as its own unit

TestFormat verifies the %8d column contract independently of analysis, using asymmetric values (12 / 3456 / 789012 / 34) that expose padding mistakes. Small, boring, essential: formatting regressions are user-visible and trivially cheap to catch.

Known limitation: %8d pads but never truncates, so any count of nine or more digits fuses adjacent columns with zero separating spaces (Format of nine-digit values yields one long digit run). GNU wc shares this exact property, so wordkit matches its contract — just don't assume the output is safely machine-parsable at ≥10⁹ counts.

06Go in the Wild

Where this stack runs in production

wordkit's stack — pure stdlib CLI reading stdin/files, printing to stdout, exiting non-zero on failure — is the exact skeleton of virtually every widely deployed command-line tool written in Go:

  • Docker CLI (docker) — container management; built on cobra, which itself builds on the flag mechanics you just used.
  • GitHub CLI (gh) — GitHub's official terminal client, pure Go, shipped as a static binary for every platform.
  • Terraform & OpenTofu — infrastructure-as-code engines driving clouds worldwide; a Go binary you download and run.
  • kubectl — the Kubernetes client, arguably the most-run Go binary on Earth.
  • hugo, ghz, hey, gitleaks — the long tail: static site generator, load tester, secret scanner. All stdlib-first CLIs.

Why Go dominates the CLI space

  1. Single static binary. go build emits one self-contained executable — no runtime install, no interpreter, no dependency resolution at deploy time. Distribution is a download URL.
  2. Fast startup. Compiled to native code with no VM warm-up, Go CLIs start in milliseconds — critical for tools invoked thousands of times in scripts and CI pipelines.
  3. Trivial cross-compilation. GOOS=linux GOARCH=arm64 go build targets another OS/architecture from your laptop. Release matrices that take C toolchains days take Go minutes.
  4. Batteries-included stdlib. As wordkit demonstrates, flag parsing, buffered I/O, and unicode handling ship with the compiler. Many production CLIs stay zero-dependency end to end.

The through-line: the skills in this project — accept io.Reader, propagate errors as values, keep the binary thin — aren't academic exercises. They're the load-bearing habits of tools running on millions of machines right now.
