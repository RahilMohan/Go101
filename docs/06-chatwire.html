01Stack Evaluation

The stack: raw TCP from the net package

chatwire is built directly on Go's raw socket layer — net for Listener/Conn, bufio for line framing, context for shutdown deadlines, and plain channels for every piece of coordination. No HTTP, no websocket library, no RPC framework, no go.sum. After project 05's net/http, dropping down to bare TCP feels like removing training wheels: you see exactly where connections come from, who owns each one, and what a “message” actually is before any protocol exists.

Rejected alternatives

  • Websockets — the natural choice for “real-time chat,” and precisely wrong here. Websockets need a protocol library to handle the upgrade dance, framing, ping/pong, and close semantics. That machinery would obscure the very thing this project teaches: what a socket connection is, who owns it, and how goroutines coordinate around it. Websocket framing is also binary and buffered, so the newline protocol lesson evaporates.
  • HTTP long-polling / SSE — would keep you inside net/http's comfortable abstractions, hiding accept loops, conn ownership, and bidirectional flow. Chat over request/response also forces awkward fakes of what TCP gives you natively: a persistent, ordered, bidirectional byte stream.
  • gRPC — a fine production technology and entirely the wrong lesson. It would replace hand-rolled fan-out with generated stubs and streaming semantics defined by someone else. The project's point is to build the server-shaped concurrency patterns that gRPC servers use internally, not to consume them.
  • sync.RWMutex around shared maps — the reflexive choice for “concurrent map access,” rejected in favor of a single hub goroutine that owns both maps outright. See D1: ownership removes the lock and an entire class of bugs.

What this stack uniquely teaches

  1. Connection lifecycle ownership. With HTTP, the runtime hides the connection; here you own every stage — accept, handshake, register, stream, teardown — and must answer for each: who closes the listener? Who closes each conn? What happens to a reader blocked on a dead peer? The answers (listener closed by Shutdown, only the hub closes out channels, closing the conn interrupts everything) form a discipline that transfers to every network server you'll ever write.
  2. Channel-ownership patterns. One hub goroutine owns the client registry and subscriber set; all mutation flows through request channels. There are no mutexes on the hot path because there is no shared mutable state — there is a single owner and a mailbox. This is Go's “share memory by communicating” maxim made structural rather than slogans.
  3. Backpressure by design. Two different policies, chosen deliberately: readers block on the hub's bounded event queue (fast talkers slow down — backpressure), while writes to slow clients' queues drop the client instead (slow-client isolation). Deciding where to block and where to drop is the core design act of any message system.

02Requirements

Derived directly from chatwire_test.go — the executable specification. If your implementation passes these tests (including under -race -count=2), it satisfies the requirements.

Functional

  • R1 — Join, roster, and fan-out. Two clients connect; each sends its name as the first line. Each learns its assigned name (“* you are alice”), newcomers receive the current roster (“* online: …”), existing members see join announcements, and messages fan out to every member including the sender.
  • R2 — Duplicate names are uniquified. A second “bob” is registered as bob-2; both parties are informed (the newcomer in its welcome, the room via a system event).
  • R3 — Slow-subscriber isolation. With a subscriber whose buffer holds one event and 100 messages flowing, the hub never stalls: active clients and a roomy (256-capacity) subscriber receive all 100, the starved subscriber receives at most its buffer, Unsubscribe doesn't deadlock afterward, and the hub still delivers the next message.
  • R4 — Graceful shutdown. Every client gets a “* server shutting down, goodbye” system line followed by EOF; Serve returns nil; Shutdown returns nil within the caller's context.
  • R5 — Shutdown is idempotent-by-error. A second Shutdown call returns an error wrapping net.ErrClosed rather than panicking or double-closing channels.
  • R6 — Deadline-bounded shutdown force-closes stragglers. A client wedged mid-Write (32MB unread backlog) cannot hold Shutdown past its context: past the deadline, remaining conns are force-closed and context.DeadlineExceeded is returned.
  • R7 — Pre-expired context takes the deterministic fast path. Calling Shutdown with an already-expired context skips the polite wait entirely and immediately force-closes live clients, returning ctx.Err().
  • R8 — Abrupt clients don't disturb others. Peers who hang up before the handshake or die mid-handshake cause no panic and no impact on connected clients.
  • R9 — No goroutine leaks across the whole lifecycle. After joins, traffic, and shutdown plus a settle delay, runtime.NumGoroutine() is back within 5 of baseline.

Non-functional

  • NF1 — Bounded resources everywhere. Per-client write queues cap at 64 slots; the hub's inbound queue caps at 256 events; goroutines scale with connections, never with message volume.
  • NF2 — No lock contention on the hot path. Message routing touches no mutexes; the two mutexes that exist guard the listener state and the live-connection tracking set at their edges.
  • NF3 — Flake-free under load. The suite passes repeatedly (-count=2) with the race detector on real TCP sockets over loopback; assertions wait on conditions with generous timeouts rather than assuming timing.
  • NF4 — Honest shutdown contract. Callers can distinguish clean drain (nil) from deadline-forced teardown (ctx.Err()) from misuse (second call → net.ErrClosed).

03Architecture Decisions

D1: One hub goroutine owns both maps — request channels instead of mutexes

func (s *Server) runHub() {
    clients := make(map[string]*client)
    subs := make(map[<-chan Event]chan Event)

    for {
        select {
        case <-s.stopCh:
            s.finalize(clients, subs)
            return
        case req := <-s.regCh:
            s.register(clients, subs, req)
        case c := <-s.unregCh:
            s.removeAndAnnounce(clients, subs, c)
        case ch := <-s.subAddCh:
            subs[ch] = ch
        case ch := <-s.subDelCh:
            delete(subs, ch)
        case ev := <-s.eventCh:
            s.broadcast(clients, subs, ev)
        }
    }
}

This is the architectural heart of the project. Instead of guarding clients and subs with a sync.RWMutex touched by dozens of goroutines, exactly one goroutine owns both maps, and everyone else talks to it through typed request channels. The select loop is the server's event loop: registrations, departures, subscriptions, unsubscribes, and broadcast events all arrive as messages, and the owner applies them serially — serialization is free, it's the loop itself. The payoff compounds downstream: no lock ordering to reason about, nothing to forget to lock, and (critically, see D4) no send-on-closed-channel panic class, because only the owner ever closes the out-channels.

D2: Reader-per-connection, writer-per-client, hub in between

conn := ln.Accept()
go s.handleConn(conn)   // reader: one per connection

// inside register(), once accepted:
s.wg.Add(1)
go s.writeLoop(c)       // writer: drains c.out onto the socket

Traffic splits along the direction it flows. Each connection's reader goroutine performs the name handshake, then forwards message lines into the hub's bounded eventCh (blocking there applies backpressure to fast talkers), and finally asks the hub to deregister the client on EOF. Each registered client gets a writer goroutine draining its private 64-slot out queue onto the socket. The hub sits between them, moving lines from readers' events to writers' queues. Three rules make the topology safe: the reader never touches the conn once registered; only the hub closes any client's out channel; and in the graceful path the writer is who closes the connection — though it is not the only possible closer, because the hub's eviction path and Shutdown's force-close also close conns directly (see D3 and D5). The invariant that actually prevents races is about channels, not sockets: exactly one owner per out channel, so no send-on-closed panic is possible, and double-closing a conn — which the multiple closers make routine — is harmless by design. Ownership is deliberate, so races are structurally impossible rather than merely avoided.

D3: Drop-on-full vs block-and-wait — two backpressure policies

// To a client's write queue: DROP on full — never stall the room
select {
case c.out <- line:
default:   // slow client: evict it
    delete(clients, c.name)
    s.untrackConn(c.conn)
    close(c.out)
    c.conn.Close()
}

// Into the hub's event queue: BLOCK on full — fast talkers slow down
select {
case s.eventCh <- Event{...}:  // capacity 256
case <-s.hubDone:
}

The same problem — a bounded queue is full — gets opposite answers depending on which side of the hub it happens on, and the asymmetry is the lesson. A slow client (not reading its socket) has nowhere for its queue to drain; blocking the hub would freeze the entire chat room behind one bad connection, so we drop the client instead: close its queue, kill its conn, let its writer exit. That's slow-client isolation. A slow talker filling the hub's inbound queue is different: making them wait is correct, natural backpressure — they'll block in eventCh <- until the hub catches up, and nobody else suffers. Subscribers get the client treatment: non-blocking sends that silently drop events when their buffer is full (slow-subscriber isolation), verified by R3. Choosing per-edge between “block” and “drop” is the fundamental design decision in every message broker, log shipper, and metrics pipeline you'll meet.

D4: Why single-owner maps beat sync.RWMutex here

client = {name, conn, out}
// Exactly two owners of `out`: the hub (sends and closes it),
// the writer (drains it, then closes the conn). Nobody else touches either.

The mutex-based alternative — an RWMutex, readers taking RLock to iterate clients during broadcast, registrars taking Lock — looks simpler and hides three traps. First, lock ordering: broadcast iterates the registry while eviction during that same iteration wants to modify it; every new code path must be audited against every other. Second, lifecycle races: if a deregistering path closes a client's out channel while a broadcaster holds only a read lock, the broadcaster can send on a closed channel — a panic no mutex placement cleanly fixes. Third, fairness: a slow broadcast under lock stalls registration. The ownership design dissolves all three at once: only the hub closes anything, so send-on-closed is impossible by construction; mutation is serialized inside one loop, so there is no ordering to reason about; and the hub never blocks on a client thanks to D3's drop policy. The mutexes that remain (s.mu for listener state, connsMu for live-connection tracking) guard tiny leaf structures at the API boundary — the right place for locks when ownership can't cover them.

D5: Incremental liveConns tracking for deadline force-close

// trackConn runs at every registration and removal point, so the set
// is always current — force-close never sees a stale snapshot.
func (s *Server) forceCloseConns() {
    s.connsMu.Lock()
    conns := s.liveConns
    s.liveConns = make(map[net.Conn]struct{})
    s.connsMu.Unlock()
    for cn := range conns {
        cn.Close()  // closing an already-closed conn is a harmless no-op
    }
}

When Shutdown's deadline expires, wedged writers must be unblocked by killing their sockets. The naive approach — ask the hub for a list of connections — fails exactly when it matters: the deadline may fire before the hub processes the stop signal, so the “snapshot” would be stale or unavailable. Instead, every registration, drop, and departure updates liveConns incrementally under a small mutex, so the set is current at all times regardless of hub progress. This is the fix pinned by regression test TestShutdownExpiredContextForceCloses: with a pre-expired context the hub may never reach finalize, yet the victim's socket still closes. Because closing an already-closed net.Conn just returns an error harmlessly, the “close everything, twice is fine” pattern is safe here.

D6: The shutdown sequence

ln.Close()       → Accept returns net.ErrClosed → Serve returns nil
close(s.stopCh)  → hub exits its select loop…
finalize         → goodbye line queued per client, then close(c.out)
                 → subscriber channels closed → close(s.hubDone)
writers          → range c.out ends → drain → conn.Close() → wg.Done()
doneCh watcher   → wg.Wait() returns → close(doneCh)
Shutdown         → <-doneCh ⇒ return nil | <-ctx.Done() ⇒ forceClose, return ctx.Err()

Graceful shutdown is choreography, and each arrow above is a synchronization edge some goroutine is waiting on. Closing the listener unblocks Serve first so no new clients arrive mid-teardown. stopCh tells the hub to run finalize, which queues the goodbye and then closes each out channel — the close is what releases every writer's range, letting each drain whatever remains before closing its own conn and calling wg.Done(). A dedicated watcher goroutine turns “hub finished and all writers exited” into the single doneCh signal Shutdown waits on. And the deadline arms the escape hatch: if politeness takes too long, force-close kills the stragglers and the caller learns via ctx.Err(). One subtlety earns a test of its own (R7): if the context is already expired, Shutdown skips the polite wait entirely — selecting between two ready cases would race — and goes straight to force-close. Polite-first, forced-if-late, immediate-if-doomed: the full contract in three modes.

04Concept Walkthroughs

net.Listener and net.Conn — owning a connection from birth to death

ln, err := net.Listen("tcp", addr)
...
for {
    conn, err := ln.Accept()
    if err != nil {
        if errors.Is(err, net.ErrClosed) {
            return nil  // Shutdown closed us: a clean stop, not a failure
        }
        return err
    }
    go s.handleConn(conn)
}

A Listener is a queue of incoming connections; Accept pops one and hands you a Conn — a bidirectional byte pipe implementing io.Reader/io.Writer. Everything interesting is in the error handling and lifecycle. When Shutdown closes the listener, a blocked Accept wakes with an error satisfying errors.Is(err, net.ErrClosed) — distinguishing “we're stopping” from “something broke” is what lets Serve return nil on purposeful close. Conns carry deadlines as their universal interrupt: SetReadDeadline bounds the silent handshake window (60 seconds here, so pre-registration conns can't linger forever), and is then cleared with time.Time{} so registered users may idle indefinitely. Most importantly, conn.Close() works from another goroutine: it's how the hub evicts a slow client and how force-close unblocks wedged writers — which is why “who may close, and when” must be answered explicitly rather than left to convention. In chatwire the answer has two parts: the writer goroutine performs the close in every graceful drain, while the hub (eviction) and force-close (shutdown deadline) may close a conn out from under anyone at any time — safe precisely because closing an already-closed conn is a no-op and channel closure stays hub-exclusive.

select as multiplexer — one goroutine, many conversations

select {
case s.eventCh <- ev:   // try to deliver the event...
case <-s.hubDone:       // ...unless the server is shutting down
    return
}

select waits on multiple channel operations and proceeds with whichever is ready — Go's answer to both multiplexing and cancellation. Two uses dominate this codebase. As a multiplexer, it powers the hub's event loop (D1): one goroutine services six different request types without threads-per-request. As a cancellation guard, nearly every blocking operation is paired with a <-s.hubDone arm: a reader pushing an event, a client trying to register, a Subscribe caller — all can abort cleanly if the hub dies mid-conversation instead of blocking forever on a channel nobody will read again. Add default and select becomes a poll — the try-send that implements drop-on-full in D3. The pattern generalizes: whenever a goroutine might block on a channel, ask “what else should I be waiting for?” and add that case. A bare blocking send with no escape hatch is how goroutine leaks begin.

Slow-client vs slow-subscriber — isolating failure domains

The rule: a component's failure may cost itself, never the system. Decide per consumer whether lag means “drop my data” or “evict me” — but never “freeze everyone.”

Both isolation mechanisms exist to protect the hub's progress guarantee — it never waits on a consumer — but they differ in consequence and clientele. A slow subscriber is an in-process observer (tests, metrics hooks): its buffered channel simply misses events when full. Cheap, silent, lossy — appropriate when observations are advisory. A slow client is a remote peer whose socket has stopped draining: buffering can't save it, so the server severs the relationship — queue closed, conn closed — and no farewell is sent: eviction is deliberately silent, with no leave or system event emitted, not even to subscribers. Between them sits the fast talker case, handled by blocking instead: a client flooding eventCh waits for the hub, converting excess enthusiasm into latency rather than loss. Three consumer archetypes, three policies, one invariant throughout: the hub advances. Any architecture where one consumer's pace dictates the system's throughput has already lost at scale.

Graceful shutdown patterns — drain politely, force under deadline

if err := ctx.Err(); err != nil {
    // Deterministic fast path for an already-expired context:
    // skip the polite wait instead of racing two ready cases.
    s.forceCloseConns()
    return err
}
select {
case <-s.doneCh:    // hub finished AND every writer drained
    return nil
case <-ctx.Done():   // patience ran out
    s.forceCloseConns()
    return ctx.Err()
}

Production servers face a shutdown trilemma: lose in-flight work, hang forever, or bound the wait and accept partial teardown. The standard resolution — graceful with a deadline — needs four ingredients, all present here: a stop signal (stopCh) that initiates drain; a join barrier (wg.Wait() inside the doneCh watcher) proving workers finished; a deadline from the caller's context; and an escape hatch (force-close) that converts “wedged” into “closed.” The check of ctx.Err() before entering the select handles the fourth mode most implementations miss: a pre-expired context means both select arms are instantly ready, and which wins is scheduler roulette — so the code checks first and forces deterministically. Note also what Shutdown does not do: it never closes client channels directly. It signals the hub, and the hub — the sole owner — performs every close. Delegation to the owner keeps the no-double-close invariant intact even under repeated Shutdown calls (the second caller gets net.ErrClosed, guarded by s.closed).

05Testing Strategy

Real TCP on ephemeral ports

Nothing is mocked. Tests bind 127.0.0.1:0 to reserve a free port, dial real connections through the loopback stack, and speak the actual wire protocol with bufio readers — exercising accept loops, deadlines, kernel buffering, and half-open connections exactly as production would. Helpers enforce hygiene throughout: startServer registers cleanup that shuts down and asserts Serve returned cleanly; awaitListener polls until the server accepts (its probe conns deliberately hang up before handshake, doubling as abrupt-client fodder); every dial, read, and write carries explicit deadlines so a broken server fails a test in seconds instead of hanging CI. Reading is done via readUntil(substr) — consume lines until the expected one appears — which tolerates interleaved broadcasts rather than assuming message order across clients.

The slow-subscriber proof

slow := s.Subscribe(1)    // capacity 1 — starved by design
fast := s.Subscribe(256)  // roomy — must stay complete

for i := 0; i < total; i++ { gen.send(t, strconv.Itoa(i)) }

waitFor(t, "echo client completeness",
    func() bool { return echoCount() >= total })
...
if dropped > 1 {
    t.Fatalf("slow sub delivered %d events with capacity 1", dropped)
}

TestSlowSubscriberIsolation stages the adversarial scenario directly: one subscriber with capacity 1 against 100 rapid-fire messages, alongside clients and a fat subscriber who must receive all of them. Assertions verify both sides of the contract: completeness for healthy consumers, starvation for the sick one (at most its single buffered event retrievable without blocking), no deadlock on the subsequent Unsubscribe, and hub liveness afterward (one more message still lands). The counting helper reads occupancy via len(ch) without consuming — measuring without perturbing the drop semantics under test. Every wait goes through waitFor, polling a condition against a 10-second ceiling: conditions, not sleeps, are what make this suite flake-proof.

Abrupt-client resilience

TestAbruptClientsDoNotDisturbOthers attacks the handshake path from both ends: a ghost who connects and immediately hangs up (EOF before any name line), and a partial who writes half a name with no newline before dying. Both must be absorbed silently by the reader goroutine — close the conn, exit, disturb no one — while a steady connected client continues exchanging messages normally across a settle window. The same robustness shows up in awaitListener's probe conns: in a real deployment, port-scanners and health checks behave exactly like these ghosts, and a chat server that panics or wedges on them fails within seconds of facing the internet.

Goroutine-leak deltas over the whole lifecycle

time.Sleep(settle)               // let earlier tests finish reaping
base := runtime.NumGoroutine()

// ...3 concurrent users join, chat, then Shutdown...

time.Sleep(2 * settle)
if delta := runtime.NumGoroutine() - base; delta > tolerance {
    t.Fatalf("goroutine leak: delta %d > %d", delta, tolerance)
}

A chat server spawns goroutines per connection and per writer — precisely the shape where leaks hide, because each individual leak looks tiny. The leak test runs the entire lifecycle (joins, traffic, shutdown) and asserts the population returns within 5 of baseline after settle time. This catches all four classic leaks at once: a reader blocked forever on a dead conn, a writer whose out-channel was never closed, the hub failing to exit, and the doneCh watcher stranded by a missed wg.Done(). The generous tolerance acknowledges background noise from the test framework itself; what matters is trend, and a monotonic upward trend across a full lifecycle is never benign.

The -count=2 -race flake protocol

# each project is its own Go module — run from inside the project:
cd projects/06-chatwire && go test -race -count=2 ./...

Concurrency bugs are probabilistic, so proving their absence requires repetition: -count=2 runs the suite twice in one process, multiplying exposure to interleaving luck, and -race instruments every memory access to catch races that didn't happen to corrupt anything this run — especially valuable here because the tests exercise genuinely concurrent paths (concurrent dials, a reader racing shutdown, subscribers filling while broadcasts run). A suite that passes once but flakes on repetition trains people to rerun instead of investigate. Every assertion in this suite was designed under this protocol: primary proofs count events or check identities, timing bounds appear only as generously-bounded backstops (the 3-second cap on a 200ms-deadline Shutdown leaves 15× headroom), and helpers poll conditions rather than sleeping fixed durations. Run the protocol before declaring victory.

06Go in the Wild

Where this stack runs in production

Raw TCP listeners, reader-per-connection goroutines, single-owner state machines, and deadline-bounded shutdown aren't teaching toys — they're the working skeleton of serious infrastructure written in Go:

  • CockroachDB's pgwire — the layer where every PostgreSQL driver connects. Each client connection gets its own goroutine reading the Postgres wire protocol off a raw net.Conn, exactly like chatwire's readers; context cancellation closes conns to unblock query execution, the same force-close move this project's shutdown uses.
  • HashiCorp serf / memberlist — cluster membership and gossip used by Consul and Nomad. Memberlist speaks a custom binary protocol directly over TCP and UDP sockets, manages per-node connections with explicit handshakes and timeouts, and shut down via coordinated channels — a chat room where the members are servers and the messages are liveness gossip.
  • etcd's raft RPC layers — etcd serves raft consensus messages over plain streaming TCP between peers, with dedicated send/receive goroutines per peer connection and careful ownership so only one goroutine writes each stream — chatwire's reader/writer split at production stakes.
  • IRC servers — chatwire's wire format (newline-delimited text, a name handshake, broadcast with system lines prefixed *) is a stripped- down descendant of IRC, which has run the internet's chat since 1988 on exactly this shape of protocol.

Why Go owns the network-server niche

  1. Goroutines make connection-per-goroutine affordable. Classic servers needed epoll or thread pools because threads cost megabytes; a goroutine costs a few kilobytes. That collapses the design space: the obvious program — one reader per connection, blocking reads, straight-line logic — is also the scalable one. Ten thousand connections is ten thousand cheap goroutines, not a callback maze.
  2. Channels make ownership composable. The hub-owns-the-maps pattern you built here scales up unchanged: a single owner plus request channels is how Go's own net/http manages connection state machines, and how production message systems partition ownership. When there's exactly one writer of a piece of state, the race detector stays quiet and reviews get shorter.
  3. Newline-delimited text remains a great first protocol. Redis speaks it (RESP is newline-framed), syslog ships billions of lines a day framed by newlines, JSON Lines powers most data pipelines, and InfluxDB's line protocol put it in the name. It's debuggable with nc, trivially parseable, streaming- friendly, and — as chatwire proves — implementable in five lines of bufio. Start simple; upgrade to length-prefixed framing only when you need binary payloads.

The through-line: accept loop, reader goroutines, an owning hub, bounded queues with deliberate backpressure, and shutdown choreography under a deadline — that's not a classroom exercise. It's the load-bearing structure of databases, cluster managers, and consensus systems, exercised here in ~450 lines with the race detector keeping score.
