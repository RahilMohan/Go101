01Stack Evaluation

The stack: pure standard library, again

taskline uses three load-bearing stdlib packages — encoding/json, time, and os — plus small helpers (errors, fmt, path/filepath). No database driver, no storage engine, no CLI framework, no go.sum. Where project 01 proved you can build a real tool with nothing imported, project 02 proves something harder to believe until you've done it: persistent state doesn't require a database.

PackageRole in tasklineLesson it carries
encoding/jsonSerialize/deserialize the whole task list as a JSON arrayStruct tags as declarative metadata; round-tripping your own types
timeCreatedAt/DoneAt timestampstime.Time has built-in JSON marshaling — timestamps survive a save/load cycle exactly
osCreateTemp, Rename, ReadFile, env vars in the CLIAtomic writes via temp file + rename; files as the simplest durable store

Rejected alternatives

  • boltDB / SQLite (via CGo or pure-Go ports) — both are excellent embedded stores used by real tools (etcd runs on boltDB). But they drag storage-engine mechanics — B-trees, pages, transactions, cursors — into a lesson about structs and JSON. The engine would dominate the codebase and drown the actual teaching content. When a later project needs indexed or concurrent access, one of these returns and its value will be obvious.
  • Third-party CLI frameworks (cobra et al.) — taskline's five subcommands are a plain switch over os.Args[1]: ~30 lines, fully transparent. A framework would add a dependency tree to hide logic this small.
  • An append-only log file — writing one line per mutation avoids full rewrites but introduces replay/recovery/compaction concerns: exactly the complexity budget this project refuses to spend (see D2).

What this stack uniquely teaches

  1. Struct tags as metadata. One backquoted string per field controls how Go structs become JSON and back — your first taste of reflection-driven programming without writing any reflection yourself.
  2. Atomic file writes. The temp-file-then-rename dance is the same pattern databases, editors, and package managers use under different names. Learning it on a 40-line save() makes the idea permanent.
  3. The zero-dependency philosophy. A single static binary storing its data in one human-readable file is a legitimate production design for countless tools — not just a teaching simplification. Knowing when the stdlib suffices is itself an engineering skill.

02Requirements

Derived directly from taskline_test.go at the project root — the executable specification. If your implementation passes these tests, it satisfies the requirements.

Functional

  • R1 — Add creates tasks with sequential IDs. Each Add(title) assigns ID = index + 1 within a run, sets status todo, records a non-zero, monotonically non-decreasing CreatedAt, and leaves DoneAt nil. Unicode titles like "fika ☕ med kanelbulle" work unchanged.
  • R2 — List reflects stored tasks. After adding N tasks, List() returns N tasks whose IDs, titles, statuses, and CreatedAt values match what was added (comparing times with Equal, since time equality isn't simple field comparison).
  • R3 — Missing store reads as empty, not error. A never-written file yields an empty, non-nil slice from List() — so callers can range over it safely. Same for an existing-but-empty file.
  • R4 — State survives reopen. Tasks added through one Store must be visible through a second OpenStore(path) pointed at the same file — including exact CreatedAt values after a JSON round-trip.
  • R5 — SetStatus mutates persisted state. After SetStatus(id, doing), the raw file parses as valid JSON containing the task with the new status.
  • R6 — Unknown IDs return ErrNotFound. Both SetStatus and Remove fail with errors satisfying errors.Is(err, ErrNotFound).
  • R7 — Remove deletes only the target. After removing ID 1 of two, only ID 2 remains — and the next Add gets ID 3, not 1 (see D4 for why that's correct).
  • R8 — Corrupt store surfaces an error. A file containing garbage makes every operation fail with a decode error — never panic, never silently reset data.
  • R9 — DoneAt tracks Status. Fresh tasks have nil DoneAt; marking done sets it (≥ CreatedAt); moving away from done clears it again.

Non-functional

  • NF1 — Atomic persistence. Every mutation leaves the store file either fully old or fully new — never truncated or half-updated, even if the process dies mid-write. The atomic-rename test verifies the file still parses after mutation.
  • NF2 — Errors wrap, don't erase. Domain sentinels (ErrNotFound) and I/O failures travel up the call chain wrapped with context, checkable via errors.Is at the boundary where the CLI turns them into messages and exit codes.
  • NF3 — Human-inspectable format. The store is indented JSON (MarshalIndent) — openable, diffable, and editable by hand, which matters more than compact bytes at this scale.

03Architecture Decisions

D1: Store as a path plus behavior

type Store struct {
    path string
}

func OpenStore(path string) (*Store, error) {
    if path == "" {
        return nil, fmt.Errorf("taskline: empty store path")
    }
    return &Store{path: path}, nil
}

The entire persistent layer is one unexported string. No open handles, no caches, no locks: each method reads fresh from disk, computes, and writes back. That's a deliberate constraint — statelessness makes the store trivially testable (reopen freely, inspect the raw file between calls) and eliminates a whole category of stale-cache bugs. The cost is re-reading the file on every operation, which is irrelevant at human TODO-list scale and honest about what this design is. Note the pointer receiver throughout: *Store methods mutate shared disk state, and returning &Store{...} is the constructor idiom Go uses instead of class constructors.

D2: Whole-file rewrite, always

Every mutation follows the same shape: List() → modify the slice → save(tasks) serializes the entire array and replaces the file. An append-log would write fewer bytes but buys two problems: recovery logic to replay partial logs, and compaction to bound growth. Rewriting the whole file avoids both — the file's contents after any successful save are definitionally consistent, because they were produced by one json.MarshalIndent of one coherent slice.

But be clear about what this design does not buy you: it assumes a single writer at a time. There is no locking. Each operation is read-modify-write-rename, so two concurrent writers each read the same snapshot, apply their own change, and rename over the file in turn — the second rename silently discards the first writer's update (last-writer-wins). Run thirty taskline add processes at once and you end up with a one-task store and zero errors. The temp+rename dance guarantees readers never see a torn or half-written file; it says nothing about lost updates. If you need multi-writer safety, that's what file locks (syscall.Flock) or real databases are for — deliberately out of scope for a zero-dependency lesson. Correctness-by- construction within one writer beats incremental cleverness here, which is precisely the trade real databases eventually make too (checkpointing is a whole-file snapshot wearing a suit).

D3: Temp file + rename = atomicity

tmp, err := os.CreateTemp(filepath.Dir(s.path), ".taskline-*.tmp")
// ...write, Sync, Close...
if err := os.Rename(name, s.path); err != nil {
    os.Remove(name)
    return fmt.Errorf("rename over %s: %w", s.path, err)
}

Writing directly to tasks.json risks leaving a truncated file if the process crashes mid-write. Instead: write the complete new content to a temp file in the same directory (same-directory matters — rename is only atomic within one filesystem), flush it with Sync, close it, then os.Rename it over the target. Rename is atomic at the OS level: readers see either the old inode or the new one, never a hybrid. Every failure path cleans up the abandoned temp file. This is the same guarantee editors implement when they save your file, and the seed of what databases call a commit.

D4: IDs are max(existing)+1 — and what that implies

max := 0
for _, t := range tasks {
    if t.ID > max { max = t.ID }
}
task := Task{ID: max + 1, /* ... */}

No counter lives in the Store, because the Store holds no state — the file is the state. So new IDs derive from the current contents: highest existing ID plus one. The consequence, pinned by TestRemoveDeletesTask: after removing ID 1 from {1, 2}, the next Add gets ID 3, not recycled ID 1. Freed IDs are reused only once all higher IDs are gone. That's the right trade for a file-backed store — it keeps allocation deterministic from file contents alone — and it mirrors how users think: a removed task's ID shouldn't silently reappear attached to something else.

D5: DoneAt stays consistent with Status

tasks[i].Status = st
if st == StatusDone {
    now := time.Now()
    tasks[i].DoneAt = &now
} else {
    tasks[i].DoneAt = nil
}

DoneAt is a derived fact, not independent state: it's set exactly when a task transitions to done and cleared on any other status. Letting them drift — a task marked doing still carrying a completion timestamp — would poison every report built on the data, so SetStatus enforces the invariant on every write rather than hoping callers remember. Two details worth studying: DoneAt is a *time.Time because Go has no tri-state bool — nil is the only way to say "never"; and now is captured in a local before taking its address, because &time.Now() won't compile (you can't take the address of a return value). TestDoneAtLifecycle walks the full todo → done → doing arc to lock the rule in.

D6: Library core, thin command shell

projects/02-taskline/
├── taskline.go             # package taskline — stubs you implement
├── taskline_test.go        # the executable spec
└── solution/
    ├── solution.go         # package solution — Task, Store, ErrNotFound
    └── cmd/taskline/main.go   # subcommand wiring

All persistence logic lives in the library package; main only dispatches subcommands (add/list/do/start/rm), formats columns, maps errors.Is(err, ErrNotFound) to friendly stderr output, and picks the store path from TASKLINE_FILE (defaulting to ~/.taskline.json). The split keeps the interesting code process-free and unit-testable — the same library-plus-cmd layout as project 01, now carrying state.

04Concept Walkthroughs

Structs and methods with receivers

The idea: a Go struct bundles related fields; a method attaches behavior via a receiver — the parameter written before the method name. Value receivers work on copies; pointer receivers share and can mutate.

type Task struct {
    ID        int
    Title     string
    Status    Status
    CreatedAt time.Time
    DoneAt    *time.Time
}

func (s *Store) SetStatus(id int, st Status) error

Task is pure data; Store owns behavior. Every Store method uses a pointer receiver because they logically operate on the same underlying store — even though Store contains only a string, using *Store signals "these methods belong together, operating on one thing," and matches how Go reads idiomatic API design. Notice also the named type Status string: three constants (StatusTodo/StatusDoing/StatusDone) replace bare strings, giving typos a compile-time home and IDEs something to autocomplete. This is Go's type-safety sweet spot: no classes, no inheritance — just data plus functions with a first argument spelled differently.

JSON tags — metadata that drives code

ID        int        `json:"id"`
Title     string     `json:"title"`
CreatedAt time.Time  `json:"created_at"`
DoneAt    *time.Time `json:"done_at,omitempty"`

Those backquoted strings are struct tags — annotations the compiler stores alongside each field and encoding/json reads at runtime via reflection. They're a contract in miniature:

  • json:"created_at" renames the key in serialized output — Go convention says CreatedAt, JSON convention says snake_case; tags translate.
  • ,omitempty drops DoneAt entirely when nil, so unfinished tasks carry no misleading "done_at": null noise in the file.
  • Omit a tag and json falls back to the field name verbatim — usually wrong for cross-language formats, which is why explicit tags everywhere is the disciplined habit.

This is your first encounter with declarative metadata: you describe what the mapping should be and a library figures out how. The same mechanism powers config parsing, ORM column mappings, and Kubernetes' YAML-to-Go decoding — learn it here on ten lines and you'll recognize it everywhere.

Slices vs maps — the ordering tradeoff

The natural alternative to []Task is map[int]Task keyed by ID — O(1) lookup, no linear scans in SetStatus/Remove. So why a slice? Because List() must return tasks in insertion order, and Go map iteration order is deliberately randomized — relying on it is a classic bug. With a slice, order is structural, not reconstructed: the file is a JSON array, the decode produces an ordered slice, and List() hands that ordering straight through. The costs are acceptable: finding a task by ID is O(n) over a list sized in tens, and duplicate-ID prevention rests on the max+1 discipline of D4. The general lesson: choose the structure whose default iteration matches what you actually need to produce; convert to maps (or sort) at the edges where lookup genuinely dominates. Note also the discipline in List(): missing files and empty input return []Task{}, never nil — callers can range over the result unconditionally, and the test suite enforces non-nil explicitly.

time.Time marshals itself

if got[0].ID != first.ID || !got[0].CreatedAt.Equal(first.CreatedAt) { // .Equal, not ==

time.Time implements json.Marshaler: it serializes to RFC 3339 — "2026-08-25T14:03:00.123456789+02:00" — and unmarshals back losslessly, including timezone. That's why TestPersistenceAcrossReopen can assert an exact timestamp match after a save/load cycle with zero custom code: the round-trip is handled by the type's own methods. The subtle part the tests teach: compare times with t.Equal(u), not == — two time.Time values can represent the same instant with different monotonic-clock or location internals, making raw == unreliable. And note time.Now()'s value includes a monotonic reading that JSON strips away — another reason equality goes through the exported API.

os.CreateTemp + os.Rename — the atomic pair

tmp, err := os.CreateTemp(dir, ".taskline-*.tmp")  // unique name, O_EXCL create
tmp.Sync()                                        // force bytes to disk
tmp.Close()
os.Rename(name, s.path)                            // atomic swap

CreateTemp solves the "safe scratch filename" problem correctly: it opens the file with exclusive-create semantics, so no collision or symlink attack window exists, and the * in the pattern becomes random characters. Sync matters because Write reaching the OS buffer isn't durability — Sync forces the data to stable storage before rename publishes it, so the renamed file is never empty-on-disk. Rename itself replaces the destination atomically on POSIX and Windows alike. The choreography — create, write, sync, close, rename, remove-on-any-error — is worth memorizing; it recurs whenever Go code must update a file without ever exposing a torn version.

Sentinel errors and errors.Is

var ErrNotFound = errors.New("taskline: task not found")

return fmt.Errorf("taskline: set status: %w", ErrNotFound)

// at the CLI boundary:
if errors.Is(err, solution.ErrNotFound) {
    fmt.Fprintf(os.Stderr, "taskline: no task with id %d\n", id)
}

A sentinel is a package-level error created once and compared against by identity. Interior layers wrap it with context using %w; the outermost caller interrogates with errors.Is, which unwraps through every layer until it finds the sentinel. The payoff is visible in main.go's do/start/rm handler: user-facing "no task with id %d" (exit 1) versus generic failure (exit 1 with the raw chain logged) — decided by one errors.Is, with zero message-string matching anywhere. The same pattern distinguishes "file doesn't exist yet" from real I/O trouble in List(), via the standard library's own fs.ErrNotExist sentinel. Project 01 introduced wrapping; this project is where you feel why: sentinels let libraries speak in codes while humans read sentences.

05Testing Strategy

Persistence means reopening, not just reading back

TestPersistenceAcrossReopen asserts the property that actually matters: data written through one Store instance is readable through a different instance constructed later from the same path.

reopened, err := OpenStore(path)
got, err := reopened.List()

if got[0].ID != first.ID || !got[0].CreatedAt.Equal(first.CreatedAt) {
    t.Errorf("after reopen got[0] = %+v, want %+v", got[0], first)
}

Why reopen instead of calling List() on the original store? Because a broken implementation could pass a naive test by keeping tasks in memory and skipping the file entirely. Reopening forces the data through the full JSON serialize → write → read → decode round-trip, catching tag mistakes, timestamp truncation, and encoding drift. It's the difference between testing "the object remembers" and testing "the disk remembers" — only the second is persistence.

Corrupt input is a first-class test case

os.WriteFile(path, []byte("{not json at all"), 0o644)
if _, err := s.List(); err == nil {
    t.Fatal("List() on corrupt file error = nil, want decode error")
}

The test hand-writes garbage directly into the store file — bypassing the API to simulate the real world, where files get truncated by full disks, mangled by concurrent editors, or half-migrated by older versions. The assertion is deliberately minimal: an error must occur. That pins the safety contract — corrupt data never masquerades as an empty list (which would let the next Add wipe the file), never panics — while leaving error message wording free to evolve. Compare with TestListMissingFileReturnsEmptyNonNilSlice, which draws the opposite conclusion from a different absence: missing file = empty store = success; unreadable file = loud failure.

errors.Is assertions on domain sentinels

if err := s.SetStatus(99, StatusDone); !errors.Is(err, ErrNotFound) {
    t.Errorf("SetStatus(99) error = %v, want errors.Is(err, ErrNotFound)", err)
}

Note what the test does not do: it doesn't compare err == ErrNotFound, and it doesn't inspect strings. It demands the error wraps the sentinel — which means the implementation must use %w somewhere between detection and return. The test enforces the architecture, not just the outcome: get the right error the wrong way (say, by formatting the message manually) and it fails. This is executable specification at its sharpest — the wrapping discipline from Concept Walkthroughs exists because a test refuses anything less.

Lifecycle tests walk state transitions end to end

TestDoneAtLifecycle and TestRemoveDeletesTask are scenario tests: add → transition → verify → transition back → verify again, checking the file (via a fresh List) at each step rather than trusting return values alone. They exist because bugs love transitions — the code path that sets DoneAt is easy; clearing it on the way back is the part that rots. Meanwhile mustOpen's use of t.TempDir() gives every test a fresh directory auto-cleaned at test end — parallel-safe isolation for free, no teardown boilerplate.

06Go in the Wild

Where this stack runs in production

A single static binary persisting structured state to a local file is one of the most common shapes in the Go ecosystem:

  • Kubernetes API objects — every k8s resource (Pod, Deployment) is a Go struct decoded from JSON/YAML via struct tags, exactly like taskline's Task at infinitely larger scale.
  • Docker configuration — ~/.docker/config.json is read and rewritten by the Docker CLI with encoding/json; registries speak the same vocabulary.
  • GitHub CLI (gh) — keeps auth tokens and preferences in a JSON config file managed by the binary itself; taskline's TASKLINE_FILE-style configuration is the same pattern.
  • taskwarrior-style TODO CLIs — the entire genre of terminal task managers stores tasks as line-oriented or JSON files in the home directory, for exactly the reasons this project chose them: greppable, syncable, diffable, indestructibly simple.
  • etcd's boltDB foundation — proof the rejected alternative is real: when scale demands B-trees and transactions, Go reaches for embedded engines built with Go itself.

Why encoding/json conquered the ecosystem

  1. Struct tags make schemas free. Any Go type becomes wire-format-ready with a few annotations — no codegen, no schema language, no separate model layer. This lowered the cost of "just expose that struct as JSON" so far that it became the default way Go services, CLIs, and cloud APIs exchange data.
  2. The cloud runs on it. AWS SDKs, GCP clients, and effectively all of the Kubernetes control plane marshal and unmarshal with encoding/json semantics. Fluency in tags, omitempty, and round-trip quirks is table stakes for cloud engineering in Go.
  3. Stdlib suffices until scale demands otherwise. File-based storage carries real products surprisingly far — config, state, small datasets, single-user tools. The escalation path (embedded KV store → client/server database) is well-marked, and knowing when to climb it starts with having built the rung below: whole-file snapshots with atomic commits are conceptually a checkpointing database, minus the concurrency.

The through-line: structs-with-tags, atomic writes, and sentinel errors aren't toy-project techniques. They're the daily vocabulary of every Go service talking to a cloud API and every tool keeping state on your laptop — and this project exercises all three in under 200 lines.
