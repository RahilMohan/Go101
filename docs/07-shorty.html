01Stack Evaluation

The stack: the stdlib web tier plus one driver

shorty is built from Go's own HTTP server stack — net/http with the Go 1.22-enhanced http.ServeMux, httptest, and crypto/rand — plus exactly two things beyond the standard library: database/sql's driver contract fulfilled by modernc.org/sqlite, a pure-Go SQLite implementation. That single dependency is the entire go.sum. Projects 01–06 stayed dependency-free; this is the first project that deliberately crosses the line, precisely so you can learn how little a well-chosen dependency costs — and what the interface between your code and someone else's package actually looks like.

Rejected alternatives

  • chi / gorilla/mux routers — both are excellent and battle-tested, but they exist largely because the old default mux couldn't match methods or capture path segments. Go 1.22 closed that gap. Routing through chi would hide exactly the lesson this project exists to teach: reading and trusting the new pattern-matching grammar ("POST /api/shorten", "/{code}", r.PathValue) that now ships in every Go installation.
  • mattn/go-sqlite3 — the historically dominant SQLite driver, but it binds to the C library via cgo. That means every contributor needs a C toolchain, cross-compilation becomes painful (CGO_ENABLED=1 plus per-target compilers), and Windows CI needs extra setup. For a teaching repo whose tests must run anywhere go test runs, that friction is disqualifying.
  • PostgreSQL — the production-grade answer for a real multi-instance URL shortener, and the wrong answer here. It demands a server process, credentials, port management, and cleanup before the first test can run. A file-backed SQLite database created inside t.TempDir() gives real SQL semantics — constraints, transactions, persistence across reopen — with zero setup.

The pure-Go tradeoff, stated honestly

The implementer's rationale, from the solution's own package comment:

"Storage uses modernc.org/sqlite: a pure-Go (cgo-free) SQLite driver, trading raw speed for zero toolchain friction — no C compiler needed on any platform."

The pure-Go translation of SQLite is measurably slower than the C binding under heavy write load, and its error strings are its own (more on that below). For a service whose hot path is one indexed primary-key lookup per redirect — microseconds either way — the speed cost is invisible, while the build-portability win is total.

What this stack uniquely teaches

  1. The modern stdlib web tier. Method matching, wildcard segments, and path-value extraction are now first-class in the standard library. Learning them here — before any framework — means you'll always know what a router library is adding beyond what http.ServeMux already does.
  2. database/sql as an interface, not a product. Your code speaks *sql.DB; the driver is interchangeable. Swapping modernc for mattn (or for a Postgres driver) changes one import and one DSN — which is exactly why the places where the driver leaks through (error-text matching) deserve your attention.
  3. Server lifecycle ownership. Bounded request bodies, panic recovery, structured logging, and Ctrl-C-driven graceful shutdown are not features you add later — they're part of what "an HTTP server" means, exercised here from the first version.

02Requirements

Derived directly from shorty_test.go — the executable specification. If your implementation passes these tests (including under -race), it satisfies the requirements.

Functional

  • R1 — Round trip works end to end. POSTing {"url": "https://example.com/path?q=1"} to /api/shorten returns 201 with a 6-character code and a short_url of base + "/" + code; GETting /code returns 302 Found with the original target in Location; the store then reports Count() == 1.
  • R2 — Duplicate explicit codes conflict safely. A second SaveCode("dup1", …) returns an error satisfying errors.Is(err, ErrCodeTaken), and the original mapping remains intact when resolved afterwards.
  • R3 — Validation rejects bad URLs with JSON errors. Empty strings, scheme-less hosts, non-http(s) schemes (ftp://, javascript:), and malformed URLs all get 400 with an "error" key in the body, and nothing is stored (Count() == 0 after the batch).
  • R4 — Recoverer converts panics into clean 500s. A handler that panics yields 500 with a JSON {"error": …} body; the recoverer's log captures both the panic value and a goroutine stack trace; the request logger still emits its method/path/status line for the same request.
  • R5 — Concurrent shortens never collide. Twenty parallel POSTs all return 201 with six-character codes, all codes are distinct, and the store holds exactly twenty rows — passing under -race.
  • R6 — Data survives close/reopen. Save a mapping, close the store, reopen the same database file: resolve succeeds and count persists.
  • R7 — Unknown codes surface as a typed error. Resolve("missing") returns an error satisfying errors.Is(err, ErrNotFound).

Non-functional

  • NF1 — Codes are unguessable. Generated from crypto/rand over base62, not counters or timestamps — one user cannot enumerate another's shortened URLs.
  • NF2 — Request bodies are bounded. Every shorten request wraps its body in http.MaxBytesReader at 1 MiB, so a hostile client can't stream gigabytes into memory.
  • NF3 — Panics never take down the process. Any downstream handler panic is recovered at the middleware boundary, answered with a uniform 500 JSON body, and fully logged with a stack.
  • NF4 — Shutdown is graceful. Ctrl-C stops accepting new connections, gives in-flight requests up to five seconds to finish, and closes the store cleanly.
  • NF5 — Tests need no environment. Every test builds its own server on an ephemeral port backed by a fresh temporary-file SQLite database; the suite passes anywhere Go compiles, including with cgo disabled.

03Architecture Decisions

D1: One declarative route table

mux := http.NewServeMux()
mux.HandleFunc("POST /api/shorten", sv.handleShorten)
mux.HandleFunc("GET /api/stats", sv.handleStats)
mux.HandleFunc("GET /{code}", sv.handleRedirect)
mux.HandleFunc("/", writeError(http.StatusNotFound, "not found"))

The entire API surface is four lines, each readable as an English sentence: this method on this path goes to this handler. Two details carry weight. First, /api/stats is registered before /{code} conceptually matters less than you'd think — ServeMux prefers the more specific pattern, so literal segments always beat wildcards; /api/stats wins over /{code} regardless of registration order. Second, the catch-all "/" exists to turn every unmatched request into a deliberate JSON 404 rather than the mux's default plain-text response — clients of a JSON API should never receive an HTML error page.

D2: Logger outside, recoverer inside

return RequestLogger(log.Writer())(Recoverer(log.Writer())(mux))

Read middleware chains inside out: a request passes through RequestLogger first, then Recoverer, then reaches the mux. The order is chosen for a concrete reason: if Recoverer were outermost, a panicking request would abort before the logger ever saw it finish, and the log line would vanish along with the panic. With the logger outside, every request — including ones that panicked mid-handler — gets exactly one completion line with its true status (the 500). Meanwhile the recoverer sits close enough to the handlers that its deferred recover() catches anything below it, and it writes the panic value plus debug.Stack() to the same log sink. The test suite pins this arrangement: it asserts both the recovered JSON response and the subsequent log line for the same exploded request.

D3: One connection, because SQLite has one writer

db, err := sql.Open("sqlite", dbPath)
...
db.SetMaxOpenConns(1) // modernc.org/sqlite serializes writes; one conn avoids SQLITE_BUSY churn
for _, pragma := range []string{
    "PRAGMA journal_mode=WAL",
    "PRAGMA busy_timeout=5000",
} { ... }

This is the least obvious line in the project and arguably the most instructive. database/sql wants to open many connections, but SQLite allows exactly one writer at a time; a pool racing N connections toward the file produces SQLITE_BUSY contention that the busy-timeout then papers over with waiting. Capping the pool at one makes serialization happen in Go (where requests queue politely) instead of inside SQLite lock machinery. The PRAGMAs follow immediately after open because they apply per connection — with a one-connection pool, executing them once is guaranteed sticky; with a growing pool you'd have to re-apply them on every new connection via a connect hook. WAL journaling lets readers proceed during a write, and busy_timeout=5000 is belt-and-braces patience for any residual contention.

D4: Bound the body before you decode it

r.Body = http.MaxBytesReader(w, r.Body, maxBodyLen)  // maxBodyLen = 1 << 20 (1 MiB)
var req struct{ URL string `json:"url"` }
if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
    writeError(http.StatusBadRequest, "invalid JSON body")(w, r)

A JSON decoder will happily consume whatever stream it's handed; without a cap, one malicious client streaming a multi-gigabyte "request body" becomes a memory/disk-exhaustion denial of service. MaxBytesReader enforces the limit at read time and signals the server to close the connection once the limit trips. Because the wrapper surfaces the violation as an ordinary read error, the existing decode-failure path handles it — which is why an oversized body comes back as 400 Bad Request rather than the arguably more correct 413 Content Too Large. That's a documented simplification, not an accident: one validation funnel, one status code, simpler contract. Production services often split the case by inspecting the error type; the lesson is that you choose this deliberately.

D5: Crypto-random codes with collision retry

for i := 0; i < insertTries; i++ {   // insertTries = 5
    code := generateCode()
    switch err := sv.store.Save(code, u.String()); {
    case err == nil:
        writeJSON(w, http.StatusCreated, map[string]string{
            "code": code, "short_url": sv.base + "/" + code,
        })
        return
    case errors.Is(err, ErrCodeTaken):
        continue // generated-code collision; astronomically rare — retry

Six base62 characters give 62⁶ ≈ 56.8 billion codes. At even a million stored URLs, the chance a fresh random code collides is about 0.0018% — yet the design still handles it, because "astronomically rare" and "impossible" are different engineering claims. The loop treats ErrCodeTaken not as failure but as instruction: draw again. Five tries bounds worst-case work. The generator itself uses crypto/rand, mapping random bytes onto the 62-character alphabet via modulo. That introduces a tiny modulo bias (256 isn't divisible by 62), skewing some characters by under 4% — negligible here where the requirement is unguessability at human scale, and worth recognizing as a real (and fixable, via rejection sampling) bias whenever the alphabet grows or security margins tighten.

04Concept Walkthroughs

Go 1.22 routing grammar: methods, wildcards, and what {code} won't match

mux.HandleFunc("POST /api/shorten", sv.handleShorten)
mux.HandleFunc("GET /{code}", sv.handleRedirect)
...
target, err := sv.store.Resolve(r.PathValue("code"))

Before Go 1.22, the default mux matched only literal prefixes; anything dynamic required a third-party router. The new grammar puts three powers into the standard library. A method prefix ("POST /api/shorten") rejects wrong-method requests with 405 Method Not Allowed automatically — no manual method checking inside handlers. A wildcard segment (/{code}) captures exactly one path segment, retrievable with r.PathValue("code"). And specificity rules resolve conflicts deterministically: literal beats wildcard, longer beats shorter, so GET /api/stats always routes to stats, never into the redirect handler as a code named "stats".

The subtle point: {code} matches a single segment — it stops at /. A request to /foo/bar doesn't route to the redirect handler with code "foo/bar"; it falls through to the catch-all "/" and gets the JSON 404. That containment is what makes the catch-all safe to register: only genuinely single-segment paths can ever be interpreted as codes.

Middleware as func(http.Handler) http.Handler

func RequestLogger(w io.Writer) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(rw http.ResponseWriter, r *http.Request) {
            start := time.Now()
            rec := &statusRecorder{ResponseWriter: rw, status: http.StatusOK}
            next.ServeHTTP(rec, r)
            fmt.Fprintf(w, "%s %s %d %v\n", r.Method, r.URL.Path, rec.status, time.Since(start))
        })
    }
}

The triple-nested signature looks intimidating until you name each layer: the outer call takes configuration (where to log); the middle receives the next handler in the chain; the inner is the actual handler that runs per request. This shape is the ecosystem's de facto standard — chi, gorilla, and countless libraries use the identical type, which is why middleware written this way composes across all of them. Note the statusRecorder trick: http.ResponseWriter offers no way to ask "what status did I write?", so the logger wraps it, records the code in WriteHeader, and passes the wrapper downstream. Composition is visible in one line — RequestLogger(...)(Recoverer(...)(mux)) — and changing execution order is literally reordering those calls.

Placeholders vs concatenation: why ? is not a style choice

// correct — the value travels separately from the SQL text:
db.Exec(`INSERT INTO urls (code, url) VALUES (?, ?)`, code, url)

// broken — the value is parsed as SQL:
db.Exec("INSERT INTO urls VALUES ('" + code + "', '" + url + "')")

Run the broken version with code = "x'); DROP TABLE urls;--" and the database dutifully executes two statements: your insert and an attacker's table deletion. With placeholders, the driver sends the statement text and the values down separate channels; the SQL parser never sees user bytes as code, so injection is structurally impossible — not merely filtered. The same mechanism is also a performance feature: the prepared statement shape can be reused instead of re-parsed per row. In shorty every query uses placeholders without exception, including lookups (SELECT url FROM urls WHERE code = ?) — a lookup feels harmless to interpolate, which is exactly how injection bugs survive code review.

database/sql lifecycle: QueryRow, ErrNoRows, and honest wrapping

var target string
err := s.db.QueryRow(`SELECT url FROM urls WHERE code = ?`, code).Scan(&target)
if errors.Is(err, sql.ErrNoRows) {
    return "", fmt.Errorf("shorty: resolve %q: %w", code, ErrNotFound)
}

QueryRow is the idiomatic single-row read: it defers fetching until Scan and — critically — releases the connection automatically, so there is no rows.Close() to forget. Its one quirk is that "no rows" arrives as an error, the sentinel sql.ErrNoRows. The translation step shown above is where storage vocabulary becomes domain vocabulary: callers check errors.Is(err, ErrNotFound) and never learn that SQL was involved. One accuracy note worth internalizing: because fmt.Errorf("%w", ErrNotFound) wraps the domain sentinel (not sql.ErrNoRows) into a brand-new chain, a caller who checks errors.Is(err, sql.ErrNoRows) will not match — the storage detail is intentionally sealed behind the domain error. Also note the duplicate-detection counterpart in SaveCode: it recognizes conflicts by matching the substring "UNIQUE constraint failed" in the driver's error text. SQLite's spec doesn't mandate structured error codes through database/sql, so this driver-dependent sniffing is a pragmatic but portable-only-within-this-driver compromise — swap drivers and that check may need revisiting.

Graceful shutdown: signal to deadline to drain

ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
defer stop()
...
select {
case err := <-errCh:          // server stopped on its own
case <-ctx.Done():            // Ctrl-C arrived
}

shutdownCtx, cancel := context.WithTimeout(context.Background(), 5 * time.Second)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil { ... }

Killing a server mid-request drops connections and leaves clients retrying blind. Graceful shutdown has three steps. signal.NotifyContext turns SIGINT into a canceled context — signals become ordinary cancellation, testable and composable. srv.Shutdown(ctx) then closes the listener (no new requests) while letting in-flight handlers finish, bounded by the context: five seconds is a common budget long enough for normal requests, short enough that a stuck handler can't pin the process forever (after the deadline, Shutdown gives up and returns an error). Finally store.Close() runs via defer, flushing SQLite cleanly — the reason the persistence-across-reopen property holds in real operation, not just in tests. Note the select guards the case where the server exits on its own (port already bound): ListenAndServe always returns http.ErrServerClosed after a successful Shutdown, which the code filters explicitly.

05Testing Strategy

Full-stack tests without managing ports

ts := httptest.NewServer(sv.Handler())
t.Cleanup(ts.Close)

resp, body := postShorten(t, ts, target)

httptest.NewServer wires the real handler stack — mux, both middleware, the real SQLite store — onto an OS-assigned ephemeral port, so tests exercise genuine HTTP over loopback with zero port bookkeeping and zero cross-test collisions. The helpers encode the suite's hygiene: postShorten marshals, posts, decodes, and fails the test on transport errors; noRedirectClient sets CheckRedirect to return http.ErrUseLastResponse so the redirect test sees the raw 302 and inspects its Location header instead of silently following it to the destination.

Real databases, disposable files

func newTestStore(t *testing.T) *Store {
    t.Helper()
    store, err := OpenStore(filepath.Join(t.TempDir(), "test.db"))
    ...
    t.Cleanup(func() { ... store.Close() })
}

The tests refuse to fake the storage layer. Each test opens a genuine SQLite database in its own t.TempDir() — auto-created, auto-deleted — so constraint behavior, PRAGMA effects, and persistence semantics are the real thing. That choice is what makes TestPersistenceAcrossReopen meaningful: save, Close(), OpenStore the same path again, and prove the mapping survived a genuine process-level close/reopen cycle. An in-memory fake would test the fake.

Concurrency as a first-class assertion

TestConcurrentShortensAllDistinct fires twenty POSTs simultaneously from goroutines, collecting codes into pre-assigned slice slots guarded by one mutex. The assertions are three-layered: zero failures, all twenty codes present and distinct (checked via a seen-set), and store.Count() == 20 — proving the single- connection pool serialized the writers correctly rather than dropping any insert. Run with -race, the test doubles as a memory-model audit of the handler stack under simultaneous load. Distinctness is not paranoia: it verifies the crypto-random generator and the collision-retry loop together, since a counter-based or timestamp-based code generator could produce duplicates under exactly this kind of burst.

Middleware proven with a deliberately exploding route

panicHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    panic("boom")
})
wrapped := RequestLogger(&reqBuf)(Recoverer(&logBuf)(panicHandler))

TestMiddlewareRecoverAndLog builds the chain by hand with bytes.Buffer sinks instead of the global logger, mounts a handler whose only job is to panic, and asserts the complete aftermath: the client receives a decodable JSON 500 (not a hung or truncated response); the recoverer's buffer contains both the panic value "boom" and goroutine stack evidence; and the logger's buffer contains GET /explode 500 — confirming the logger-outside-recoverer ordering from D2 actually delivers a completion line for the failed request. Redirecting middleware output into buffers is what turns "it logs somewhere" into an assertable fact.

Negative space: proving what didn't happen

The strongest assertions in the suite are about absence. TestShortenValidationRejectsBadURLs drives six invalid payloads through the table and then checks store.Count() == 0 — rejected input left no residue. TestSaveCodeConflict resolves "dup1" after the failed second insert and asserts the original URL is intact — a conflict must not corrupt or overwrite. Testing the happy path shows the system works; testing that failures leave no trace shows it's safe.

06Go in the Wild

Where this stack runs in production

Every piece of shorty — stdlib routing, middleware discipline, database/sql portability, SQLite durability — maps onto systems serving serious traffic today:

  • bit.ly-class URL shorteners — the canonical architecture is exactly this shape scaled out: a thin HTTP tier doing one indexed key lookup per redirect, fronted by aggressive caching. The interesting engineering lives in code generation (avoiding guessable, colliding IDs) and read scalability — both problems shorty's crypto-random base62 codes anticipate. Services like gotiny and kubectl's own link shortener are Go-built examples.
  • Go's dominance in API tiers — companies running high-traffic APIs on Go's net/http stack include Uber, American Express, PayPal, and Twitch. The pattern is consistent: modest handlers, composed middleware, strict timeouts and body limits at the edge — precisely the habits this project drills.
  • database/sql everywhere — the driver-interface pattern lets one codebase target SQLite locally and Postgres in production; tools like rqlite (distributed SQLite over Raft, itself written in Go) and litestream (SQLite replication) demonstrate how far the humble embedded-database choice scales when paired with disciplined access code.
  • WAL mode in the field — write-ahead logging is why SQLite tolerates concurrent readers during writes; it underpins everything from every browser's internal storage to mobile apps to edge devices. Flipping one PRAGMA switched shorty's concurrency profile too — a one-line decision with production-sized consequences.

Why Go owns the web tier

  1. The standard library is the framework. Routing, middleware, graceful shutdown, and test harnesses ship in the distribution. Teams choose Go for API layers partly because onboarding is "read net/http," not "learn our DSL" — and Go 1.22's router upgrade removed the last common excuse for reaching outside the stdlib on day one.
  2. Goroutines make per-request concurrency free. The server spawns a goroutine per connection; your handlers stay straight-line synchronous code even under thousands of simultaneous requests. Shorty's handlers contain no locks or channels — the only synchronization concern in the whole service lives at the SQLite writer boundary, and one pool setting settles it.
  3. Boring durability wins. A file-backed embedded database with WAL, a bounded-body HTTP tier, and graceful shutdown describe everything from a homelab service to a Fortune-500 edge component. The gap between shorty and production is mostly operational (replication, caching, metrics) — the code shapes you practiced here are the same ones running when the traffic arrives.

The through-line: a four-line route table, two pieces of middleware, parameterized SQL, and a clean shutdown path are not a teaching toy. They are the irreducible core of every HTTP service in Go — learned here in ~280 lines, with a race detector and a real database keeping you honest.
