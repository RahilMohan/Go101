01Stack Evaluation

The decision: pure-Go default, cgo kept available behind a tag

The brief for this project says "cgo + libvips binding" — so the first thing we did honestly was try to build exactly that, and then rejected it as the default stack on this host. The recorded tier decision: pkg-config could not resolve libvips and no C headers are installed, so a cgo build would fail before compiling a single line of Go. Rather than ship a project that cannot compile without a system dependency nobody has, fastthumb ships two things:

  • A pure-Go implementation using the stdlib image package (png, jpeg, image/color) as the default build. Every test passes with CGO_ENABLED=0, no toolchain beyond Go itself, and trivial cross-compilation.
  • A real cgo/libvips binding in solution/vips_binding.go, gated behind the vips build tag (//go:build vips). It demonstrates the entire boundary discipline — vips_init, C.CBytes buffer handoff, runtime.KeepAlive — and its failure mode when libvips is absent is intentional and contained: go build -tags vips fails loudly at 'vips/vips.h' file not found, while the default build never touches it.

This is not a dodge — it is the lesson. The trade between portability (pure Go: any host, any target, one command) and throughput (libvips' shrink-on-load can skip entropy-decoding most JPEG scanlines, often 5–20× faster than decode-then-resize) is precisely the engineering decision every production imaging service makes. We made it explicitly, recorded it before writing code, and built both sides so you can feel what each costs.

What this stack uniquely teaches

  1. The cgo boundary as a protocol, not a syntax. The cost model (~tens to hundreds of nanoseconds per crossing), the pointer rules (no Go pointers retained by C, C owns what C keeps), and the scheduler implications of blocking calls — these decide whether a binding is production-grade or a data-corruption bug waiting for the GC.
  2. Build tags as an architecture tool. A file that provably cannot leak into default builds — verified with go list -f '{{.GoFiles}} {{.IgnoredGoFiles}}' showing [fastthumb.go] [vips_binding.go] — lets optional system dependencies coexist with green CI.
  3. Hostile-input budgeting. A thumbnailer accepts attacker-controlled bytes and allocates proportional to their claims. The DecodeConfig pre-flight check (found by adversarial review, see D2) turned a multi-gigabyte allocation attack into a sub-millisecond rejection — a complete miniature of service-hardening thinking.

02Requirements

Derived directly from fastthumb_test.go — the executable specification. If your implementation passes these tests, it satisfies the requirements.

Functional

  • R1 — Magic-byte format sniffing. Format(src) returns "png" for the full 8-byte PNG signature (\x89PNG\r\n\x1a\n, truncated headers rejected) and "jpeg" for the FF-D8-FF prefix; everything else — empty input, garbage text, GIF magic — wraps ErrBadFormat.
  • R2 — Aspect-preserving fit, never upscaling. Thumb produces the largest rectangle fitting inside the w×h box while preserving aspect ratio; sources smaller than the box keep their original dimensions ({"no-upscale-small-source", 30, 20, 100, 100, 30, 20}).
  • R3 — Same-format round trip. JPEG in → JPEG out, PNG in → PNG out, with correct fitted geometry after re-decoding the output.
  • R4 — Exact-size bilinear Resize. Resize(img, w, h) scales to exactly w×h; a solid-color source stays that color everywhere within a ±2/65535 tolerance per channel.
  • R5 — Dimension validation with sentinels. Non-positive dims (0, -1) and dims above MaxDim (8192) wrap ErrBadDims before any decode; corrupt or nil input wraps ErrBadFormat; error paths return non-nil-output = never.
  • R6 — Translucent-source fidelity. Resampling an NRGBA{255,0,0,128} source must yield exactly NRGBA{255,0,0,128} per pixel — including after a full PNG round trip. Darkening translucent red toward black (the classic premultiply bug) fails this test.
  • R7 — Decompression bombs rejected pre-decode. A small PNG whose IHDR declares dimensions over the MaxSrcDim/pixel-budget limits must be rejected with an ErrBadDims wrap in well under a second — proving the check ran before any bitmap allocation.

Non-functional

  • NF1 — Default build needs nothing but Go. No libvips, no pkg-config, no C toolchain: go build ./... and go test ./... pass with CGO disabled, and cross-compilation stays a one-liner.
  • NF2 — The cgo path is opt-in and contained. With -tags vips on a host lacking libvips, the failure is loud, immediate, and confined to the tagged file; default builds/tests/vet/cross-compilation are provably unaffected (IgnoredGoFiles containment).
  • NF3 — Race-clean. The suite runs green under -race.
  • NF4 — No committed binaries. Every fixture — including the hostile ones — is synthesized inside the test process.

03Architecture Decisions

D1: Sniff by magic bytes, then trust the sniffed decoder

var pngMagic = []byte("\x89PNG\r\n\x1a\n")

case len(src) >= 3 && src[0] == 0xFF && src[1] == 0xD8 && src[2] == 0xFF:
    return "jpeg", nil

fastthumb does not ask callers for a format string and does not rely on filename extensions — it reads bytes. PNG's signature is all 8 magic bytes required; a truncated header fails the length check rather than panicking on a short slice. The JPEG check is deliberately a 3-byte prefix (the SOI marker FF D8 FF), which is enough to route to the right decoder — and if those 3 bytes were all there was, the decode step itself produces an error wrapped with %w, so errors.Is(err, ErrBadFormat) still holds. Two-stage honesty: sniff cheaply, fail precisely. The sniffed name also decides the output encoder, which is how R3's same-format guarantee falls out of structure instead of extra bookkeeping.

D2: The DecodeConfig pre-flight — the decompression-bomb guard

cfg, _, err := image.DecodeConfig(bytes.NewReader(src))
if cfg.Width > MaxSrcDim || cfg.Height > MaxSrcDim ||
    int64(cfg.Width)*int64(cfg.Height) > maxSrcPixels {
    return nil, "", fmt.Errorf(
        "fastthumb: source %dx%d exceeds budget (%d per side, %d pixels): %w",
        cfg.Width, cfg.Height, MaxSrcDim, maxSrcPixels, ErrBadDims)
}

This guard did not exist in the first version. Adversarial review found the hole with a ~300-byte valid 8×8 PNG whose IHDR width/height fields were patched to huge values (CRC fixed): the probe measured 3,433 MiB allocated in 4 ms at 30000×30000, 13.7 GiB and a 4-second stall at 60000×60000, and a >10 s hang at 100000×100000. Why so easy? Go's PNG decoder sizes its buffers from the declared header before validating pixel data — a few hundred attacker-chosen bytes become a gigabytes-scale allocation request. The fix exploits the same fact: parsing only the header via image.DecodeConfig costs almost nothing, so the declared dimensions can be checked against a two-part budget — MaxSrcDim = 20000 per side plus maxSrcPixels = 1 << 26 total (~256 MiB of RGBA). The pixel cap matters because a 20000×4000 source passes each per-side check individually while still declaring 80M pixels. The regression test now rejects crafted bombs in effectively ~0 ms, with a wall-clock assertion (<900 ms) proving the full decode never ran.

D3: The no-upscale rule, in integer arithmetic

func fitDims(w, h, maxW, maxH int) (int, int) {
    if w <= maxW && h <= maxH {
        return w, h                      // fits: keep original size
    }
    if int64(h)*int64(maxW) <= int64(w)*int64(maxH) {
        nh := maxInt(1, h*maxW/w)
        return maxInt(1, maxW), nh       // width-constrained
    }
    nw := maxInt(1, w*maxH/h)
    return nw, maxInt(1, maxH)          // height-constrained
}

"Never upscale" is a product decision with technical teeth: enlarging invents pixels, doubles memory and encode time, and flatters nobody. The first branch encodes it — a source that already fits keeps its size untouched. For the shrink case, comparing the two candidate scales uses integer cross-multiplication (h*maxW vs w*maxH) instead of floating division, eliminating precision surprises at the tie boundary; int64 intermediates make overflow impossible even at MaxDim scale, and maxInt(1, …) guards the floor division against degenerate zero results on odd aspect ratios (an exhaustive ~43k-combination sweep during review confirmed fitDims never exceeds its box). Geometry like this is where thumbnailers quietly go wrong — {"portrait-source-landscape-box", 100, 400, 100, 50, 12, 50} pins the exact expected rounding.

D4: Bilinear over NRGBA — sampling premultiplied, storing straight

dst := image.NewNRGBA(image.Rect(0, 0, w, h))
...
// Interpolate in premultiplied space (correct for alpha compositing
// — translucent edges don't bleed color).
topR := lerp16(c00[0], c10[0], tX)
...
// Un-premultiply exactly once, into straight-alpha storage;
// storing the premultiplied values as-is darkened every
// translucent source toward black.
dst.SetNRGBA(x, y, color.NRGBA{
    R: uint8(straight16(lerp16(topR, botR, tY), a16) >> 8),
    ...
})

This decision exists because of a confirmed fleet finding (F1). The original code sampled colors through color.Color.RGBA() — which legitimately returns premultiplied 16-bit channels — and stored them into an *image.RGBA, whose semantics are straight alpha. For a half-transparent red NRGBA{255,0,0,128}, the premultiplied R≈128 got stored as straight R=128: every translucent source visibly darkened toward black, and the PNG round trip faithfully preserved the corruption. Opaque images were unaffected — which is why the original suite stayed green while the bug shipped. The fix has two halves, and both matter. Sampling stays premultiplied: interpolating straight-alpha RGB across a transparent/opaque edge bleeds the transparent pixel's meaningless color into the result; premultiplied interpolation is the mathematically correct compositing operation. Storage becomes NRGBA: the interpolated values are un-premultiplied exactly once (straight16(premul, a), guarding a==0) into straight-alpha storage, so the same bytes are never reinterpreted as premultiplied again. The regression test demands bit-exact fidelity: NRGBA{255,0,0,128} in, NRGBA{255,0,0,128} out, round trip included.

04Concept Walkthroughs

Cgo call overhead — the ~nanoseconds-to-hundreds scale

rc := C.fastthumb_thumbnail((*C.uchar)(csrc), C.size_t(len(src)),
    C.int(w), C.int(h),
    (*C.uchar)(unsafe.Pointer(&out[0])), C.size_t(cap(out)), &outLen)

Every Go→C crossing costs on the order of tens to a couple hundred nanoseconds: the runtime must transition off the goroutine's managed stack, save registers, and switch to the C ABI (and the reverse on return). Whether that price matters depends entirely on batch size. One call per image — milliseconds of work amortizing ~100 ns — is free. One call per pixel — 262k crossings for a 512×512 thumbnail — turns the trampoline into your profiler's hottest frame. This is why thumbVIPS is architected as exactly ONE call: input buffer in, output buffer out, the whole decode-shrink-encode pipeline living inside libvips. The transferable rule: cross the boundary in coarse grains, and let the C library own the loop whenever the operation allows it.

Pointer-passing rules — no Go pointers into C memory

// Pointer-passing rule #1: C memory must be allocated/owned by C.
csrc := C.CBytes(src)         // COPY into C-allocated memory
defer C.free(csrc)

// Rule #2 (inverse): pass a *Go* pointer ONLY if C does not
// retain it after returning.
rc := C.fastthumb_thumbnail(..., (*C.uchar)(unsafe.Pointer(&out[0])), ...)
runtime.KeepAlive(out)        // pin until C is done with it

The garbage collector may move or reclaim Go memory at any time; C code has zero visibility into that. Hence cgo's contract, enforced by runtime checks that crash offending programs loudly. Direction one: handing C a pointer into the Go heap is legal only if the memory contains no other Go pointers and C finishes with it before the call returns — safe here because libvips writes into out synchronously. Direction two: anything C might retain past the call must live in C-heap memory, so the input bytes are copied via C.CBytes and freed with a matching defer C.free — the same discipline applies to the C.CString passed to vips_init in the tagged init. Finally, runtime.KeepAlive(out) pins the staging buffer until after the last C use: once the only reference has been laundered through unsafe.Pointer, the compiler can no longer prove liveness, and without the pin the GC would be entitled to collect the buffer mid-call. These four moves — copy-in, lend-out, free-everything, KeepAlive — are the entire safety protocol of a production cgo binding.

Build-tag mechanics — verified containment

//go:build vips

$ go list -f '{{.GoFiles}} {{.IgnoredGoFiles}}' ./solution
[fastthumb.go] [vips_binding.go]

A single comment line excludes vips_binding.go from every build that lacks -tags vips. The proof is mechanical, not hopeful: go list reports the file under IgnoredGoFiles, so the compiler never sees it in default builds, tests, vet runs, or cross-compilations — a missing system library cannot break CI that never asks for it. Flip the tag on a libvips-less host and the failure is equally loud and equally local: fatal error: 'vips/vips.h' file not found. Note what the mechanism buys architecturally: both files declare package fastthumb, so the tagged and untagged worlds present the same package API and tests exercise whichever implementation is active. Build tags are usually taught as platform plumbing (linux, darwin); this project shows their better role as a dependency-isolation device — optional capability behind an explicit, greppable switch.

Cross-compilation — the CC_FOR_TARGET tax

$ GOOS=windows GOARCH=amd64 go build ./...            # pure Go: done
$ CC_FOR_TARGET=x86_64-w64-mingw32-gcc \
  GOOS=windows GOARCH=amd64 CGO_ENABLED=1 \
  go build -tags vips ./...                            # cgo: toolchain needed

Pure Go cross-compiles trivially — set GOOS/GOARCH, done; the compiler ships with every target baked in, which is one of Go's genuine superpowers. The moment import "C" enters the build, you need a C cross-toolchain for each destination: a mingw-gcc for Windows targets, an osxcross wrapper plus SDK for macOS, matching sysroots and libc choices (musl vs glibc) for Linux, static-linking flags multiplying on top. Each target is another matrix cell someone must provision and keep working. This asymmetry — not raw performance — is often what decides the portability-vs-throughput question in production, and it is why fastthumb's default is pure Go: ship portable by default, pay the toolchain tax only where the performance genuinely demands it, and gate that payment behind a build tag so the portable path is never hostage to it.

05Testing Strategy

All fixtures synthesized in-test — including the weapons

type solidImage struct { w, h int; c color.RGBA }
func (s *solidImage) At(x, y int) color.Color { return s.c }

func encodePNG(t *testing.T, img image.Image) []byte { ... }

No committed binaries exist anywhere in the project. Valid inputs come from a tiny solidImage helper encoded through the real png.Encode / jpeg.Encode, which makes every test self-contained and every dimension pair a one-line table row. Crucially, the hostile fixtures follow the same rule: bombPNG builds a genuine 8×8 PNG, patches its IHDR width/height fields with binary.BigEndian.PutUint32, recomputes the CRC32 with hash/crc32.ChecksumIEEE, and hands the result to Thumb. The attack artifact is 300 bytes of test code — reproducible forever, unlike a checked-in binary nobody dares regenerate.

The bomb regression: rejection measured in ~0 ms

start := time.Now()
_, err := Thumb(bomb, 64, 64)
elapsed := time.Since(start)
if !errorsIs(err, ErrBadDims) { ... }
if elapsed > 900*time.Millisecond {
    t.Fatalf("bomb took %v to reject — full decode ran before the header check", elapsed)
}

Finding A1's fix is pinned by a test that asserts two independent properties. First, the error identity: the crafted-IHDR bomb (tested at both MaxSrcDim+10000 per side and the sneakier 20000×4000, which passes per-side checks but blows the pixel budget) must wrap ErrBadDims. Second, the timing: a wall-clock bound generous enough to be stable on loaded CI machines, tight enough to catch a regression that lets png.Decode allocate gigabytes — because the original bug wasn't a wrong answer, it was a 13.7 GiB pause before the wrong answer. Timing assertions are rare in unit tests and justified exactly when latency IS the behavior being specified.

The translucency regression: NRGBA{255,0,0,128} end to end

nc := color.NRGBAModel.Convert(resized.At(x, y)).(color.NRGBA)
if nc != (color.NRGBA{R: 255, G: 0, B: 0, A: 128}) { ... }

Finding F1 gets an equally sharp pin. The subtlety is in the assertion itself: .RGBA() legitimately reports premultiplied channels, so checking through it could mask a storage bug. The test converts through NRGBAModel to read back exactly what is stored — demanding bit-exact NRGBA{255,0,0,128} at every output pixel of a resized half-transparent-red field, then repeating the check after a full encode→decode PNG round trip. Any relapse into storing premultiplied values as straight (red decaying to R=128) fails instantly. Alongside it, the suite covers the rest of the contract surface: the format-sniffing table (empty, garbage, truncated PNG header, GIF-magic rejection), nine-row aspect-fit geometry including the no-upscale cases, solid-color invariance within ±2/65535, JPEG→JPEG retention, all six error-path corners, and sentinel reachability via errors.Is.

Race-clean and convention-clean

The note: the whole suite runs under go test -race ./solution/... per repo convention, and root stubs stay failing-by-design — the executable specification lives in the unimplemented stubs until someone writes the real thing.

Even though fastthumb is single-goroutine, the race detector earns its keep by validating the memory discipline around the cgo-shaped code paths and keeping the project uniform with the concurrency-heavy siblings in this curriculum. The adversarial fleet's abuse probes (nil/empty/magic-only/truncated inputs under watchdogs with MemStats deltas) all came back clean post-fix: prompt errors wrapping the right sentinel, zero allocation spikes, no panics, no out-of-bounds reads — the hostile-input surface behaves exactly as NF-level promises require.

06Go in the Wild

Where this stack runs in production

The cgo boundary you met here — and the decision about whether to cross it at all — shapes large parts of the Go ecosystem:

  • libvips bindings: govips and bimg — the production answer to exactly fastthumb's problem. Both wrap libvips for high-throughput image services (bimg famously powered resize infrastructure serving billions of images); both carry the same machinery you just wrote — C.CBytes copies in, staged or C-owned buffers out, KeepAlive pins — and both inherit the same cross-compilation tax. Teams choose them when JPEG shrink-on-load throughput justifies a C dependency per deploy target.
  • SQLite drivers: mattn/go-sqlite3 vs modernc.org/sqlite — the ecosystem's clearest pure-Go-vs-cgo fork of the same tradeoff. mattn's driver wraps the C amalgamation (battle-tested, fastest, needs a C toolchain everywhere it deploys); modernc transpiled the whole engine to Go (slower, but CGO_ENABLED=0 everywhere). Whole companies standardize on one side purely for build-pipeline reasons — the portability half of this project's tier decision, at industrial scale.
  • Docker's runc and container runtimes — heavy cgo consumers for namespaces, cgroups, and system calls via C libraries where stable low-level interfaces matter, while carefully keeping the hot paths native. Their build docs spend more words on cross-toolchains than on Go itself — the CC_FOR_TARGET story, lived daily.
  • The counter-example: golang/freetype — font rasterization implemented in pure Go, proving that imaging-grade pixel work is achievable without leaving the language when throughput targets allow. fastthumb's pure-Go default sits in this tradition: the stdlib image stack powers plenty of real thumbnail pipelines that never compiled a line of C.

Why the boundary stays worth learning

  1. Some capabilities only exist on the far side. Hardware codecs, decades-old battle-tested C engines (libvips, sqlite, openssl), platform APIs without Go wrappers — sooner or later a Go service needs one, and the difference between a working binding and a corrupted heap is precisely the pointer-passing protocol this project drills.
  2. The cost model prevents cargo-culting. Knowing that a crossing costs ~100 ns tells you immediately that per-image batching is free and per-pixel calls are ruinous — the same arithmetic that made "one call per thumbnail" the obvious architecture here decides real integration designs.
  3. The opt-in pattern scales to whole platforms. Build tags isolating an expensive capability behind an explicit switch is how ecosystems offer both worlds without taxing everyone — the same shape as -tags variants, driver forks, and pure-Go fallbacks you'll meet throughout production Go.

The through-line: fastthumb teaches both halves of an honest engineering decision — what the C boundary costs (call overhead, pointer discipline, toolchains) and what the pure-Go path delivers (portability, simplicity, adequate speed) — by building both and letting the build tag draw the line.
