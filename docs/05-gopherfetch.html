01Stack Evaluation

The stack: stdlib concurrency, nothing else

gopherfetch is built from four load-bearing stdlib packages — net/http, context, sync, and time — plus errors in a supporting role. No errgroup, no worker-pool library, no crawling framework, no go.sum. Projects 01–04 proved parsing, persistence, and API design don't need dependencies; project 05 makes the stakes higher, because concurrency is where hand-rolled code is most tempting to replace with a library — and where replacing it costs you the most understanding.

Rejected alternatives

  • golang.org/x/sync/errgroup already at this stage — errgroup is a genuinely good tool, and this curriculum isn't against it. But it compresses exactly the mechanics this project exists to teach: wg.Add/Done pairing, dispatch loops over a jobs channel, and join-before-read discipline become one g.Go(func() ...) call each. errgroup gets taught properly in project 12 — after you've built what it abstracts, so you know what you're trading away when you reach for it.
  • Third-party worker-pool libraries — packages offering pool.Submit(fn) with tunable sizing would hide the WaitGroup mechanics behind an API, leaving you unable to answer "what happens to queued work when the context dies?" A pool library is a fine production choice precisely because its failure modes are the ones you learn to reason about here.
  • colly / crawling frameworks — Go's most popular scraper would turn this into configuration: selectors, depth limits, politeness settings. But then the lesson becomes "read colly's docs" instead of "understand why a fixed pool of workers draining an index channel produces ordered, bounded, cancellable output." The checking logic here is ~100 lines; owning them is the point.

What this stack uniquely teaches

  1. Worker-pool anatomy from first principles. Every concurrent system you'll ever debug reduces to the same skeleton: a work source, N executors, a way to join, and a cancellation path. Building that skeleton by hand — dispatcher, workers, close(jobs), wg.Wait() — makes the pattern permanent in a way no library call can.
  2. Deterministic result ordering as a testable property. Concurrent output feels inherently unordered until you see the trick: write each result at the index of its input, and order falls out for free. More importantly, the suite proves the property under adversarial latency, turning "should be ordered" from a hope into a regression-tested invariant.
  3. Cancellation as a first-class return value. When the caller's context dies mid-run, gopherfetch doesn't panic, block, or drop URLs silently — it returns a complete result set where abandoned slots carry ctx.Err(). Partial-success semantics under cancellation are a design skill, not an accident.

02Requirements

Derived directly from gopherfetch_test.go — the executable specification. If your implementation passes these tests (including under -race -count=3), it satisfies the requirements.

Functional

  • R1 — Concurrency stays inside the pool bound. Checking 50 URLs with 5 workers never exceeds 5 simultaneous in-flight requests — but reaches at least 2, so a purely sequential implementation fails too.
  • R2 — Results preserve input order. With a server engineered so later URLs finish earlier (reverse-scaled sleeps), results[i].URL == urls[i] for every i despite wildly shuffled completion order.
  • R3 — Cancellation abandons the rest but returns everything. When the context is canceled after some checks complete, Check returns all n results: finished ones carry statuses, unsent ones wrap context.Canceled, and both groups are non-empty.
  • R4 — Per-request timeout fires and reports cleanly. A handler blocked forever with a 50ms timeout yields one result whose error satisfies errors.Is(err, context.DeadlineExceeded), with Status == 0, in roughly the timeout duration rather than hanging.
  • R5 — Error taxonomy separates transport failures from statuses. Connection refused gives non-nil Err with Status == 0; an HTTP 404 gives Status == 404 with nil Err (a status is data, not an error).
  • R6 — Redirect chains cap at three hops. A server offering four hops is followed only through three; the final reported status is the third hop's 302, and the destination URL is provably never requested.
  • R7 — Rate limiting spaces request starts. Six requests at a 30ms interval take at least ~150ms total — an unthrottled implementation finishes in milliseconds and fails the bound.
  • R8 — Invalid worker count errors per-result, not by panicking. NewChecker(0 or negative, …)'s Check returns one errored Result per URL (wrapping ErrNoWorkers) instead of crashing.
  • R9 — Empty input returns empty results. Check(ctx, nil) yields a zero-length slice with no goroutines spawned.
  • R10 — No goroutine leaks. After a 20-URL run plus CloseIdleConnections() and a settle delay, runtime.NumGoroutine() is back within 2 of the baseline.

Non-functional

  • NF1 — Bounded resources. Goroutines scale with the configured worker count, never with the URL list length; pooled idle connections are releasable on demand so long-lived processes can quiesce.
  • NF2 — Deterministic output. Result ordering is a function of input ordering alone — identical inputs produce byte-identical result sequences on every run, every platform.
  • NF3 — Flake-free under load. The whole suite must pass repeatedly (-count=3) with the race detector (-race) enabled on a loaded machine; timing assertions are backstops, not primary proofs.
  • NF4 — Graceful partial failure. Cancellation is surfaced as data (Result.Err wrapping ctx.Err()), letting callers distinguish "checked and failed" from "never checked."

03Architecture Decisions

D1: Dispatcher/worker split over a jobs channel of indices

jobs := make(chan int)
var wg sync.WaitGroup
wg.Add(min(c.workers, n))
for range min(c.workers, n) {
    go func() {
        defer wg.Done()
        for idx := range jobs {
            results[idx] = c.doOne(ctx, urls[idx])
        }
    }()
}

The design separates two concerns that naive implementations entangle. The dispatcher (the calling goroutine) owns scheduling: it walks indices in order, respects the rate ticker and the context, and pushes work into an unbuffered channel — which means dispatch naturally blocks when all workers are busy, giving you the pool bound for free. The workers own execution only: pull an index, check the URL, write the result, repeat. Because min(workers, n) workers start, a two-URL run doesn't spin up eight idle goroutines. Note what the unbuffered channel buys: there is no queue whose length needs bounding, because the channel is the bound — at most one undelivered job exists at any instant.

D2: An indexed results slice beats a results channel

results := make([]Result, len(urls))
...
results[idx] = c.doOne(ctx, urls[idx])   // each worker owns disjoint indices

The obvious alternative — workers send Result values down a second channel and someone reassembles them — creates three new problems: a collector goroutine (more lifecycle), a map or sort step to restore input order (the very nondeterminism we're avoiding), and a synchronization question about when reading is safe. Writing directly at idx eliminates all three at once. It is race-free because each index is handed to exactly one worker — the slices' elements have disjoint owners, so there is no shared mutable state and no mutex. And the read-after-write safety comes from a single well-defined edge: wg.Wait() establishes a happens-before relationship between every worker's final write and the dispatcher's subsequent read of the whole slice. One primitive, zero locks, perfect order.

D3: Filled-marker repair on cancellation

filled := make([]bool, n)

dispatch:
    for idx := range n {
        select {
        case <-ctx.Done():
            break dispatch
        case jobs <- idx:
            filled[idx] = true
        }
    }
close(jobs)  // workers drain what was sent, then exit
wg.Wait()

if err := ctx.Err(); err != nil {
    for i := range results {
        if !filled[i] {  // never scheduled, so never checked
            results[i] = Result{URL: urls[i], Err: err}
        }
    }
}
return results

When the context dies, some slots were checked (real data), and some were never dispatched (still zero values). How do you tell them apart? Scanning for "looks like a zero Result" is a trap: {URL: "", Status: 0, Err: nil} could collide with legitimate outcomes, and any heuristic based on Status or Duration is guessing. The dispatcher instead records filled[i] = true at the moment index i is handed to a worker — written only by the dispatcher itself, so it needs no synchronization. After wg.Wait(), every unfilled slot is repaired with Err: ctx.Err(). The contract that emerges is strong: Check always returns len(urls) results, canceled or not, which is exactly what makes the CLI's per-line reporting possible.

D4: Shared Transport sized to the pool

client: &http.Client{
    Transport: &http.Transport{
        // Idle-connection pooling is per host; sizing it to the
        // pool avoids churn when every worker hits the same host.
        MaxIdleConns:        workers,
        MaxIdleConnsPerHost: workers,
    },
}

All workers share one client, and therefore one connection pool — the default Transport keeps only 2 idle connections per host, so eight workers hammering one server would constantly close and re-open TCP connections (and TLS handshakes) that should have been reused. Setting both idle caps to workers lets every worker keep its warm connection alive. This is also why CloseIdleConnections() exists on Checker: pooled keep-alive connections each hold a reader goroutine, and the leak test can't get a clean baseline unless the pool can be deliberately drained — a real concern for long-lived processes too, not just tests.

D5: HEAD requests and the redirect cap

req, err := http.NewRequestWithContext(reqCtx, http.MethodHead, url, nil)
...
CheckRedirect: func(_ *http.Request, via []*http.Request) error {
    if len(via) >= maxRedirects {
        return http.ErrUseLastResponse  // report the 3xx instead of following hop four
    }
    return nil
},

A link checker asks "does this URL respond OK?" — it doesn't need the body, so HEAD avoids transferring bytes entirely. Redirects need a policy because real web links can chain indefinitely: returning http.ErrUseLastResponse from CheckRedirect stops the chase and hands back the 3xx response itself, so the caller sees Status: 302 rather than whatever lies at the end of the chain (a login page, a tracking pixel, a loop). Three hops covers ordinary redirects while refusing to be weaponized into an infinite crawl. Crucially, the request carries reqCtx — derived from the caller's context — so cancellation and the optional per-request timeout both reach the transport layer, where they can actually interrupt in-flight network I/O.

D6: Library core, thin command shell

projects/05-gopherfetch/
├── gopherfetch.go            # package gopherfetch — stubs you implement
├── gopherfetch_test.go       # the executable spec
└── solution/
    ├── gopherfetch.go        # package solution — Checker, run engine, doOne
    └── cmd/gopherfetch/main.go  # flags, signal handling, report lines

The library knows nothing about terminals; main knows nothing about channels. The CLI adds flags (-c workers, -timeout, -rate), wires signal.NotifyContext so Ctrl-C cancels the run mid-flight, and renders the taxonomy:

OK   200  12ms  https://x
SKIP 0    0s    https://y  context canceled
FAIL 0    3ms   https://z  Get "https://z": connection refused

The SKIP/FAIL split is deliberate and worth internalizing: only results wrapping context.Canceled print as SKIP and are excluded from the "checked" count — they were never really checked. Everything else with an error prints FAIL, including a per-request timeout (DeadlineExceeded): if the deadline belongs to this URL's request, the check genuinely ran and genuinely failed. That distinction — caller gave up vs. this URL failed — is exactly the information errors.Is over the wrapped chain provides.

04Concept Walkthroughs

Goroutine lifecycle and leaks — measuring with NumGoroutine

before := runtime.NumGoroutine()
c := NewChecker(8, 0)
c.Check(context.Background(), urls)
c.CloseIdleConnections()
time.Sleep(200 * time.Millisecond)  // settle: let closed conns' goroutines exit

if delta := runtime.NumGoroutine() - before; delta > 2 {
    t.Errorf("goroutines grew by %d after Check, want <= 2 (leaked workers or conns)", delta)
}

A leaked goroutine is the concurrency analog of a memory leak: invisible in functional tests, fatal at scale. The classic causes are all here to be learned — a worker blocked forever on a channel nobody closes, a WaitGroup counter that never reaches zero, or (subtler) pooled HTTP connections whose background read loops outlive the requests that made them. runtime.NumGoroutine() turns leakage into a number you can assert on: snapshot before, run, drain the connection pool with CloseIdleConnections, give the runtime a moment to reap exited goroutines, and compare. The tolerance (≤2) acknowledges that runtimes and test infrastructure spawn goroutines too — the assertion catches trend, not exact counts, which is the only honest way to test this. The habit transfers directly to production: any server that grows goroutine count monotonically under load has a bug shaped like a missing close(jobs).

sync.WaitGroup semantics — Add-before-go, defer Done

wg.Add(min(c.workers, n))          // before any goroutine starts
for range min(c.workers, n) {
    go func() {
        defer wg.Done()         // first statement, not last
        for idx := range jobs { ... }
    }()
}
...
wg.Wait()                       // join; happens-before edge for reads of results

The WaitGroup is Go's join barrier, and its rules are stricter than they look. Add must happen before the go statement: if you incremented inside the new goroutine, Wait could observe the counter at zero before the goroutine even ran, ending the wait prematurely. Done belongs in a defer so panics inside the loop still decrement the counter — otherwise one panicking worker deadlocks every future Wait. And Wait is more than bookkeeping: it synchronizes memory. Everything a worker wrote before Done — including its slot in results — is guaranteed visible to whoever returns from Wait. That guarantee is why D2's lock-free design is correct, not lucky.

The context tree — parent cancel plus per-request timeout

reqCtx := ctx
if c.timeout > 0 {
    var cancel context.CancelFunc
    reqCtx, cancel = context.WithTimeout(ctx, c.timeout)
    defer cancel()
}
req, err := http.NewRequestWithContext(reqCtx, http.MethodHead, url, nil)

Contexts form a tree, and cancellation flows strictly downward. Here each request derives its own child of the caller's context: the child fires when either the parent is canceled (Ctrl-C, upstream deadline) or its own 50ms elapses, whichever comes first. Two consequences matter. First, the per-request timer cannot outlive its purpose — the deferred cancel() releases the timer the moment the request finishes, so a fast run on ten thousand URLs never holds ten thousand live timers. Second, error identity tells you which trigger fired: errors.Is(err, context.Canceled) means the caller aborted; errors.Is(err, context.DeadlineExceeded) means this specific request timed out. The CLI exploits exactly that split when choosing SKIP versus FAIL. Passing the context into NewRequestWithContext is what connects the tree to the network: the transport watches the context and tears the request down mid- flight when it fires — no polling, no goroutine-per-check watchdog required.

time.Ticker rate limiting — pacing the dispatch loop

var tick <-chan time.Time
if interval > 0 {
    ticker := time.NewTicker(interval)
    defer ticker.Stop()
    tick = ticker.C
}

dispatch:
    for idx := range n {
        if tick != nil && idx > 0 {
            select {
            case <-ctx.Done():
                break dispatch
            case <-tick:
            }
        }
        ...

Rate limiting lives in the dispatcher, not the workers — capping request starts at one per interval automatically caps the whole system, because workers can't invent work. The shape is a select over the tick channel and ctx.Done(): wait for either permission to proceed or an order to stop, never just one. Skipping the Done arm would make cancellation stall for up to one interval per remaining URL. The first request skips the wait (idx > 0), so latency isn't paid unnecessarily. defer ticker.Stop() releases the timer resource — a running Ticker holds a runtime timer that would otherwise linger for the process lifetime. Compare this to the naive time.Sleep(interval) between sends: a sleep can't be interrupted by cancellation, whereas the select wakes instantly on either event. This ticker-select is also, verbatim, the skeleton of token-bucket limiters throughout production Go code.

Writing flake-free concurrency tests

The rule: assert on counts and identities that are true by construction; use timing only as a coarse backstop with huge margins; never assert that the scheduler behaved nicely on your machine today.

Concurrency tests fail spuriously when they encode assumptions about timing. The suite survives loaded CI machines and -race overhead through several techniques. The atomic max-tracker records peak concurrency without locks or lost updates:

type concurrencyTracker struct {
    inFlight int64
    maxSeen  int64
}

cur := atomic.AddInt64(&t.inFlight, 1)
for {
    old := atomic.LoadInt64(&t.maxSeen)
    if cur <= old || atomic.CompareAndSwapInt64(&t.maxSeen, old, cur) {
        break
    }
}

The CAS loop is the standard lock-free "max" update: read the current max, and swap in yours only if nobody else raised it meanwhile — retrying on contention. A plain non-atomic if cur > max { max = cur } is itself a data race, which -race would flag inside the very test meant to prove thread safety. Then the assertions are two-sided but tolerant: maxSeen > 5 fails (bound violated — a hard property), maxSeen < 2 fails (never parallelized), and anything between passes. Timing bounds appear only as backstops with enormous headroom: the cancellation test allows 250ms where the serial worst case is 200ms and the expected case is ~30ms — loose enough to survive any scheduler, tight enough to catch an implementation that ignores the context entirely. Wherever possible, correctness is proven by counting events, not by clock-watching.

05Testing Strategy

Pool-bound proof via an in-flight counter

TestCheckRespectsWorkerPoolBound wraps a normal httptest handler in a tracker that increments on entry and decrements on exit, recording the high-water mark. Fifty URLs against five workers, each request widened to 10ms so overlaps are statistically certain. The beauty is that the assertion tests the implementation's promise, not the test's patience: an unbounded go checkURL(u)-per-URL implementation spikes toward 50 in-flight requests and fails immediately; a sequential loop fails the maxSeen >= 2 floor; only a genuine pool lands in the legal window. The counter is built from atomics precisely so the measuring instrument cannot introduce the race it's hunting.

Determinism under shuffled completion order

// Later URLs finish earlier: a completion-order bug would shuffle
// results even if scheduling were otherwise correct.
time.Sleep(time.Duration(n-idx) * 5 * time.Millisecond)

TestCheckPreservesInputOrder engineers the worst case on purpose: URL 11 finishes in 5ms while URL 0 takes 60ms — completion order is almost the reverse of input order. If results arrived in completion sequence, the final slice would visibly scramble. Asserting results[i].URL == urls[i] across all twelve slots converts "output should probably match input" from folklore into a pinned contract. Any implementation that appends to a shared slice from workers (racy and disordered), or collects through a channel without reassembly, fails this test loudly.

Cancellation produces honest partials

TestCheckContextCancellationAbandonsRest choreographs a realistic abort: the server signals each completed response through a channel, and a goroutine waits for the first success, pauses 10ms, then cancels the context. The assertions then demand the full contract at once: all 20 results exist, at least one succeeded (ok > 0), at least one wraps context.Canceled (canceled > 0), nothing else appears, and total elapsed time proves work was actually abandoned rather than politely finished. The elapsed check is explicitly labeled a backstop in the test comments — the ok/canceled partition is the primary proof; 250ms of headroom exists only to catch a context-ignoring implementation without flaking on a slow machine.

Error taxonomy as executable cases

TestErrorTaxonomy packs three servers into one table of reality: a pre-closed port (connection refused → Err != nil, Status == 0), a 404 endpoint (Status == 404, Err == nil — a status is data), and a four-hop redirect chain where an atomic counter proves the fourth hop is never requested and the third hop's 302 is what gets reported. Together with TestPerRequestTimeout (blocked-forever handler, 50ms budget, DeadlineExceeded asserted through errors.Is, prompt elapsed time) and TestInvalidWorkerCountFailsAtCheckTime (misconfiguration surfaces as per-result errors, not a panic), the taxonomy — refused / status / redirected / timed out / misconfigured — is fully enumerated. There is no outcome the CLI can receive that some test hasn't characterized.

The -count=3 -race flake protocol

go test -race -count=3 ./projects/05-gopherfetch/...

Concurrency bugs are probabilistic, so proving their absence requires repetition: -count=3 runs the suite three times in one process, multiplying exposure to interleaving luck, and -race instruments every memory access to catch races that didn't happen to corrupt anything this run. A test suite that passes once but flakes on repetition is worse than one that fails consistently — it trains people to rerun instead of investigate. Every timing-sensitive assertion in this suite was designed under this protocol: primary assertions count events (results, statuses, hits), timing appears only as generously-bounded backstops, and the measurement tools themselves (atomic CAS trackers) are race-clean. Run the protocol before declaring victory; it is the difference between "passed on my laptop" and "correct."

06Go in the Wild

Where this stack runs in production

Fixed worker pools, context-driven cancellation, and shared HTTP clients are the working skeleton of much of the internet's tooling — a lot of it written in Go:

  • Prometheus blackbox_exporter — probes endpoints (HTTP, TCP, ICMP) on a schedule and exports up/down metrics; each probe is a bounded, timeout-carrying HTTP request derived from a scheduling context, i.e. exactly a doOne call with better dashboards.
  • Kubernetes controllers — every controller runs a reconcile loop that lists desired state, fans out work through bounded worker pools, and honors ctx.Done() on shutdown. The dispatcher/worker/join structure you built here is the structure of controller-runtime's worker queues; deployment rollouts are cancellation-aware fan-outs.
  • Hugo's build pipeline — the static site generator parallelizes page rendering across a fixed pool sized to CPU count, joining before write-out — the same WaitGroup discipline, applied to thousands of Markdown files.
  • godoc and Go's own tooling — the documentation server and pkg.go.dev crawl, fetch, and render package sources concurrently with shared transports and polite rate limits; link extraction and verification has been part of Go's toolchain story since the language's earliest days.

Why Go owns cloud infrastructure tooling

  1. Goroutines make the concurrency model cheap. A worker pool of hundreds of goroutines costs kilobytes of stack — not OS threads. That's why a single Go process comfortably probes thousands of endpoints (blackbox_exporter) or reconciles tens of thousands of objects (kube-controller-manager): the unit of concurrency is nearly free, so bounding it is a design choice, not a survival tactic.
  2. context made cancellation universal. Before context became the convention, every library invented its own shutdown story. Now a kubectl delete, a pod eviction, and an HTTP request timeout all speak the same interface — which is why the pattern of deriving child contexts with their own deadlines composes across ecosystem boundaries. Learning the tree here means reading any production Go call chain and knowing exactly what dies when.
  3. Reconcile loops are this project, renamed. Desired state = your URL list. Workers = your pool. Results slice = observed status. Cancellation = graceful shutdown, with partial progress preserved. Kubernetes won partly because its control loops are boring, legible instances of the pattern you just implemented — when you read controller code someday, it will look familiar in the best way.

The through-line: a jobs channel, a fixed set of workers, a WaitGroup join, and a context threading through everything is not a teaching toy. It's the load-bearing pattern of the systems running the cloud — exercised here in under 200 lines, with the race detector keeping you honest.
