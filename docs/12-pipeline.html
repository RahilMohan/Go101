01Stack Evaluation

The stack: generics + errgroup + channels

pipeline is built from three load-bearing pieces: Go's type parameters (for type-safe result retrieval), golang.org/x/sync/errgroup (for structured concurrency), and plain unbuffered channels (for dispatch and completion handoff). One honest note up front: unlike every project so far, this one carries a single external dependency — errgroup. It earns its place because it is barely a library at all: about two hundred lines of sync.WaitGroup plus a derived context, i.e., the exact glue you'd write yourself, battle-tested. Everything else — the DAG scheduler, the worker pool, cycle detection, cancellation semantics — is yours.

Rejected alternatives

  • Actor frameworks (proto.actor, ergo) — mailbox-per-task actor models can express DAG execution, but they invert the pedagogy: instead of learning how scheduling, backpressure, and cancellation actually work, you learn one framework's supervision tree. They also hide the exact bug this project exists to teach — the blocked-dispatcher deadlock — behind framework internals. After building pipeline, you can read an actor framework's docs and know what its mailboxes are doing for you.
  • sync.WaitGroup-only fan-out/fan-in — spawning one goroutine per task and waiting on all of them is the naive first draft. It cannot bound concurrency (a 10,000-task graph means 10,000 live goroutines and their stacks), it has no story for early failure (one task failing still runs all siblings to completion), and wiring cancellation through it means bolting channels back on anyway. WaitGroup remains the right tool inside each layer — here, it isn't used at all because errgroup subsumes it.
  • Topological-sort-then-run (level-by-level) — computing full topological levels before running anything is simpler, but it serializes independent work: a level finishes entirely before the next starts, so one slow straggler idles the whole pool. Kahn's algorithm executed incrementally (in-degree countdown as tasks complete) keeps the ready queue flowing continuously — which is what pipeline implements.
  • Workflow engines (Temporal, Cadence as dependencies) — the production answer for durable workflows, and wildly overkill: they bring persistence, retries, versioning, and cross-process durability. This project builds the in-memory core those systems wrap, so their abstractions become legible rather than magical.

What this stack uniquely teaches

  1. DAG execution as an ownership problem. The hardest concurrency bugs come from shared mutable state touched by many goroutines. pipeline's answer — one dispatcher goroutine owns all scheduling state (in-degrees, ready queue, results map) while workers stay stateless — eliminates locks not by cleverness but by architecture. Internalizing "single-owner state beats shared-state-plus-mutex" changes how you design every concurrent system afterward.
  2. errgroup as the shape of structured concurrency. Any goroutine returning an error cancels everyone; Wait joins everything; the caller gets one error. You'll implement dispatcher, workers, and cancellation propagation against that contract, and learn where its edges are (it does not recover panics — more below).
  3. Generics at the API boundary. Tasks produce any; consumers want typed values. Get[T] shows the idiomatic reconciliation — store untyped, retrieve typed, fail soft — and why (T, bool) beats both reflection and panic-on-mismatch.

02Requirements

Derived directly from pipeline_test.go — the executable specification. If your implementation passes these tests under go test -race, it satisfies the requirements.

Functional

  • R1 — Linear chains execute strictly in dependency order. A task whose dependency hasn't published its result yet must observe that absence and fail — the tests plant shared-state probes so "ran too early" is detected, not assumed.
  • R2 — Diamond fan-out/fan-in works. Two parallel children of one parent, joined by a dependent that sees both results, complete correctly.
  • R3 — Wide graphs execute in parallel. Fifty independent tasks run with order-independent results; a stress test of 200 sleeping tasks observes maximum concurrency ≥ 2 via atomic CAS bookkeeping, proving genuine parallelism.
  • R4 — Graph construction validates inputs. Duplicate IDs wrap ErrDuplicate (checkable with errors.Is); empty IDs, nil tasks, and nil Run funcs are rejected with errors naming the offender.
  • R5 — Invalid graphs fail before running. Unknown dependencies wrap ErrUnknownDep; cycles — including self-cycles — wrap ErrCycle naming every chain member. Both surface identically from Validate and from Run.
  • R6 — Validation output is deterministic and injection-safe. With multiple invalid entries, the lowest-ID offender is reported every run (map iteration order must not leak into messages); hostile IDs containing newlines appear strconv.Quoted so forged log lines can't be smuggled into error text.
  • R7 — First failure cancels siblings and wraps cleanly. A task returning an error causes in-flight siblings to stop via context, Run returns within bounded time, the error wraps the original sentinel (errors.Is) and names the failing task, and Results is nil.
  • R8 — Caller cancellation propagates in bounded time. Cancelling the caller's context mid-run makes Run return context.Canceled well under a 5-second cap, with no typed results retrievable afterwards.
  • R9 — Panicking tasks don't kill the process. A task body that panics surfaces as a wrapped error naming the task and the panic value; dependents never run; Run returns normally.
  • R10 — Typed result retrieval is safe on every path. Get[int]/Get[string] succeed on matches; wrong type, missing ID, and nil *Results all yield the zero value and false — never a panic.
  • R11 — Empty graphs succeed. Zero tasks produce non-nil, empty Results without spawning workers.
  • R12 — Consumers only start after deps publish. A consumer gated behind a deliberately blocked dependency must not run during the blockage (asserted by observing Run hasn't returned after 100 ms), then completes once released.

Non-functional

  • NF1 — Race-clean under the detector. All suites pass go test -race: the results map is written only by one goroutine and read only after a happens-before edge established by eg.Wait().
  • NF2 — No goroutine leaks. Every spawned goroutine exits on channel close, context cancellation, or error return; Run leaves goroutine counts unchanged (verified empirically during adversarial review).
  • NF3 — Bounded worker pool. In-flight tasks never exceed maxWorkers (16); a 10k-task wide graph completes in milliseconds-scale time on a laptop (exact figures are machine-dependent).
  • NF4 — Repeated Runs are independent. All scheduling state lives inside one Run invocation; the same *Graph can be run repeatedly, even concurrently, without state leaking between invocations.

03Architecture Decisions

D1: Dispatcher-multiplexed worker pool — single-owner state

// Dispatcher: sole owner of scheduling state. When all workers are
// busy, the dispatcher multiplexes between offering the next ready
// task and collecting completions — blocking on either alone would
// deadlock the other side.
eg.Go(func() error {
    ...
    if len(queue) > 0 {
        select {
        case ready <- queue[0]:
            queue = queue[1:]
            continue
        case <-cctx.Done():
            return cctx.Err()
        case ev = <-completions:
        }
    }...

The entire scheduler is one goroutine owning three pieces of mutable state — the in-degree map, the ready queue, and the results map. Workers are stateless: receive, run, report. Because only the dispatcher writes the results map, and callers read it only after eg.Wait() returns (which establishes a happens-before edge with the dispatcher's exit), there are no mutexes anywhere and the race detector stays silent by construction. This is the design lesson worth keeping: a mutex is often the symptom of a missed ownership decision. Ask "which single goroutine should own this data?" before asking "how do I lock this data?"

D2: The multiplex fix — why the dispatcher must select on both directions

// First version (deadlock-prone):
case ready <- queue[0]:   // blocks until a worker takes it
// ...but completions pile up unread meanwhile!

This fix came straight out of adversarial review, and it's the deepest lesson in the project. Consider the naive dispatcher that blocks sending on ready whenever all workers are busy. Now suppose every worker is itself blocked trying to send its completion on completions. Nobody can take a new task until someone frees up; nobody frees up until the dispatcher reads their completions; the dispatcher can't read completions because it's stuck offering work. Classic four-way handshake deadlock — reachable with as few as three tasks. The repair: when the queue is non-empty, a single select multiplexes sending work, receiving completions, and cctx.Done(), so progress is always possible from at least one direction. When the queue is empty, the dispatcher simply waits for completions. The general rule: any goroutine that feeds and drains a ring of peers must be able to make progress in both directions concurrently.

D3: Unbuffered channels as semaphore and synchronization point

ready := make(chan *Task)
completions := make(chan completion)
...
workers := len(g.tasks)
if workers > maxWorkers {
    workers = maxWorkers   // capped at 16
}

Both channels are unbuffered, deliberately. On the ready side this makes the handoff itself the concurrency limit: a send completes only when a free worker receives, so at most len(workers) tasks are ever executing — no separate semaphore, no counter to drift. On the completions side it forces every finished task's result through the dispatcher's ownership boundary, keeping the state machine single-writer. Buffering would feel faster but would silently break both properties: buffered sends don't block, so the bound evaporates and completions could arrive while the dispatcher believes otherwise. The worker count is min(number of tasks, 16) — enough to exploit parallelism in stress tests, small enough that a pathological graph can't spawn thousands of goroutines.

D4: Panic containment at the boundary — runSafely

func runSafely(t *Task, ctx context.Context) (value any, err error) {
	defer func() {
		if r := recover(); r != nil {
			value = nil
			err = fmt.Errorf("pipeline: task %q panicked: %v", t.ID, r)
		}
	}()
	if t.Run == nil {
		return nil, fmt.Errorf("pipeline: task %q has nil Run", t.ID)
	}
	return t.Run(ctx)
}

Two hardening decisions landed here after adversarial review flagged them. First, a nil Run func was originally accepted by Add and crashed the process at dispatch time — a nil function dereference inside an errgroup-spawned goroutine is unrecoverable from the caller, so one malformed task took down the whole binary. Add now rejects it eagerly, and runSafely checks defensively again in case one slips past. Second, errgroup famously does not recover panics from its goroutines — a panicking task body would crash everything. Since an orchestrator's whole contract is "failures come back as errors," the wrapper converts panics into wrapped errors carrying the task ID and panic value, which then flow through the normal cancellation machinery. The transferable rule: at any boundary where you invoke arbitrary user code inside a library-managed goroutine, recover and convert — the alternative is your library having a remote-code-crash primitive.

D5: Fail-fast validation with deterministic, injection-safe errors

sort.Strings(ids)   // deterministic traversal order
...
chain := append(append([]string(nil), stack[start:]...), dep)
quoted := make([]string, len(chain))
for i, id := range chain {
    quoted[i] = strconv.Quote(id)   // hostile IDs cannot forge log lines
}
return fmt.Errorf("pipeline: %w: %s", ErrCycle, strings.Join(quoted, " -> "))

Validation runs before any goroutine spawns: unknown deps first (cheap map lookups), then a white/gray/black DFS for cycles that reconstructs the offending chain from its own stack. Two details repay attention. Determinism: map iteration order is random, so both validation passes sort IDs first — the same invalid graph reports the same lowest-ID offender on every run, making tests and bug reports reproducible. Injection safety: task IDs are attacker-controlled strings; an ID like "\nFORGED LOG LINE severity=critical" interpolated raw into an error could forge additional log lines downstream. Quoting every member with strconv.Quote neutralizes control characters, and a test plants exactly such an ID to prove no raw newline survives. Treating error text as an output channel that needs sanitizing is a habit most codebases learn the hard way.

D6: Error precedence — the caller's context wins

waitErr := eg.Wait()
// Cancellation of the caller's context takes precedence: report
// ctx.Err() even if some in-flight task also surfaced an error.
if err := ctx.Err(); err != nil {
    return nil, err
}
if waitErr != nil {
    return nil, waitErr
}
return &Results{vals: results}, nil

When a run ends, several things may be true at once: the caller cancelled, and/or a task failed. Which error should Run return? The chosen precedence — caller cancellation first — encodes an honest causal story: if you cancelled the run, the informative answer is context.Canceled, not whatever error some interrupted task happened to emit while being torn down (task functions racing cancellation often produce spurious errors of their own). Only when the caller's context is clean does the first task error surface, wrapped with the failing task's ID so errors.Is works on sentinels. Error-selection rules are API design: decide them explicitly, document them, and test them — ambiguity here multiplies into flaky assertions downstream.

04Concept Walkthroughs

errgroup patterns — one contract, three behaviors

eg, cctx := errgroup.WithContext(ctx)
eg.Go(func() error { ... })   // dispatcher + N workers
waitErr := eg.Wait()

errgroup.WithContext bundles three mechanisms into one object. WaitGroup semantics: Wait blocks until every function passed to Go has returned — the join point that makes goroutine leaks structurally impossible here, since Run cannot return while any worker lives. Error capture: the first non-nil return wins; subsequent errors are dropped, and that first error is what Wait yields — pipeline wraps it with the failing task's identity along the way. Derived context: the second return value cctx is cancelled when the first goroutine fails or when the parent context cancels — which is how one task's failure becomes every sibling's problem without anyone wiring signals manually. Note what errgroup does not do: it doesn't recover panics and doesn't limit concurrency by itself. Both gaps are filled explicitly here — runSafely for the former, the fixed pool size for the latter.

Context cancellation propagation — reaching every blocking point

for {
    select {
    case <-cctx.Done():
        return nil          // workers exit promptly mid-idle
    default:
    }
    select {
    case t, ok := <-ready:
        ...
    case <-cctx.Done():
        return nil
    }
}

The subtle discipline: cancellation must reach every place a goroutine can block, not just task bodies. Workers can block receiving from ready — so that receive shares a select with cctx.Done(). Workers can also block sending to completions (the dispatcher may have already exited after its own cancellation branch) — so the completion send is likewise guarded. The dispatcher guards both its send and receive paths. Miss any one of these and cancellation stops being prompt: the bounded-time test exists precisely because "it propagates eventually" and "it propagates quickly" are indistinguishable by reading code. Also notice the pre-check at the top of the loop: a cancelled-before-start worker exits immediately rather than waiting for a receive that will race with Done — selecting fairly between an always-ready channel and a closed one is nondeterministic, so the explicit check removes the coin flip.

Deadlock avoidance — the four-way handshake trap

The scenario: dispatcher blocked sending task T (pool full) · workers blocked sending completions (nobody reading) · completions can't be read (dispatcher blocked) · T can't be taken (workers blocked). Four parties, zero progress, forever.

This deadlock is invisible to the race detector and won't reproduce in small graphs by luck — it needs the exact timing of "pool saturated + dispatcher holding a ready task." The cure is architectural, not a timeout band-aid: restructure the dispatcher's loop so that whenever it holds work to offer, it simultaneously remains receptive to completions. In Go that restructuring is a select with both directions plus Done. The deeper skill being taught is deadlock reasoning as cycle-finding over a wait-for graph: draw an arrow from each blocked goroutine to whatever it waits on; a directed cycle among the arrows predicts deadlock. Before shipping concurrent code, draw the arrows. If any cycle exists among blocking operations that aren't broken by context or buffering, you've shipped a time bomb that stress and timing will eventually detonate.

Generics via Get[T] — untyped storage, typed retrieval

func Get[T any](r *Results, id string) (T, bool) {
	var zero T
	if r == nil {
		return zero, false
	}
	v, ok := r.vals[id]
	if !ok {
		return zero, false
	}
	t, ok := v.(T)
	return t, ok
}

Tasks return (any, error) — unavoidable, since a heterogeneous DAG's outputs differ per node and Go's type system won't track per-ID types through a map. The generic accessor reconciles convenience with safety: the caller states the expected type once at the call site, the type assertion checks it at runtime, and every failure mode — wrong type, missing ID, nil receiver — degrades to (zero, false) instead of a panic. Three small idioms deserve note. var zero T is the standard way to produce a zero value of a type parameter. The nil-receiver guard lets callers write Get[string](res, x) without pre-checking res after a failed run — mirroring how nil maps and nil slices are safe to read. And the comma-ok form keeps the API total: there is no input for which Get panics, which makes it usable in defer blocks, cleanup paths, and tests without ceremony.

05Testing Strategy

Bounded-time cancellation — asserting latency, not just correctness

begin := time.Now()
res, err := g.Run(ctx)
elapsed := time.Since(begin)

const budget = 5 * time.Second
if elapsed >= budget {
    t.Fatalf("Run took %v after cancellation; want return within %v", elapsed, budget)
}
if !errors.Is(err, context.Canceled) { ... }

The nastiest failure mode of an orchestrator is hanging — and a hang looks identical to "slow CI" unless you measure. TestCancellationPropagationBoundedTime starts two tasks that block until their context is done, cancels roughly 50–60 ms in (both started, short settle delay), and asserts Run returns well under a 5-second wall-clock cap with errors.Is(err, context.Canceled) and no typed results. The generous cap is deliberate: the assertion targets deadlocks and lost cancellations (which blow past 5 s instantly), not scheduler micro-latency, so it stays stable on loaded machines. The same bounded-return pattern guards the sibling-cancellation and panic-containment tests, each wrapping Run in a helper goroutine with a 5-second timeout so the test suite fails with a message instead of hanging CI.

Ordering proofs via observable side effects

mustAdd(t, g, &Task{ID: "b", Deps: []string{"a"}, Run: func(ctx context.Context) (any, error) {
    if _, ok := st.get("a"); !ok {
        return nil, errors.New("b ran before a published")
    }
    ...

You cannot assert "b ran after a" by inspecting the final result — both orders produce the same output values. Instead the tests plant a mutex-guarded shared store that each task writes and each dependent reads: if a dependent ever starts before its dependency published, the probe fails the run from the inside. The negative variant goes further: with the dependency deliberately blocked, the test confirms Run hasn't completed after 100 ms (consumer didn't sneak past the gate), then releases and joins. This technique — encoding ordering constraints as runtime-checkable probes inside task bodies — turns a property you care about into something the suite can catch nondeterministically-but- reliably, especially under repeated runs and the race detector.

-race discipline — the detector as a required gate

The rule: for this project, go test passing is necessary but not sufficient. go test -race ./solution/... is the real gate — the results map's safety depends on a happens-before edge (dispatcher exit ↔ eg.Wait() return) that only the detector can verify dynamically.

Every concurrency claim in this doc is backed by the detector: single-owner scheduling state, the post-Wait results read, double-Run independence, and eight-way concurrent Run calls on one graph were all exercised under -race -count=2 during review. The detector finds races only on executions that actually interleave badly, so the stress test (200 tasks, atomic CAS-tracked max concurrency) doubles as interleaving pressure — high contention widens the space of schedules the detector samples. Treat -race clean as a property you re-prove per change, not a one-time certificate.

Regression tests born from adversarial review

func TestAddNilRunRejected(t *testing.T) {
    ...
    if !strings.Contains(err.Error(), "nil Run") { ... }
    if !strings.Contains(err.Error(), "norun") { ... }
}

func TestTaskPanicBecomesWrappedError(t *testing.T) {
    ... // panic("boom") must yield an error naming "panicky" AND "boom"
}

Two of the sharpest tests exist because review agents broke the implementation on purpose. TestAddNilRunRejected pins the fix for a finding where a nil Run func sailed past Add and crashed the process at dispatch — the test demands rejection with a message naming both the defect ("nil Run") and the offending ID. TestTaskPanicBecomesWrappedError pins the panic-containment contract: a panicking body must become a wrapped error carrying the task ID and panic value, dependents must not run, Results must be nil, and Run must return within its bounded window. Similarly, TestCycleErrorQuotesIDs plants a newline-bearing hostile ID and asserts the rendered error contains no raw newline. These are regression tests in the truest sense: executable memories of ways the code was actually broken, so those specific wounds can't silently reopen.

Determinism and completeness sweeps

The remaining suites round out the contract. TestUnknownDepDeterministicOffender runs Validate twenty times on a graph with multiple offenders and requires the lowest-ID one every iteration — flushing out map-order leakage that a single run would hide. TestValidateCycleNamesMembers and TestSelfCycle cover the DFS across three-node rings and self-loops. TestWideParallelOrderIndependent verifies fifty independent tasks' results by ID regardless of completion order, while TestConcurrencyStress tracks peak simultaneous tasks with atomics and fails if observed parallelism drops below two — proving the pool genuinely overlaps work rather than accidentally serializing. TestGetTypedRetrieval sweeps every failure mode of the generic accessor, including nil receivers. Each is one sentence of contract, executable.

06Go in the Wild

Where this stack runs in production

DAG orchestration over Go's concurrency primitives powers some of the largest workflow systems in industry — you've now built their in-memory core:

  • Temporal — the durable-workflow platform (successor to Uber's Cadence, both written substantially in Go). Its SDK executes your workflow functions as deterministically-replayed task graphs with exactly the concerns pipeline teaches — dependency ordering, cancellation propagation, failure isolation — plus persistence and replay across process restarts. Its client-facing Go APIs lean on the same context-and-error-wrapping idioms you implemented.
  • Argo Workflows — the Kubernetes-native workflow engine, written in Go, that runs millions of CI/CD and batch pipelines. Its core abstraction is precisely a DAG of steps with fan-out/fan-in, retry policies, and dependency-driven scheduling — pipeline's diamond and wide-graph shapes are Argo's daily bread, scaled up and made durable via CRDs.
  • Airflow-alternatives in the Go ecosystem — teams escaping Python's Airflow increasingly reach for Go-native schedulers (e.g., Dagu-style single-binary DAG runners, and Luigi/Prefect-style orchestration reimplemented atop Go services). Their common architecture — parse the DAG, validate acyclicity, schedule ready nodes, propagate failures — mirrors pipeline's Validate-then-dispatch structure almost line-for-line.
  • Build systems and CI schedulers — Bazel-style remote execution frontends and Go's own build cache treat compilation units as a dependency graph scheduled onto bounded worker pools. The in-degree-countdown scheduling you wrote is the same algorithm, and the same saturation-deadlock hazards apply to their task dispatchers.

Why errgroup became the ecosystem's default

  1. It makes goroutine lifetime lexical. Before errgroup, every concurrent operation needed bespoke bookkeeping — a WaitGroup here, an error channel there, a done channel for early exit, and a comment begging future maintainers not to miss a return path. errgroup collapses all four into one type whose Wait is the single join point. Docker, etcd, Kubernetes controllers, and CockroachDB all adopted it for exactly this reason: leaked-goroutine bugs stopped being a review category and became a structural impossibility.
  2. First-error-wins with automatic cancellation matches how failures actually cascade. In distributed systems, when one shard fails, continuing its siblings usually wastes work or produces inconsistent partial output. errgroup's derived context encodes the policy "first failure stops the world" in five lines of library code — and pipeline shows how to extend that policy inward, so cancellation reaches not just sibling goroutines but the scheduler coordinating them.
  3. Its known gaps teach as much as its features. errgroup neither bounds concurrency nor recovers panics — deliberate scope choices that push you to the patterns production code needs: fixed worker pools over unbounded Go calls, and explicit recover wrappers around third-party callbacks. Every serious user of errgroup eventually writes both; you did, on purpose, with tests.

The through-line: a DAG orchestrator is not exotic technology — it is a dispatcher that owns a ready queue, a bounded pool that executes, and a context threading cancellation through every blocking point. Master those three moving parts here, and Temporal's documentation, Argo's DAG spec, or any scheduler codebase you open next will read as variations on a theme you've already implemented, raced, deadlock-tested, and reviewed.
