01Stack Evaluation

The stack: sync/atomic + net/http + encoding/json, zero dependencies

metricsd is built from three corners of the standard library: sync/atomic for lock-free counters, gauges, and histogram sums; net/http both to poll targets (http.Client) and to serve the exposition endpoint (ServeMux, including Go 1.22's /history/{name} path wildcards); and encoding/json to parse scraped values out of target payloads. No client library, no storage engine, no go.sum. Where project 08 proved generics make broker APIs type-safe, project 09 asks a sharper question this stack answers uniquely: when is an atomic operation better than a mutex? Every metric type in this project gives a different answer.

Rejected alternatives

  • prometheus/client_golang — the obvious choice and the whole reason not to use it: the point of this project is building the exposition format by hand once. Emitting name_bucket{le="0.5"} 3 yourself teaches you what cumulative buckets, the implicit +Inf bucket, and _sum/_count lines actually are. After this project, the official library's types are documentation instead of magic — you know precisely what its histograms do on every Observe.
  • Full TSDB-style storage — appending samples to disk with chunk files, compaction, index structures. Rejected because the lesson is the memory/time tradeoff, which a ring buffer makes vivid: 64 slots per target is ~1 hour of history at a 1-minute interval, allocated once, never growing, oldest data silently overwritten. A real TSDB buys unlimited history at the cost of exactly the complexity (persistence, retention policies, compaction) that would bury the concurrency lessons this project exists for.
  • Mutex-guarded counters everywhere — the naive implementation would put a single sync.Mutex around all metric writes. It would pass the tests, but it serializes every Inc across every goroutine in the process, and it skips the actual learning: choosing between atomics and locks per access pattern. This rejection is the project's thesis, not an optimization footnote.

What this stack uniquely teaches

  1. Atomic-vs-mutex decision-making as a first-class skill. Counters use a plain atomic.Add (no read-modify-write dependency beyond the add itself). Gauges use a pointer swap (last-write-wins needs no CAS). Histogram sums need a full CAS loop (float addition must read before writing). And ring buffers deliberately go back to a mutex — because the single-writer pattern makes the mutex free. Four cases, four different correct answers, all in one file.
  2. Ring buffers as bounded memory. Fixed capacity, O(1) append, automatic eviction of the oldest sample by overwrite. The wrap-around math — (next - n + size) % size — is small enough to verify by hand but general enough to appear unchanged in audio processing, network windows, and log rings.
  3. Exposition endpoints accept approximation. The snapshot loop documents that its output can be a torn read across metric lines — and explains why that's acceptable for scraping. Learning where linearizability is required versus merely nice is half of practical concurrent design.

02Requirements

Derived directly from metricsd_test.go — the executable specification. If your implementation passes these tests (including under -race), it satisfies the requirements.

Functional

  • R1 — Counter increments are exact under concurrency. Sixteen goroutines each incrementing a counter 1,000 times yield exactly 16,000 — no lost updates. Plain adds accumulate too (Add(name, 1024) then Add(name, 2048) reads 3072).
  • R2 — Gauges are last-write-wins with no torn values. Thirty-two goroutines set a gauge simultaneously after a start-gun; the observed value must equal one of the written values exactly — never a mix, never missing.
  • R3 — Histogram bucketing follows the table. With bounds [0.5, 1, 4]: observations land in the first bound ≥ the value; buckets are cumulative; values above every bound fall only into +Inf; and _count equals total observations while _sum accumulates exactly (0.25 + 0.75 + 2.5 = 3.5).
  • R4 — Bucket bounds are locked at first use. A later Observe for the same name with different bounds is ignored entirely: the snapshot must be byte-identical afterward — neither the new value nor alternative bucket lines may appear.
  • R5 — Snapshot format is golden-exact. Counters render first (sorted), then gauges (sorted), then histograms with cumulative _bucket{le="..."} lines, trailing {le="+Inf"}, _sum, and _count — byte-for-byte against the expected text. An empty collector renders zero bytes.
  • R6 — The scraper parses JSON paths and accounts errors. Against an httptest server: target pool serving {"workers":{"active":7}} with path workers.active produces points with Value 7 and non-zero timestamps in its ring, plus gauge pool_last 7. Target flaky hitting a 500 increments flaky_errors, sets no gauge, and writes nothing to its buffer.
  • R7 — Immediate first tick, then interval discipline. Start scrapes immediately (no waiting one interval), subsequent ticks honor the interval; a 250 ms run at a 10 ms interval records between 15 and 30 ticks.
  • R8 — Stop is idempotent and deadlock-free. Two consecutive Stop calls complete promptly; History remains safe to call after Stop.
  • R9 — Handler serves both endpoints. GET /metrics returns the exposition text (counter lines and scraped gauges present); GET /history/{name} returns the ring as a JSON array of Points; unknown names return an empty array with status 200.

Non-functional

  • NF1 — Lock-free record hot paths. Once a metric name exists, Inc/Add/SetGauge/Observe never acquire the collector lock again — only atomics.
  • NF2 — Clean under -race. All concurrency proofs pass the race detector; the scraper's goroutines (loop + per-target fetches) synchronize exclusively through the documented locks and atomics.
  • NF3 — Bounded memory forever. Each target retains at most ringSize (64) samples regardless of runtime or tick count; snapshots are fresh copies, never aliases into the ring.
  • NF4 — Cancellation propagates. Stopping the scraper cancels in-flight HTTP requests via their contexts; no goroutine outlives Stop.

03Architecture Decisions

D1: Double-checked locking for metric creation

c.mu.RLock()
ctr, ok := c.counters[name]
c.mu.RUnlock()
if ok {
    ctr.Add(v)   // hot path: one RLock'd map probe, then pure atomic
    return
}

c.mu.Lock()
defer c.mu.Unlock()
if ctr, ok = c.counters[name]; !ok { // lost the creation race
    ctr = new(atomic.Int64)
    c.counters[name] = ctr
}
ctr.Add(v)

The cost structure of a metrics library is lopsided: any given name is created exactly once but incremented millions of times. So the lock is only for registration. The fast path takes an RLock, probes the map, and — if found — drops straight to a single atomic add; multiple incrementers share the read lock without contending. Only a cache miss escalates to the write lock, and the second check inside it handles the race of two goroutines registering the same name simultaneously: the loser reuses the winner's counter rather than clobbering accumulated counts. Gauges and histograms repeat the same pattern. This is the classic double-checked idiom, and it works here because map reads under RLock establish the happens-before edge that makes the published atomic.Int64 safe to touch lock-free afterward.

D2: Per-target ring mutex, justified by the single-writer guarantee

func (r *ring) add(p Point) {
    r.mu.Lock()
    defer r.mu.Unlock()
    r.buf[r.next] = p
    r.next = (r.next + 1) % ringSize
    if r.n < ringSize {
        r.n++
    }
}

A reviewer's instinct says "you just taught us atomics — why a mutex here?" The answer is in the package comment, deliberately: exactly one goroutine ever writes a given ring (the scrape loop's per-target fetch goroutine), and History reads are rare. An effectively uncontended mutex costs nanoseconds and — crucially — removes every memory-ordering subtlety of a hand-rolled atomic write index paired with a valid-count. Getting next and n coherent across two separate atomics without a lock is exactly the kind of puzzle whose solution is subtle enough to be wrong in ways -race can't even see. Choosing the dumb-but-obviously-correct tool when contention is provably absent is the senior move; knowing why it's provably absent is the lesson.

D3: The scrape loop — ctx + ticker + inner WaitGroup, immediate first tick

s.wg.Add(1)
go func() {
    defer s.wg.Done()
    ticker := time.NewTicker(interval)
    defer ticker.Stop()

    s.scrapeAll(ctx, tg)          // immediate first tick
    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            s.scrapeAll(ctx, tg)
        }
    }
}()

This is the canonical Go background-loop shape, assembled from parts each earning their place. The WaitGroup lets Stop block until the loop has fully exited — shutdown means "done," not "signaled." The ticker fires before the select loop starts, so callers get data immediately instead of waiting a full interval (the tests rely on this). The inner scrapeAll spawns one goroutine per target and waits for them all with its own WaitGroup — a slow target delays its own tick, not other targets, and the fan-out bound is simply len(targets), so no worker pool machinery is needed. Every HTTP request carries the loop's context, so Stop's cancel reaches into any in-flight fetch. Two lifecycle rules are documented on the API itself: calling Start twice is undefined, and Stop must happen-after Start — the cancel field is unsynchronized by design, written only in Start and read only in Stop, which is sound precisely because of that documented ordering.

D4: Handler — one mux, two routes, wired to the two subsystems

mux := http.NewServeMux()
mux.HandleFunc("GET /metrics", func(w http.ResponseWriter, _ *http.Request) {
    w.Header().Set("Content-Type", "text/plain; version=0.0.4")
    if err := c.Snapshot(w); err != nil {
        http.Error(w, "snapshot failed", http.StatusInternalServerError)
    }
})
mux.HandleFunc("GET /history/{name}", func(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    _ = json.NewEncoder(w).Encode(s.History(r.PathValue("name")))
})

Handler(c, s) composes both halves of the daemon behind one http.Handler: the collector's exposition text and the scraper's ring history. Note the Go 1.22 features doing quiet work — the method-prefixed patterns reject non-GET requests automatically, and r.PathValue("name") extracts the wildcard without a manual string split. The /metrics route propagates Snapshot's writer errors into a real 500 rather than serving truncated output with a 200; /history encodes directly to the response writer, streaming. One known limitation is deliberate and worth stating honestly: metric names are written verbatim into the exposition output with no validation — a caller passing a name with spaces or newlines could produce malformed format. Production libraries validate; this project trusts its caller and spends the budget on the concurrency lessons instead.

04Concept Walkthroughs

Three atomic shapes — and when atomics are NOT enough

// Counter: plain atomic add — the RMW is the whole operation
ctr.Add(v)

// Gauge: last-write-wins needs no CAS — writers don't read
g.Store(p)

// Histogram sum: float add MUST read-modify-write atomically
for {
    old := h.sumBits.Load()
    newSum := math.Float64frombits(old) + v
    if h.sumBits.CompareAndSwap(old, math.Float64bits(newSum)) {
        return
    }
}

The rule: pick the weakest primitive that covers your write pattern. Pure accumulation → Add. Overwrite-without-reading → Store. Anything that must read, compute, and write as one indivisible step → CAS loop.

The histogram sum is where the lesson bites. Float64 has no native atomic add, so the trick is storing the value's bits in an atomic.Uint64. Why not just load-and-store like the gauge? Because addition is read-modify-write: if two goroutines both load 3.5, both compute +0.5, and both store 4.0, one update vanishes — the exact lost-update bug the counter test proves impossible for Add. CompareAndSwap closes the window: the store succeeds only if the bits still hold the value we read; on failure, someone else moved the world, so we retry with their number. Also note the gauge design: SetGauge heap-allocates a fresh *float64 per call and swaps the pointer — readers loading the pointer see either the complete old value or the complete new one, never a torn half-written float.

Eventually-consistent snapshots — the torn read you choose on purpose

histos := make(map[string]*histogram, len(c.histos))
for n, h := range c.histos {
    // Counts and sums stay readable after RUnlock because each is
    // individually atomic. Accepted tradeoff: a snapshot is
    // eventually-consistent, not linearizable...
    histos[n] = h
}
c.mu.RUnlock()   // ...then reads buckets/sums outside the lock

Snapshot copies counters and gauges inside the RLock, but for histograms it copies only the pointers and reads bucket counts afterward, unlocked. That means one scrape can contain a counter read at instant T1 and a histogram bucket updated at T2 — lines in one response reflecting different moments of reality. This is a documented, deliberate tradeoff, spelled out in the source comment. The reasoning: Prometheus treats every scrape as a point-in-time sample of an approximation anyway; making the snapshot linearizable would force every Observe to contend on the same lock, converting the entire write path from lock-free back to serialized — destroying the project's core property to buy a coherence guarantee nobody downstream consumes. Knowing where consistency boundaries can safely blur is as valuable as knowing how to enforce them.

Ring buffer wrap-around math

// Append: overwrite slot, advance, cap the count
r.buf[r.next] = p
r.next = (r.next + 1) % ringSize

// Read: oldest sample lives at (next - n) mod size,
// possibly straddling the end of the array
start := (r.next - r.n + ringSize) % ringSize
copy(out, r.buf[start:])
if start+r.n > ringSize {
    copy(out[ringSize-start:], r.buf[:r.n-(ringSize-start)])
}

A ring is just an array plus the invariant "n valid samples ending just before next." While filling, next walks forward and n grows; once full, appends stomp the oldest slot and n pins at 64 — eviction by overwrite, no shifting, no allocation. Reading is the fiddly direction: the logical sequence wraps physically, so the copy splits at the array boundary (the modulo dance in (next - n + size) % size keeps the subtraction non-negative). Snapshot returns a freshly built slice rather than the internal array — callers can hold it forever without pinning or racing the ring. Verify the math with a pencil on a 4-slot example once; it will never feel opaque again.

Anatomy of the Prometheus text format

bytes_in 2048                          # counter: bare name + integer
queue_depth 3.5                        # gauge: name + float
latency_bucket{le="0.5"} 1             # ≤ 0.5ms: 1 observation
latency_bucket{le="1"} 2               # ≤ 1ms: 2 (cumulative!)
latency_bucket{le="4"} 3               # ≤ 4ms: 3
latency_bucket{le="+Inf"} 3            # everything, always == _count
latency_sum 3.5                        # sum of observed values
latency_count 3                        # number of observations

The format is line-oriented: name value, optionally with {label="value"} labels. The subtle parts are the histogram conventions. Buckets are cumulative — each le ("less than or equal") line counts all observations up to that bound, which is why the rendering loop accumulates as it goes rather than emitting raw per-bucket counts. The final {le="+Inf"} bucket catches everything above the highest configured bound and, by construction, always equals _count. Downstream systems derive quantiles from bucket deltas, which is why the golden test pins the cumulative layout byte-for-byte: emit raw counts there and every percentile your users compute becomes quietly wrong. Content type text/plain; version=0.0.4 is the ecosystem's handshake saying "this body parses as Prometheus exposition."

Tick discipline without flakes

A ticker guarantees at least interval spacing, never exactly N ticks in T wall seconds — scheduler pauses, GC, and slow targets all eat into the budget. So the timing test asserts a generous band: ~250 ms at a 10 ms interval must produce between 15 and 30 ticks. The lower bound catches real bugs (a loop that waits an extra interval, a scrape that blocks the next tick); the upper headroom keeps CI honest on loaded machines. The deeper design choice feeding it: scrapeAll completes fully before the next ticker fire is processed, so ticks never overlap themselves — a hung target stretches the effective period rather than stacking unbounded goroutine generations. Time-based tests fail by being too tight far more often than by being too loose; the band exists so the test fails only when the code is actually wrong.

05Testing Strategy

The 16,000-counter concurrency proof

const goroutines, perG = 16, 1000
// ...16 goroutines × 1000 × c.Inc("requests")...
got := snapshotMap(t, c)["requests"]
if got != strconv.Itoa(goroutines*perG) {
    t.Fatalf("counter total = %s, want %d (lost updates = not atomic)", ...)
}

This is the lock-free property rendered as arithmetic: with a naive count++ on shared memory, 16,000 concurrent increments deterministically lose updates (load/store races drop some entirely), so the test fails loudly and names the disease in the message. With a genuine atomic.Int64, the total is exact every run — and under -race, any unsynchronized shortcut in your implementation is flagged independently. The companion gauge test attacks the opposite failure mode: 32 racers setting one value, asserting the result is one of the written values. It can't assert which (that's genuinely nondeterministic) but it catches torn or vanished writes — the assertion is weaker than the counter's, exactly as the semantics allow.

The golden snapshot test

TestSnapshotGoldenFormat feeds a fixed diet of metrics and compares the full exposition output against a literal string, byte-for-byte. Golden tests look brittle and are deliberately so: the format is the contract, consumed by parsers expecting exact syntax, and any drift (missing space, wrong sort order, non-cumulative buckets, float formatting like 3.50 instead of 3.5) must break the build, not production dashboards. Sorted-name emission within sections makes output deterministic — map iteration order would otherwise flake the test and, worse, make scrapes incomparable. TestSnapshotEmptyCollectorRendersNothing covers the degenerate case: an empty collector must produce zero bytes, not a stray newline.

Canned-JSON scraping against httptest

srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    switch r.URL.Path {
    case "/stats":
        fmt.Fprint(w, `{"workers":{"active":7}}`)
    default:
        http.Error(w, "boom", http.StatusInternalServerError)
    }
}))

One httptest server plays both roles: a healthy target serving canned JSON and a failing one returning 500s — no network, no external services, deterministic. The assertions then walk the full success path and the full failure path: pool points carry Value 7 parsed through the dotted path workers.active with non-zero timestamps in oldest→newest order plus the derived pool_last gauge; flaky accumulates flaky_errors, never gains a _last gauge, and leaves an empty ring — proving failed fetches skip buffer writes rather than recording garbage. The helper waitFor polls conditions every 2 ms up to a generous deadline, converting "eventually true" async behavior into a deterministic assertion without sleep-and-pray timings.

Lifecycle edges and the generous-bounds philosophy

TestStopIdempotent runs Start → brief sleep → Stop → Stop inside a goroutine with a 5-second watchdog: the second Stop must be a safe no-op, and any deadlock surfaces as a named timeout instead of a hung suite. TestObserveBoundsLockedAtFirstUse snapshots before and after a mismatched-bounds Observe and demands map equality — neither growth nor mutation permitted. And the tick-discipline test embodies the project's timing philosophy: assert a wide band (15–30 hits where theory says 25), because a timing test that's tighter than the platform's scheduling jitter doesn't catch bugs, it manufactures them. Throughout, primary assertions check counted things (values, lengths, error totals); timing appears only as watchdogs with huge margins — the same methodology as project 08, now applied to a system that actually runs on a clock.

06Go in the Wild

Prometheus itself is Go — and so is most of its ecosystem

The exposition format you emitted by hand is the lingua franca of cloud-native monitoring, and the systems speaking it are overwhelmingly written in the language of this course:

  • Prometheus — the CNCF monitoring standard, written in Go. Its pull-based model is exactly what you built the server side of: it periodically scrapes /metrics endpoints, parsing the same name{labels} value lines your Snapshot emits. Its client_golang library is the production version of your Collector — after this project, reading its source feels like reviewing a familiar design.
  • VictoriaMetrics — a Go-written, high-performance TSDB often deployed as a Prometheus replacement. Its remote-write pipeline and storage compression are the "full TSDB" road not taken in this project, industrialized: same ring-buffer instincts, scaled to billions of samples.
  • Grafana Agent (now Grafana Alloy) — a Go telemetry collector that scrapes endpoints, transforms series, and fans results out — architecturally a souped-up version of this project's Scraper: targets, intervals, per-target state, error accounting.
  • Kubernetes — every component (kubelet, apiserver, etcd's Go clients) exposes Prometheus-format metrics on a port; cluster autoscaling decisions literally consume lines shaped like the ones your daemon serves.

Why lock-free counters matter at scrape scale

Metrics are the one instrumentation path that must get cheaper than the code it measures. A high-traffic service might increment request counters millions of times per second — if each increment took a contended global mutex, observability itself would become the bottleneck, adding latency and serializing exactly the hot paths you're trying to watch. Atomic adds compile to single CPU instructions on the hot path, letting thousands of goroutines count concurrently with near-zero interference. This is why client_golang's counters are atomics behind the scenes, why VictoriaMetrics brags about lock-free ingestion, and why the double-checked registration pattern you wrote — lock once to create, then never lock again — is the shape real telemetry libraries ship. The ring buffer has an industry twin too: bounded recent-history windows appear in latency trackers, connection pool stats, and rate limiters wherever "the last N observations" is the right amount of memory to spend on the past.

From this project to production observability

Every concept here maps one-to-one onto production vocabulary: your Collector is a metrics registry; Snapshot is an exposition handler; the Scraper inverted becomes Prometheus itself; ring buffers become retention windows; the eventual-consistency of your snapshots reappears as the documented fact that scraped data is sampled, not transactional. When you later wire a real service to Prometheus, nothing about the wire format, the bucket semantics, or the concurrency model will be new — you'll recognize it, because you built the small true version first.
