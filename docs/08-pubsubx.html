01Stack Evaluation

The stack: generics + sync + channels, nothing else

pubsubx needs three things from the standard library — type parameters ([T any]), the sync package (Mutex, RWMutex, Once, WaitGroup), and buffered channels — plus context for bounded blocking. No message-broker library, no event bus, no go.sum. Where project 05 proved concurrency primitives don't need a library, project 08 raises the stakes again: this time the API surface itself is generic, so every type flowing through the system is one you chose at compile time.

Rejected alternatives

  • An interface{}-based broker — the pre-generics way: Publish(msg interface{}) into chan interface{}, with every consumer type-asserting on receive. It works, but it moves type errors from compile time to run time. With generics, b.Publish("oops") against a Broker[int] simply doesn't compile; with interface{}, the same mistake surfaces as a failed assertion in some handler, in production. The generic version prevents entire bug classes — that's the point worth seeing concretely.
  • NATS / MQTT client libraries — production-grade brokers would turn this into configuration: subjects, QoS levels, reconnect policies. The lesson becomes "read NATS docs" instead of "understand why evict-then-send is race-free only while one publisher holds the lock." Real broker libraries are excellent precisely because their internals solve the problems you learn to reason about here.
  • A single owner goroutine owning all broker state — genuinely considered and rejected, with the rationale written into the package comment. Publish would need a reply channel per call just to report its delivered count, and PublishBlocking would need careful multiplexing of many waiters onto one goroutine — more moving parts than the mutex scheme, with no added safety. Knowing when not to use "share memory by communicating" is half the lesson.

What this stack uniquely teaches

  1. Real type parameters flowing through channel types. Not a generic stack or map from a tutorial — here T travels through map[int64]*subscriber[T], into chan T, out as <-chan T handed to the caller. You watch inference work end-to-end and feel what [T any] buys over interface{}: the delivered count, the buffer, the close semantics are all identical for every instantiation.
  2. Backpressure as an API surface. Most libraries hide what happens when a consumer falls behind. pubsubx makes it an explicit enum — DropNew, DropOld, Block — captured per subscriber at Subscribe time. Choosing a policy becomes part of the contract you design, not an accident you debug.
  3. Slow-consumer isolation as a testable invariant. A stalled reader on a capacity-1 buffer cannot delay other subscribers or block the publisher. That property is asserted directly by the tests, turning "the broker shouldn't jam" from folklore into a regression-tested guarantee.

02Requirements

Derived directly from pubsubx_test.go — the executable specification. If your implementation passes these tests (including under -race), it satisfies the requirements.

Functional

  • R1 — Fan-out is complete and FIFO per subscriber. Publishing 50 messages to 3 subscribers reports delivered == 3 each time, and every subscriber receives exactly messages 0..49 in order, with nothing extra afterward.
  • R2 — A slow subscriber can't hurt anyone. With one fast sub (capacity 300) and one never-read sub (capacity 1), all 200 publishes complete without blocking; the fast sub still receives every message in order; the slow sub admitted exactly its first message and dropped the rest.
  • R3 — DropOld keeps the freshest messages. Five publishes into a capacity-3 subscriber leaves exactly messages 3, 4, 5 readable, in order — oldest evicted, size pinned at capacity, delivery count stays 1 throughout.
  • R4 — PublishBlocking honors cancellation. With a full Block subscriber and a 100ms context, the blocked publish returns context.DeadlineExceeded promptly (a watchdog bounds it at 3s), the overflow was never admitted, and the original buffered value survives untouched.
  • R5 — PublishBlocking admits when space frees. Once a consumer drains one slot, the pending message is admitted and arrives after the already-buffered value (FIFO), well within a generous elapsed-time backstop.
  • R6 — Only Block-policy subscribers gate PublishBlocking. A full DropNew subscriber doesn't stall completion; the Block subscriber admits behind its buffered value; the DropNew sub drops overflow silently. Both outcomes verified explicitly.
  • R7 — Close semantics are clean. After Close: Publish returns 0, already buffered values remain readable before the channel reports closed, double-Close is a safe no-op, and Unsubscribe after Close (twice!) panics nowhere.
  • R8 — Unsubscribe is idempotent and race-free. Eight goroutines each calling unsub() twice concurrently produce no panic; subsequent publishes deliver 0; the buffered value drains then the channel reports closed.
  • R9 — Capacity clamps to minimum 1. Subscribing with capacity 0 yields a working subscriber that admits one message.
  • R10 — Generics instantiate with any type. The same broker code serves Broker[point] (concrete struct) and Broker[any] (heterogeneous payloads including nil), with identical fan-out semantics.
  • R11 — Hammer survival. Eight goroutines mixing Subscribe, Publish, PublishBlocking, repeated Close, and Unsubscribe for 200ms complete without panic or deadlock, guarded by a 30-second watchdog.

Non-functional

  • NF1 — Send-on-closed is structurally impossible. Not "we were lucky" — the locking protocol makes close-during-send unrepresentable under any interleaving.
  • NF2 — Publishers never block. Plain Publish uses only non-blocking selects; even Block-policy subscribers degrade to DropNew for it.
  • NF3 — Flake-free under -race. Timing assertions are watchdogs with huge margins; primary assertions count events (delivered counts, buffer contents, closed flags).
  • NF4 — Bounded blocking. Any path that waits (PublishBlocking) is bound by the caller's context; Close may wait only for sends that are themselves already context-bounded.

03Architecture Decisions

D1: Two-level locking over an owner goroutine

// Broker.mu serializes broker-level state. Because Publish holds it
// for the whole fan-out, only one publisher mutates a channel
// buffer at a time — which is exactly what makes DropOld's
// "evict one, then send" sequence race-free.
b.mu.Lock()
defer b.mu.Unlock()
for _, sub := range b.subs {
    if sub.deliver(msg) { delivered++ }
}

Two designs were weighed, and the loser is documented in the package comment so you can audit the reasoning. An owner goroutine owning all state is the idiomatic-sounding choice — but Publish must return a delivered count, which means a reply channel per call, and PublishBlocking means many concurrent waiters multiplexed onto one goroutine: more machinery, more failure modes, zero added safety. The chosen scheme is two-level instead. Broker.mu serializes subscriber-map access and whole fan-outs; holding it across a Publish is what guarantees only one publisher ever touches a given buffer mid-delivery — the fact DropOld correctness rests on. subscriber.mu guards each channel's closed flag, and its job is subtler: making a specific panic impossible.

D2: Read-mode locks held across sends — why send-on-closed can't happen

func (s *subscriber[T]) deliver(msg T) bool {
    s.mu.RLock()
    defer s.mu.RUnlock()
    if s.closed { return false }  // lost the race with Unsubscribe/Close
    select {
    case s.ch <- msg: return true
    default:
    }
    ...
}

Go's most feared concurrency panic is send on closed channel, because the usual defenses (a boolean flag checked before sending) don't work: the check and the send are two operations, and a close can slip between them no matter how carefully you order them. The fix here is structural. Every sender takes the subscriber's RWMutex in read mode for the entire send — including any blocking wait inside blockingDeliver. Closing a channel requires the write mode lock. Since readers and writers exclude each other, a close physically cannot execute while a sender is mid-send, under any interleaving whatsoever. The unsubscribe path shows the discipline: remove from the broker map first (under b.mu) so no future Publish sees the subscriber, then take sub.mu write-mode to flip the flag and close. Double-close is likewise impossible: the closed flag lives inside the same critical section as the close(ch) call, so exactly one closer ever wins.

D3: Backpressure as a Policy enum, captured at Subscribe time

const (
    DropNew Policy = iota  // full? drop the incoming message (default)
    DropOld                 // full? evict oldest to admit newest
    Block                   // caller waits via PublishBlocking until admitted or ctx done
)

sub := &subscriber[T]{
    ch:     make(chan T, capacity),
    policy: b.policy,   // captured now; later SetDefaultPolicy won't affect me
}

Each subscriber snapshots the broker's current default policy when it subscribes. This is a deliberate coupling decision: a consumer's tolerance for loss shouldn't change out from under it because someone reconfigured the broker later. The three policies have sharply different shapes. DropNew is a pure non-blocking select — the simplest possible thing, and the default. DropOld does something clever only because D1's invariant holds: evict one element, then send, knowing no other publisher can interleave (Broker.mu is held) and consumers only ever remove elements — so after eviction there is guaranteed room. Block changes who feels the pain: the publisher waits, which is why plain Publish deliberately treats Block subscribers like DropNew (it promised never to block) and only PublishBlocking honors them.

D4: The PublishBlocking admission protocol

b.mu.Lock()
defer ...  // partition subs under the lock:
for _, sub := range b.subs {
    if sub.policy == Block && !sub.closed {
        blocking = append(blocking, sub)  // these gate completion
        continue
    }
    sub.deliver(msg)                     // ordinary drop semantics
}
b.mu.Unlock()

// then, outside the lock: one goroutine per Block sub,
// each polling admission every 250µs until admitted / removed / ctx done
wg.Wait()

Blocking delivery has to answer a hard question: the broker cannot observe consumers receiving from their channels — callers own those channels directly — so "wait for room" has no natural wakeup signal. The solution polls: retry admission every 250µs, exiting when admitted, when the subscriber disappears (a vanished subscriber counts as admitted — there's nobody left to wait for), or when ctx fires. Three contract details matter. First, non-Block subscribers are dispatched under the initial lock grab and never gate completion — R6 pins this. Second, the per-subscriber goroutines run outside Broker.mu, so one stalled Block subscriber can't freeze the whole broker. Third, the edge case the review flagged: if the broker closes while a publisher is mid-wait, the subscriber vanishes, blockingDeliver sees closed == true, and returns admitted. Mid-wait close = admitted — the message goes where it can, and the publisher isn't stranded. And yes: Block + context.Background() blocks until Close/Unsubscribe. That is the contract, not a bug — the API makes the escape hatches explicit.

D5: Subscribe-after-Close and other spec gap-fills

if b.isClosed {
    b.mu.Unlock()
    ch := make(chan T)
    close(ch)                        // immediately-closed channel
    var noop sync.Once
    return ch, func() { noop.Do(func() {}) }  // harmless no-op unsub
}

Every lifecycle corner gets an explicit answer rather than a shrug. Subscribing to a closed broker returns an already-closed channel plus a no-op unsubscribe — the caller's code runs unchanged, receives nothing, and cleans up harmlessly. Capacity below 1 clamps to 1, since a zero-capacity channel would change Block/drop semantics entirely. Unknown policy values fall back to DropNew rather than misbehaving silently. These aren't gold-plating: they're the difference between a type whose edge behavior you must memorize and one whose edges are all load-bearing and documented.

04Concept Walkthroughs

Generics beyond containers — typed channels as return values

func (b *Broker[T]) Subscribe(capacity int) (<-chan T, func()) {
    ...
    sub := &subscriber[T]{ ch: make(chan T, capacity), ... }
    return sub.ch, unsubscribe
}

Most generic Go code you've seen wraps slices or maps. Here the type parameter flows into the public API itself: the caller receives a <-chan T — receive-only, correctly typed — and the compiler enforces that a Broker[int] can never emit a string. Two details reward attention. The return type is the bidirectional chan T's receive-only projection, so callers can't close or inject into the broker's channel — capability restriction via type direction, for free. And TestGenericInstantiationWithInterfaceType shows New[any]() is still available as an explicit opt-out: heterogeneous payloads work, but you had to choose the erasure, per broker, at the type level — the exact inverse of interface{}-everywhere.

Buffered channel capacity as a backpressure contract

The rule: a channel's buffer size is a published agreement about how far a consumer may fall behind before someone (drops the new message | drops the old message | the producer waits). Choose it per consumer, and say which failure mode applies.

The tests treat capacity as observable behavior, not tuning. A capacity-1 subscriber that is never read admits exactly one message — asserted down to the value. A capacity-3 DropOld subscriber ends holding precisely the last three publishes. This is the mindset shift: in most code a buffered channel's size is a magic number; here it's part of the API signature (Subscribe(capacity int)) backed by proofs. The same reasoning scales up to real infrastructure — Kafka partitions, NATS queue limits, gRPC flow-control windows all encode "how far behind may you lag, and then what."

sync.Once for idempotent unsubscribe

var once sync.Once
unsubscribe := func() {
    once.Do(func() {
        b.mu.Lock()
        delete(b.subs, id)
        b.mu.Unlock()

        sub.mu.Lock()
        if !sub.closed { sub.closed = true; close(sub.ch) }
        sub.mu.Unlock()
    })
}

Cleanup functions get called multiple times in real systems — defer stacks, error paths, layered owners. sync.Once turns "call me at least once" into "exactly once," safely under concurrent invocation (eight goroutines × two calls each, per R8). Note the belt-and-suspenders layering: Once handles duplicate calls, the !sub.closed check handles the separate question of whether Close already got there first — either guard alone leaves a hole. Also notice what the closure captures: not the whole broker, just id and sub. Small closures capturing small facts are easier to reason about than god-closures capturing everything.

Lock ordering discipline — b.mu → sub.mu, never inverted

Two mutexes in one program invite deadlock the moment someone acquires them in opposite orders. This codebase has one rule, stated in comments and followed everywhere: b.mu first, sub.mu second, never the reverse. Audit the paths: Publish holds b.mu and acquires sub.mu (read) per subscriber; Unsubscribe briefly takes b.mu, releases it, then takes sub.mu — note it releases the outer lock before the inner, avoiding even nested hold time; Close takes b.mu, snapshots subscribers, releases, then closes each under its own sub.mu. No path ever holds sub.mu while acquiring b.mu, so the classic ABBA deadlock is unrepresentable. When you review concurrent code, trace the acquisition order across every method — if you can't write the ordering rule in one sentence, the code doesn't have one.

Hammer testing methodology

select {
case <-finished:
case <-time.After(30 * time.Second):
    t.Fatal("hammer test deadlocked")
}

You cannot enumerate the interleavings that might break a concurrent type — so instead, generate thousands of them. The hammer runs eight goroutines for 200ms, each cycling deterministically through all five operations (Subscribe+drain+Unsub, Publish, peek-then- Unsub, bounded PublishBlocking, periodic Close) driven by (g+i)%5. Determinism matters: pseudo-random scheduling seeds make failures unreproducible, whereas a fixed cycle failing under -race tends to fail again. The watchdog pattern is the second essential ingredient — a deadlock doesn't fail a test, it hangs the suite forever, so every potentially-hanging test runs in a goroutine with a hard timeout that names the disease ("deadlocked"). Run it as go test -race ./projects/08-pubsubx/... and the pair — data-race detector plus deadlock watchdog — covers the two ways concurrent code dies.

05Testing Strategy

FIFO-per-subscriber as an executable property

TestFanOutCompletenessPreservesOrder asserts the strongest thing available: 3 subscribers × 50 ordered messages, checking each subscriber's stream position-by-position against m, then asserting emptiness. Generic helpers make the checks type-safe: recvTimeout[T] receives with a 2-second backstop (and fails loudly on premature closure), while assertEmpty[T] treats "closed and empty" as empty — the correct post-Close state. Because each subscriber has an independent buffer, order could break independently per subscriber; the loop catches a scramble in any one of them.

Isolation proven via a deliberately unread subscriber

slowCh, slowUnsub := b.Subscribe(1)  // never read: stalls immediately
...
slowDelivered := delivered - total
if slowDelivered != 1 {  // cap-1 unread buffer admits exactly the first message

The isolation test creates the worst case on purpose: a capacity-1 subscriber that nobody ever reads. Then it demands the full triangle at once — 200 non-blocking publishes total (the fast path wasn't slowed), the fast sub received all 200 in order (isolation held), and the slow sub received exactly one message (drop semantics are precise, not approximate). Deriving the slow sub's count arithmetically from the returned delivered totals is elegant: no instrumentation hooks needed, the API's own return values are the measurement instruments.

DropOld eviction, pinned exactly

TestDropOldEvictsOldestKeepsNewest feeds 1..5 into a capacity-3 subscriber and asserts the residue is exactly [3, 4, 5] — oldest gone, newest kept, order intact. Every weaker assertion would leave a bug-shaped hole: asserting only "three values" misses wrong-victim eviction; asserting only "contains 5" misses duplicates; asserting only "size ≤ 3" misses leaks. The delivered-count-stays-1 check along the way confirms eviction doesn't disturb the accounting. This is the difference between testing that something happened and testing that the right thing happened.

Context cancellation with a deadlock watchdog

go func() { done <- b.PublishBlocking(ctx, "overflow") }()
select {
case err := <-done:
    if !errors.Is(err, context.DeadlineExceeded) { t.Fatalf(...) }
case <-time.After(3 * time.Second):
    t.Fatal("...did not return within bound after ctx cancellation (deadlock?)")
}

The blocking-publish tests follow a strict shape: run the risky call in a goroutine feeding a buffered result channel, select between the result and a timeout vastly larger than the expected duration (100ms deadline vs 3s watchdog). The primary assertion is the error's identity via errors.Is; the timing arm exists purely so a broken implementation fails with a diagnosis instead of hanging CI. Each test then verifies collateral state: the blocked message was never admitted, the pre-filled value survived, or — in the mixed-policy test — the Block sub admitted behind its buffered head while the DropNew sub dropped cleanly. Cancellation correctness is never inferred from "it returned"; it's confirmed by what did and didn't enter the buffers.

Lifecycle corners, enumerated

TestCloseSemantics walks the full post-Close script in one test: buffered values drain before the channel reports closed (Go's close semantics preserved, not fought), Publish returns 0, a second Close is silent, and unsubscribe-after-Close — called twice — is harmless. TestUnsubscribeIsIdempotentAndRaceFree escalates the same corner to concurrency: sixteen unsub calls from eight goroutines, then proof that the buffered message still drains and the channel still closes exactly once. TestSubscribeCapacityClampedToMinimumOne closes out the input-validation edge. Together they ensure the type's unhappy paths aren't just non-crashing but semantically defined — the property that makes a concurrency type usable by people who didn't write it.

The -race hammer protocol

go test -race ./projects/08-pubsubx/...

The hammer test (R11) exists for the race detector, not standalone: 200ms of eight-way interleaved Subscribe/Publish/PublishBlocking/Close generates enough scheduling variety that -race's happens-before tracking catches unsynchronized accesses a single orderly test would never touch. Its own body models good citizenship — draining possibly-closed channels with comma-ok receives, bounding every blocking publish with a timeout context — because a hammer test that itself races proves nothing. Watchdog at 30 seconds converts potential deadlock from a hung suite into a named, attributable failure. This is the acceptance ritual for any concurrent type: functional tests green, then the hammer, then both together under the detector.

06Go in the Wild

Pub/sub is everywhere in Go infrastructure

The broker you just built — topics, subscribers, per-subscriber buffering, backpressure — is the core of much of the world's messaging plumbing, and a remarkable amount of it is written in Go:

  • NATS JetStream — a Go-native messaging server where every one of the concepts here reappears at scale: subjects instead of a subscriber map, configurable retention instead of Policy, per-consumer ack pending limits instead of buffer capacity. Its "limits" vs "interest" vs "workqueue" retention modes are drop-old / drop-on-ack / queue semantics you can now name.
  • Redis pub/sub (Go clients) — go-redis's PubSub hands you a channel of messages with a channel-size option: literally the same "buffered channel per subscriber" shape, with the same open question — what happens when the client can't keep up — that this project forces you to answer deliberately.
  • Kafka consumers (sarama / franz-go) — consumer groups are fan-out with durability; the per-partition buffer and Channel/Block requeue strategies in sarama are DropOld-vs-Block decisions wearing production clothes. Lag — Kafka's central operational metric — is exactly "how full is the buffer," measured.
  • Cloud Run / internal event buses — countless Go services glue components together with small in-process brokers like this one before graduating to a network broker; recognizing when you've outgrown the in-process version is the skill this project sharpens.

Backpressure strategies, industry-wide

  1. Drop-new (lossy, cheap). Telemetry, metrics, log sampling: fresh data beats complete data, and the producer must never stall. Prometheus scrapes and statsd live here. Your DropNew default encodes the same judgment call: staleness is worse than absence.
  2. Drop-old / evict (bounded freshness). Ring buffers in observability pipelines, recent-messages views, LRU caches: keep the newest N, shed history. NATS JetStream's limit-based retention and Kafka's log retention are this policy with disk attached.
  3. Block (zero loss, latency risk). Financial orders, command queues: losing data is unacceptable, so someone must wait — the only question is whether it's the producer (your PublishBlocking + ctx), a broker-side queue with admission control, or downstream flow control like TCP windows and HTTP/2 SETTINGS_INITIAL_WINDOW_SIZE. Every blocking system eventually rediscovers the need for your context parameter: waiting must be cancellable.

Most real systems compose all three per stream — which is only possible when backpressure is an explicit, per-subscriber decision, exactly as it is here.

Why generics (1.18+) changed library APIs

Before Go 1.18, a reusable broker had two bad options: interface{} payloads (runtime casts, no static safety, silent bugs at 3am) or code generation (genny-style — type-safe but a build step, and N copies of the code). Generics removed the dilemma, and the ecosystem responded visibly: samber/lo brought LINQ-style utilities, constraint-rich libraries like golang.org/x/exp/constraints matured, and container/channel APIs across the ecosystem gained type parameters. But pubsubx shows the more interesting lesson: generics shine not in clever constraint math but in quiet cases like this — one implementation, every payload type, errors caught where they belong (compile time), and [T any] doing its job so unremarkably that the types just disappear into the program.
